# BNW GameCore의 x64 컴파일 이식

> 후속 단계에서 Lua x64 제공자의 실제 x86 동등성을 비교하고 연결 오류 40개를 해소하여 현재 미해결 심볼은 302개랍니다. 숫자 경계값도 실제 /MD 제공자로 재검증했사와요. [최신 Lua 제공자 기록](M2_LUA_PROVIDER.md)

> 이 문서는 최초 전체 컴파일인 attempt_005의 과거 기록이랍니다. 현재 attempt_009는 숫자 변환 경고 479곳을 해결했고, 남은 경고 343곳·미해결 연결 342개를 기록했사와요. 최신 범위와 시험은 [숫자 경계값 기록](M2_NUMERIC_BOUNDARIES.md)에 있답니다.

2026-09-24 작업 범위이와요. 독립 기반 모듈 다음으로 실제 BNW C++ 번역 단위를 AMD64 오브젝트로 만드는 단계랍니다. 연결 라이브러리와 실행부가 아직 준비되지 않았으므로 이 관문은 전체 DLL 링크·게임 실행과 구분하와요.

## 변경 전 요구사항

| ID | 요구사항·수용 기준 |
|---|---|
| P01 | 설치 SDK와 `SDK_BNW_Original`은 기존 1,105개 해시를 보존하고, 이식은 별도 `SDK_BNW_x64`에서 수행 |
| P02 | 이식 변경은 원본 해시·정확한 치환 횟수·변경 이유를 기록하고 반복 생성 시 사용자 변경을 덮어쓰지 않음 |
| P03 | 원본 BNW 프로젝트에 선언된 번역 단위를 목록화하고 실제 x64 컴파일러로 생성한 오브젝트의 머신 형식을 확인 |
| P04 | 포인터 폭·플랫폼 분기·구형 컴파일러 문법의 문제를 구분하여 수정하며, 규칙·밸런스·기존 저장 자료 폭을 임의로 변경하지 않음 |
| P05 | 실패 시도·컴파일 경고·미완료 링크 의존성을 보존하며 오브젝트 생성만으로 실행 성공을 주장하지 않음 |

영향 범위는 이 프로젝트의 `Source/Porting`, 생성된 `Source/SDK_BNW_x64`, `Build/SDK_x64`, 조사 도구·문서·evidence이와요. 기존 모드 Source·Build·설치 MODS와 게임 설치 경로에 배포하지 않으며, 기존 Mod ID·버전·저장 키·스키마·UI·효과를 변경하지 않사와요.

## 진행 상태

**BNW 프로젝트의 C++ 161개에서 AMD64 오브젝트 161개를 생성했사와요.** 다만 DLL 링크는 미해결 심볼 339개로 실패했으며 실행 가능한 x64 GameCore는 아직 없답니다. [컴파일 기록](../evidence/sdk_x64/build_result.json), [연결 실패 분석](../evidence/sdk_x64/link_analysis.json)

| 관문 | 결과·범위 |
|---|---|
| P01·P02 | 원본·복사본 1,105개 보존. 별도 이식본의 3개 파일에 해시와 횟수를 고정한 14개 치환 적용 |
| P03 | VS 2022 x64 컴파일러, C++14, `FINAL_RELEASE`·`/MD`·`/Od`·`/fp:strict` 구성에서 161개 컴파일. 각 COFF 머신 필드 `0x8664` 확인 |
| P04 주소 절단 | 관측된 `C4302`·`C4311` 제거. `C4302`·`C4311`·`C4312`는 이후 빌드에서 오류로 승격 |
| P04 할당기 실행 | 실제 수정 SDK 헤더를 별도 x64 프로그램에서 실행. 196개 배열 배치, 단언 18,240회, 높은 주소의 실제 할당 197회 검증 |
| P05 경고 기록 | 파일·행·경고 코드로 묶은 경고 위치 822개를 CSV로 보존 |
| P05 DLL 연결 | 운영체제·CRT 연결을 포함하여 시도. x86 SDK 라이브러리는 제외. LNK1120의 미해결 339개와 추출 목록 339개 일치 |

컴파일은 최적화 없는 이식 확인 구성이며 기존 x86 기준 DLL의 최적화 구성과 성능을 비교할 수 없사와요. `FINAL_RELEASE`에서 제외된 디버그 경로나 인스턴스화되지 않은 템플릿 전체의 안전성을 확인한 것도 아니랍니다.

## 변경 파일과 이유

기준 파일은 `Source/SDK_BNW_Original`이고 실제 이식 파일은 `Source/SDK_BNW_x64`에 있사와요. 정식 변경 정의는 [sdk_x64_patches.json](../Source/Porting/sdk_x64_patches.json)이랍니다. 원본을 Latin-1 바이트 대응으로 읽어 지정한 ASCII 부분만 치환하므로 전체 SDK의 문자 인코딩을 변환하지 않사와요.

| 파일 | 변경 | 보존·회귀 경계 |
|---|---|---|
| `CvGameCoreDLL_Expansion2/Lua/CvLuaPlayer.cpp` | `getTeam`의 인자 없는 const 인스턴스 멤버 포인터 형식을 명시 | 정적 `getTeam(PlayerTypes)` 오버로드와 구분. 반환값·인자 수·Lua 메서드 이름 유지. 실제 Lua 실행은 미검증 |
| `CvGameCoreDLL_Expansion2/CvRandom.cpp` | 로그의 인스턴스 주소를 `%p`·`void*`로 출력 | 난수 식·시드·호출 횟수·직렬화 코드는 변경하지 않음. 주소 문자열 폭에 의존하는 외부 로그 도구는 영향 가능 |
| `FirePlace/include/FireWorks/FBatchAllocate.h` | 바이트 수는 `size_t`, 주소 정렬 계산은 `uintptr_t`로 처리. 덧셈·곱셈 넘침 거부 | 논리 배열 차원 `nX/nY`는 기존 32비트 유지. 기존 정렬용 여유 공간 식 보존. 0행에서 할당 경계를 넘는 데이터 포인터 생성 방지 |
| 같은 할당기 헤더 | 직접 사용하는 `FDefNew.h`를 포함하고 쓰지 않는 `FArray.h` 간접 의존 제거 | 메모리 관리 매크로의 조건부 동작 유지. 전체 GameCore 재컴파일로 포함 관계 확인 |

Windows x64의 포인터를 32비트 정수에 저장하면 높은 주소 비트가 사라질 수 있사와요. 이번 변경에서는 주소 계산과 기존 32비트 게임 자료를 구분했답니다. [Microsoft 포인터 이식 규칙](https://learn.microsoft.com/en-us/windows/win32/winprog64/rules-for-using-pointers)

구형 `stdext::hash_map`은 `_SILENCE_STDEXT_HASH_DEPRECATION_WARNINGS`를 명시하여 이번 도구 세트에서 계속 사용하와요. 이는 제거 예정 기능에 대한 호환 설정이며, 일반 경고를 모두 숨기거나 `unordered_map`으로 바꾸는 설정이 아니랍니다. 같은 컨테이너 API를 유지했어도 **구형 v90과 최신 STL의 메모리 배치·순회 순서가 같다는 뜻은 아니므로** 후속 결정성 검증이 필요하와요. [Microsoft hash_map 문서](https://learn.microsoft.com/en-us/cpp/standard-library/hash-map-class?view=msvc-170)

## SDK 할당기 실행 검증

[sdk_x64_allocator_test.cpp](../Tests/sdk_x64_allocator_test.cpp)는 실제 이식 헤더의 `FAllocBase`·`FAllocArrayType`·`FAllocArray2DType`을 사용하와요. 자료형은 1바이트 정수·32비트 정수·double·12바이트 레코드·혼합 배열이랍니다. 새 게임이나 GameCore DLL을 로드하는 시험은 아니와요.

- 1차원 32개, 2차원 100개, 혼합 64개로 총 196개 배치를 시험했사와요. 차원 0, 행 길이 0, 여러 행과 서로 다른 자료형의 정렬·범위·행 간격을 포함하와요.
- 각 배열을 실제로 쓰고 읽은 뒤 해제했으며, 혼합 배열에서는 다른 배열의 값이 손상되지 않는지도 확인했사와요.
- 4개 크기 넘침 입력은 할당이나 출력 포인터 변경 전에 `bad_array_new_length`로 거부했고, 거부 뒤 정상 입력으로 다시 할당했사와요.
- 정상 배치와 복구 시험을 합한 197개 할당의 시작 주소가 모두 `0xFFFFFFFF`보다 높았사와요. 이번 실행의 범위는 `0x2664cdb8490`~`0x2664cdd0e80`이며 주소는 다음 실행에서 달라질 수 있답니다.
- 시험 실행 파일은 `/W4 /WX`에서 경고 없이 빌드되었사와요. **전체 GameCore의 822개 경고와는 다른 결과**랍니다.

[실행 기록](../evidence/sdk_x64_allocator/conformance.json)에 실제 주소 범위·실행 파일·시험 코드·헤더·로그 해시를 남겼사와요. 높은 **가상 주소**의 사용을 확인한 것이며 4GB 이상의 물리 메모리를 할당한 시험이나 실제 게임의 확장 주소 공간 수용 관문 통과는 아니랍니다. 비단순 객체의 생성·소멸, 과도하게 큰 정렬 요구, 모든 FireWorks 할당 제공자를 검증한 결과도 아니와요.

## 남은 경고와 링크 의존성

[compiler_diagnostics.csv](../evidence/sdk_x64/compiler_diagnostics.csv)는 같은 헤더가 여러 번 보고된 진단을 파일·행·코드로 묶었사와요. 템플릿의 모든 형식별 위험을 하나로 판정한 수치는 아니랍니다.

| 분류 | 코드·고유 위치 수 | 남은 작업 |
|---|---|---|
| 원본 문자 인코딩 | C4819: 325 | 주석과 실제 문자열을 구분하고 기준판의 바이트·표시 의미 검토 |
| 폭 축소·초기화 | C4244: 289, C4267: 98, C4838: 92 | Lua 정수·컨테이너 크기·차이·자료형별 허용 범위 확인; 단순 캐스트로 경고만 제거하지 않음 |
| 구형 선언·API | C4091: 5, C4996: 13 | 선언과 CRT 호출의 의미를 확인하여 정리 |
| 주소 절단·확장 | C4302·C4311·C4312: 0 | 현재 컴파일 구성에 한한 결과; 다른 구성과 실제 실행은 별도 검증 |

링크 시도는 161개 x64 오브젝트와 표준 Windows·CRT 라이브러리를 사용했사와요. 필수 SDK 라이브러리를 32비트 상태로 섞거나 `/FORCE`로 오류를 무시하지 않았사와요. 결과는 **미해결 외부 심볼 339개, DLL 생성 없음**이랍니다. 링크 실패 과정에서 생성된 `probe.lib`·`probe.exp`는 export 연결용 중간 산출물이며 누락된 서비스를 구현한 라이브러리가 아니와요.

[미해결 심볼 목록](../evidence/sdk_x64/link_unresolved_candidates.csv)은 실제 링크 진단의 미해결 이름을 추출하고 LNK1120 합계와 대조한 결과랍니다. LNK2019의 호출자 이름을 미해결 제공자에 섞지 않도록 구분했사와요. DB·현지화·지도·Lua·문자열·스트림 및 GameCore 유틸리티 계열이 포함되며, 하나의 심볼이 하나의 함수 구현 작업과 정확히 대응하지는 않사와요. 데이터·템플릿·import 이름과 전이 의존성도 추가로 분류할 대상이랍니다.

## 재현·배포·남은 관문

1. `build_sdk_x64.py`가 원본과 기존 이식본 해시를 검사하고 패치 계획에서 별도 소스를 생성한 뒤 컴파일하와요. 기존 생성 기록과 다른 이식 파일을 발견하면 덮어쓰지 않사와요.
2. `verify_sdk_x64_allocator.py`가 해당 생성 헤더를 포함한 독립 실행 시험을 수행하와요.
3. `analyze_sdk_x64.py`가 경고 목록과 실제 연결 실패를 기록하와요.
4. `stage_sdk_x64_port.py`가 원본·이식본·오브젝트·시험 기록을 재확인하고 변경 소스 3개·패치 계획·증거를 `Stage/GameCore_x64`에 보관하와요.
5. `verify_project.py`가 기존 구성요소와 새 산출물의 정합성을 함께 확인하와요. 이번 최종 정합성 검사는 48개 관문을 통과했으며 자체적으로 게임을 실행하지 않사와요.

컴파일 실패를 포함한 시도 1~5의 응답 파일·로그·당시 패치 계획·파일 해시를 `evidence/sdk_x64/attempts`에 남겼사와요. 처음에는 구형 컨테이너 설정이 막혔고, 다음 전체 컴파일에서 Lua 오버로드 오류를 발견한 뒤 수정했답니다. 생성 도구는 원본 파일의 바이트를 유지하며 변경을 패치 계획으로 재현하와요.

현재 Stage는 **변경 소스와 검토 근거 묶음**이며 설치용 DLL 패키지가 아니와요. 기존 게임·모드에 배포하지 않았사와요. 7개 기반 라이브러리의 완전한 x64 대체는 계속 0개이며, 다음 필수 관문은 339개 연결 요구의 제공자·의미 계약을 구현하고 실제 GameCore 초기화까지 연결하는 일이랍니다. 정수 폭·인코딩 경고, 저장·모드·UI 호환성, 멀티코어 턴 성능과 실게임 검증도 남아 있사와요.
