# 게임·지도 생성 실패의 소유권 복구

2026-09-26 / 전체 게임 초기화의 실패 복구에 앞서 CvGame과 CvMap 생성자의 부분 할당 누락을 수정했사와요. 기존 553개 패치를 보존하고 3개 패치를 추가한 556개 패치랍니다.

## 요구사항과 변경

| ID | 문제 | 변경·통과 조건 |
|---|---|---|
| CTOR01 | CvGame은 배열 7개를 차례로 할당하며 생성 실패 시 CvGame 소멸자가 호출되지 않음 | 생성자 내부 임시 소유자가 배열을 보관하고 타이머·reset 성공 뒤 기존 필드로 소유권 이전; 모든 실패에서 배열 잔존 0 |
| CTOR02 | CvMap은 생성 중 객체 개수를 먼저 올리며 reset 실패 시 배열과 개수가 남음 | 실패 시 기존 uninit으로 부분 저장소 정리, 객체 개수 복원, 원래 예외 재전달 |
| CTOR03 | 정상 생성과 실패의 의미 유지 | 할당 크기·초기 값·정상 호출 순서·예외 종류와 값 유지, 실패 뒤 새 생성 성공 |
| CTOR04 | 저장·게임 계약 보존 | SDK 클래스 필드와 배치·저장 버전·Mod ID·키·스키마·규칙·밸런스 변경 없음 |
| CTOR05 | 별도 개발 범위 | 프로젝트 Source → Build → Stage만 갱신, 설치 SDK·게임·MODS·실제 저장 파일 변경 없음 |

CvGame에는 표준 배열 소유자 선언을 위한 memory 헤더와 생성자 본문 수정만 추가하와요. CvMap은 생성자 마지막 reset 호출에 실패 정리 구간을 추가하며, 기존 reset·uninit·소멸자 본문을 유지하와요.

## 실행 근거와 한계

SDK의 CvGame 생성자·소멸자, CvMap 생성자·소멸자·reset·uninit 및 CvMapInitData 정의를 원본·수정본에서 추출하여 별도 AMD64 프로그램으로 실행했사와요. 전역 배열 할당/해제에 실패 계측을 넣어 실제 저장소의 생존을 관측했답니다.

| 시험 | 원본·수정본 각각의 결과 |
|---|---|
| 게임 실패 13종 | 배열 할당 지점 7개, 타이머 Start/Stop, reset 진입·중간·종료 예외 및 reset 메모리 부족 |
| 지도 실패 13종 | 자원 수 0·1·129개, 두 배열의 할당 실패, 두 목록 초기화와 호스트 지도 준비 호출의 예외 |
| 성공 생성 | 각각 30회; 모든 실패 직후 정상 생성·파괴를 별도 확인 |
| 원본 재현 | 게임 배열 63개·지도 배열 14개가 실패 후 잔존, 지도 개수 13건 미복원; 관측 후 시험에서 별도 정리 |
| 수정본 | 모든 실패 뒤 배열 잔존 0, 지도 개수 복원, 원래 예외 유지 |
| 정상 상태 | 게임 배열 초기 값, 기타 생성자 초기 값, 지도 기본 값·자원 수·정상 호출 순서 유지 |
| 검사 | 원본 7,902개, 수정본 7,876개; 합계 15,778개 |
| 빌드·의존성 | x64 /MD /W4 /WX 경고 0, Windows/CRT import 검사 후 실행 |

실패 사례 수는 실제 할당 실패와 호출 경계에서 주입한 합성 예외를 합한 수랍니다. 타이머·지도 목록의 합성 예외가 현재 실제 서비스에서 발생한다고 입증한 것은 아니며, 해당 경계를 통해 예외가 전파될 때 소유권이 정리되는지 확인한답니다.

실제 SDK 함수 본문을 사용하지만 SDK 전체 클래스를 실행한 것은 아니랍니다. 게임의 reset·uninit, 타이머, 호스트, GUID 생성과 지도 컨테이너는 관측 가능한 대체물을 사용하며, 비활성 필드의 선언과 플레이어·팀 크기도 시험용이랍니다. 지도 reset의 자원 배열 할당·초기화와 생성자·소멸자의 소유권 처리는 추출 본문으로 실행하와요.

특히 실제 CvGame::reset은 호스트 캐시 경로의 Civ5SavedGameDatabase.db를 삭제·생성하는 경로를 포함하와요. 이번 시험은 이 파일 작업을 수행하지 않았사와요. 새 실행부에서는 프로젝트가 소유하는 별도 캐시 경로를 제공해야 하며 기존 게임 캐시나 저장 경로를 그대로 넘겨서는 안 된답니다.

지도 정리 경로를 소스에서도 대조했사와요. FFreeListTrashArray::Uninit은 내부 배열이 null이면 작업하지 않고 해제 뒤 null로 만들며, CvPlotManager::Uninit은 목록을 비우므로 생성 실패 정리 뒤 멤버 소멸에서 정리를 반복할 수 있는 형태랍니다. 이는 소스 검토이며 해당 실제 컨테이너의 실행 시험은 아니랍니다.

이 변경이 복원하는 것은 생성 중 직접 소유한 저장소와 지도 객체 개수랍니다. 호스트 콜백이 이미 수행한 외부 작업까지 되돌렸다고 보증하지 않으며, 실제 컨테이너·전체 게임 초기화·DB 변경·전체 생성자의 실패 안전성을 대신 검증하지 않사와요.

## 정식 통합과 다음 작업

attempt_025에서 C++ 161개를 재컴파일하고 제공자 16개와 연결하여 AMD64 DLL·미해결 0개를 확인했사와요. 총 556개 패치·수정 SDK 파일 94개·지원 헤더 5개이며, 기존 경고 343개 위치는 별도 항목이랍니다.

construction_evidence.py가 시험 본문을 정식 SDK 함수와 대조하고 기존 패치 보존 및 161개 오브젝트 컴파일 입력을 확인하와요. 정식 연결에도 이 증거를 등록하며, Source와 Build의 함수·기록을 Stage/Construction 및 Stage/GameCore_x64/Callers/Construction에 보관하와요.

전체 GC 초기화의 중복·재진입 방지와 단계별 실패 복구는 아직 남아 있사와요. 다음에는 호스트·DB 연결의 수명, CvPlayer 등 나머지 생성자의 부분 실패, DB 후처리·캐시의 실패 전달과 외부 작업 취소를 함께 연결해야 한답니다. 이번 구성요소 시험으로 이 전체 관문이나 게임 멀티코어 검증을 완료 처리하지 않사와요.

아래는 이 단계 당시의 소스 검토 기록이랍니다. 후속 연결 소유권·DB 후처리·캐시 실패 전달 단계에서 해당 경로들을 보완했으며, 플레이어·팀의 직접 자식과 액션 생성은 [후속 소유권 단계](M3_STARTUP_OWNERS.md)에서 보완했사와요. 전체 GC 상태 관리는 계속 남아 있답니다.

당시 다음 연결 작업의 소스 근거도 확인했사와요. CvDllGameContext::SetDLLIFace는 기존 인터페이스를 삭제한 뒤 새 인터페이스를 조회하므로 새 조회가 예외를 던지면 GC에 이전 포인터가 남을 수 있답니다. CvGlobals::init은 Defines 조회 준비와 DB 후처리·캐시 함수의 반환값을 검사하지 않으며, 후처리 함수 자체도 일부 실패를 반환하지 않사와요. 이 경로들은 원본·수정본 실행 재현을 아직 하지 않은 소스 검토 항목이며, 이번 생성자 정리로 해결됐다고 표시하지 않사와요.
