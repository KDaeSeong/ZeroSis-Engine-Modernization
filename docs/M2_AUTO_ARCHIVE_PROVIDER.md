# 실제 SDK 자동 상태 기록의 x64 제공자

2026-09-24 / 최초 제공자 단계의 계약과 실제 SDK 비교 기록이와요. **현재는 후속 [SDK 호출부 수정](M2_AUTO_ARCHIVE_CALLERS.md)까지 반영했으며**, 변수 배치 변경에 따라 GameCore attempt_014와 제공자를 재빌드하고 아래 비교를 다시 통과했사와요.

**자동 상태 기록 관련 미해결 심볼 24개를 해결하여 전체 미해결 수를 137→113개로 줄였사와요.** 161개 GameCore 오브젝트는 기존 attempt_013을 그대로 사용했으며, 새 제공자 C++ 3개와 시험 프로그램은 x64 `/MD /W4 /WX`에서 경고 없이 빌드되었답니다. 전체 GameCore DLL 생성·게임 실행·실게임 저장 및 동기화 검증은 아직 미완료랍니다.

## 요구사항과 변경 범위

| 항목 | 이번 계약 |
|---|---|
| 구현 | 실제 SDK의 `FAutoArchive`, `FAutoVariableBase`, 기본형·열거형 디버그 문자열 변환을 x64로 제공 |
| 정상 기록 | 전체 저장의 등록 순서, 차등 기록의 uint32 항목 수·등록 번호·변수별 값, 기존 endian 동작 보존 |
| 실제 호출 템플릿 | SDK의 스칼라·문자열·벡터·열거형·불리언 `FAutoVariable`을 시험에 사용 |
| 오류 처리 | 삭제한 변수의 변경 목록 제거, 중복 등록·잘못된 번호·잘린 입력 거부, 쓰기 실패 후 변경 목록 유지 |
| 의존성 | 현재 검증을 통과한 Streams·Serialization 제공자와 동일한 `/MD` 구성 |
| 빌드 범위 | `FINAL_RELEASE` ABI만 지원; 디버그 ABI와 실제 호출 스택 수집은 포함하지 않음 |
| 저장·모드 호환성 | 기존 Mod ID·버전·저장 키·스키마·밸런스 변경 없음; 전체 게임 저장 호환성은 별도 관문 |
| 배포 | 독립 Source → Build → Stage; 원본 SDK·게임 설치·MODS·사용자 저장에는 배포하지 않음 |

SDK 생성 패치 458개·수정 SDK 파일 57개·지원 헤더 3개는 이 단계에서 변경하지 않았사와요. 신규 파일은 `Source/Providers/AutoArchive`의 구현 3개·공통 포함 헤더, `Tests/sdk_auto_archive_trace.cpp`, 빌드·검증·증거 검사 도구 3개이와요. 연결 분석·Stage·프로젝트 정합성 도구와 현재 상태 문서에도 새 제공자를 반영했답니다.

## 실제 원본에서 확인한 동작

참조 실행 파일은 VC9 x86과 보존한 `FireWorksWin32.lib`, `CvGameCoreDLLUtilWin32.lib`를 연결했사와요. 링크 지도에서 원본 아카이브의 관련 함수 34개 항목을 확인하고, 직접 DLL 의존성을 확인한 뒤 독립 시험만 실행했답니다. 메모리 스트림도 원본 라이브러리의 코드이며, 참조용 FString 공유 저장소는 기존 독립 시험용 정의를 사용하와요.

| API·동작 | 원본 의미와 x64 처리 |
|---|---|
| `add`·생성자 | 등록한 순서가 변수 번호가 됨; 이름 등록 실패 시 새 등록을 제거하고 예외 전달 |
| `save`·`load` | 전체 변수 값을 등록 순서대로 처리; 별도의 변수 수 헤더 없음 |
| `touch` | 변경된 변수의 포인터를 집합에 보관하며 중복 표시를 합침 |
| `saveDelta` | 포인터 주소 순서로 순회하여 각 변수의 등록 번호와 값을 기록; 성공하면 변경 집합만 비움 |
| `clearDelta` | 변경된 변수의 `clearDelta`를 호출한 뒤 변경 집합을 비움 |
| `reset` | 모든 변수의 값을 초기화하며 이미 남아 있는 변경 집합은 그대로 둠 |
| `loadDelta` | 기록에 들어 있는 등록 번호로 변수를 골라 `loadDelta` 호출; 정상 중복 번호도 허용 |
| `findMismatchedVariables` | 입력 순서대로 비교하여 불일치 변수를 반환; 직접 값 대입은 하지 않음 |
| 호출 스택 | FINAL_RELEASE 원본은 제공된 문자열 목록을 바꾸지 않으며 `Stack Trace unavailable`을 반환 |

변수의 등록 순서와 주소 순서를 일부러 다르게 만든 배치로 번호와 순회 순서를 분리해서 확인했사와요. 주소 순서를 그대로 보존했다는 사실은 **서로 다른 실행·기계에서 차등 기록의 바이트 순서가 같다는 증거가 아니랍니다.** 수신자는 등록 번호를 사용하며, 실제 교차 읽기에서는 수신 변수의 물리 배치를 반대로 배치했사와요.

## 의도적으로 보완한 실패 동작

원본 `remove`는 등록 목록만 지우고 변경 집합에 포인터를 남기와요. 뒤이어 차등 저장을 하면 그 포인터가 항목 수에는 포함되지만 실제 값은 기록되지 않는 경로를 원본 실행·기계어에서 확인했답니다. 새 구현은 두 목록에서 모두 지우며 반복 제거에도 동일한 상태를 유지하와요. `touch`로 등록되지 않은 변수가 직접 들어온 경우에는 출력하기 전에 거부하와요.

입력의 변수 번호를 검사하고, 항목 수가 남은 최소 번호 바이트보다 크면 즉시 거부하와요. 중복 등록도 거부하되 입력 기록의 중복 번호는 정상 문법으로 유지했답니다. 저장 스트림이나 변수의 저장 콜백이 실패하면 변경 집합을 지우지 않으므로 새 출력 스트림으로 재시도할 수 있사와요.

부분적으로 쓴 출력은 호출자가 폐기해야 하며, 읽기 도중 뒤의 잘못된 항목을 발견하기 전에 앞 변수는 이미 바뀔 수 있사와요. 시험에서 이 부분 변경도 직접 확인했답니다. **전체 저장의 원자적 복구나 임의 콜백의 부작용 취소를 제공하는 계약은 아니랍니다.**

## 디버그 문자열의 호환 범위

원본은 `%uhh`, `%uh`, `%ud`, `%hh`, `%h` 같은 형식 문자열을 실제로 사용하와요. 그 결과 unsigned 형식에는 `hh`·`h`·`d`가 붙고 char·short는 빈 문자열이 된답니다. 모든 char·short 값과 unsigned 대응값, int 경계값을 합한 **131,596개 결과**가 원본과 같음을 확인했사와요. 빈 문자열은 미구현 대체물이 아니라 이 원본 동작의 보존이와요. 방향·활동의 개수 열거형 이름과 변수의 가상 문자열 호출도 비교했답니다.

실수 변환은 원본의 32바이트 스택 버퍼에 제한 없는 `%f` 출력을 하던 방식을 가변 길이 문자열·C 로캘·소수점 여섯 자리 출력으로 바꾸었사와요. 원본 버퍼를 넘을 수 있는 큰 실수는 원본에 실행하지 않았고, 새 구현의 최댓값·최솟값·비정규화 값 출력만 별도 기준으로 확인했답니다.

131,634개 진단 사례 중 **실수 표시 13개에 의도한 차이**가 있사와요. 정확한 절반 값의 반올림, 큰 float의 실제 유효 숫자, 무한대·NaN 표기가 해당하며 상세 값은 [실행 보고서](../evidence/auto_archive/conformance.json)에 남겼답니다. 이 문자열 변환의 차이를 기록 바이트 차이와 섞어서 설명하지 않사와요. 다만 원본 진단 문자열을 그대로 기대하는 외부 비교 도구는 조정이 필요하와요.

## 최초 제공자 단계에서 발견한 후속 항목

- **P1 SDK 변수 수명:** 벡터 특수화에는 제거하는 소멸자가 없으며, 파생 값 생성자가 기본 등록 후 실패하면 등록이 남을 수 있사와요. 이 제공자의 `remove` 수정만으로 해당 헤더 경로가 고쳐졌다고 계산하지 않사와요.
- **P1 SDK 이름 공유:** 클래스별 이름 표의 최초 등록은 공유 map을 바꾸므로 같은 타입의 동시 초기화가 안전하다는 보장이 없사와요. 현재 아카이브는 소유 스레드에서 비재진입 방식으로 사용해야 하며, 전역 호출 스택 설정을 원자화한 것이 아카이브 전체의 병렬화를 뜻하지 않사와요.
- **P1 SDK 벡터 변경:** 범위를 벗어난 인덱스와 변경 기록 할당 실패의 상태 보존은 별도 헤더 수정·검증이 필요하와요.
- **P1 전체 상태 복구:** 잘못된 뒤쪽 자료나 콜백 실패 시 앞쪽 변수까지 되돌리는 전체 저장·동기화 복구는 실행부 계약과 함께 해결해야 하와요.
- **결정성·호스트:** 해시 기반 컨테이너의 기존 순서 차이 6건, 실제 게임 객체의 생애·콜백·호스트 연결은 남은 관문이와요.

위 목록의 변수 수명·공유 이름·벡터 변경 실패는 현재 [후속 호출부 수정](M2_AUTO_ARCHIVE_CALLERS.md)에서 구현·검증했사와요. 전체 상태 복구, 같은 아카이브의 동시 접근, 나머지 113개 연결 요구사항과 실행부는 여전히 남아 있답니다. 새 게임·턴 진행·저장/불러오기·주요 UI·새 로그의 실게임 관문은 사용자가 별도로 실행을 허용한 뒤 진행하와요.
