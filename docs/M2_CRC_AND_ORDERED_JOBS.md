# CRC 기반 서비스와 순서를 보존하는 병렬 계산

## 변경 전 요구사항과 범위

이번 단계는 실제 SDK 연결 요구사항의 CRC 계산과, 불변 입력을 독립적으로 처리하는 x64 작업 실행기를 구현하는 범위이와요. GameCore의 상태 변경·공유 난수·Lua·UI·DB 접근은 작업자에 연결하지 않사와요.

- **C01:** SDK `FCRC::Calc`의 기본 다항식·초기 상태·분할 계산 결과를 보존해야 하와요. 공개 헤더는 `FirePlace/include/FireWorks/FCrc32.h`, `dword` 정의는 `FFireTypes.h:22`이랍니다.
- **C02:** 실제 SDK x86 코드와 새 x64 코드를 동일 입력으로 비교하고, 별도 CRC 기준으로 재확인해야 하와요.
- **C03:** 새 코드의 길이는 `size_t`, CRC 상태는 명시적 32비트로 구분하며, 빈 입력·잘못된 포인터·고정폭 인코딩의 동작을 명시해야 하와요.
- **J01:** 작업 입력은 값으로 소유하고 작업 ID를 유일하게 관리하며, 결과는 완료 순서와 무관하게 ID 순서로 반환해야 하와요.
- **J02:** 작업자 1·2·4 구성에서 같은 값 결과를 얻어야 하와요. 작업 실행 흔적과 결과 검증을 별도로 남겨야 하와요.
- **J03:** 작업 중 예외·취소·잘못된 입력에서는 부분 결과를 게임에 적용할 수 있는 성공 결과로 반환하지 않아야 하와요. 시작한 스레드는 모두 종료를 기다려야 하와요.
- **J04:** 결과를 받는 것과 게임 상태 반영은 구분해야 하와요. 실제 게임의 세대·리비전 검증, 한 번만 반영, 직렬 폴백, 저장·불러오기 연결은 이후 통합 관문이랍니다.

영향 범위는 이 독립 프로젝트의 `Source/Numerics`, `Source/Concurrency`, `Tests`, `tools`와 빌드·증거·문서이와요. 기존 게임 파일·모드 ID·버전·밸런스·저장 키·직렬화 형식은 변경하지 않사와요. 배포는 검증된 헤더와 기록을 프로젝트의 Stage에 보관하는 범위랍니다.

CRC는 충돌이 가능한 체크섬이므로 세션·객체·입력의 동일성 판단이나 권한 검사에 단독으로 사용하지 않사와요. SDK의 `FCRC::CalcFile`, 사용자 다항식, 파일 접근, 클래스 ABI 전체를 구현하는 범위도 아니랍니다.

## CRC 제공자의 구현과 참조

새 [CvCompatibleCrc32](../Source/Numerics/CvCompatibleCrc32.h)는 읽기 전용 상수 테이블을 사용하고, 기본 다항식 `0xEDB88320`·초기 상태 `0xFFFFFFFF`·최종 비트 반전 없음이라는 SDK의 동작을 유지하와요. `calculate(data, length, state)`에 앞 계산의 상태를 넘겨 이어 계산할 수 있답니다. `append_le32`는 정수 값을 명시적으로 4바이트로 인코딩하므로 구조체 패딩·포인터 폭에 의존하지 않사와요.

참조 프로그램은 [sdk_crc_reference.cpp](../Tests/sdk_crc_reference.cpp)에서 실제 SDK 헤더를 포함하고, 원본 `FireWorksWin32.lib`를 v90 컴파일러·링커로 연결한 x86 실행 파일이랍니다. SDK의 LTCG·PCH 형식 때문에 원본 개발 도구를 유지했사와요. 링크 지도에서 `FCRC::Calc`와 `g_CRC32`의 제공자가 `FireWorksWin32:FCrc32.obj`인 것을 검사했답니다. DLL 의존성은 MSVCR90과 KERNEL32이며 GameCore DLL을 로드하지 않았사와요.

입력은 길이 0~1,024와 네 가지 초기 상태, 모든 단일 바이트 값, 추가 1,024개 결정적 입력 및 알려진 문자열을 포함하와요. `123456789`의 SDK 원시 CRC는 `0x340BC6D9`로 확인했사와요. Python에서는 초기·최종 반전 차이를 명시한 `zlib.crc32(data, raw_seed ^ 0xffffffff) ^ 0xffffffff`를 독립 기준으로 사용했답니다. [Python 공식 CRC API](https://docs.python.org/3/library/zlib.html#zlib.crc32)

이식한 것은 기본 CRC 수치 기능의 의미이며, 기존 `FCRC` 이름·클래스 배치·전체 메서드를 그대로 연결한 x64 라이브러리는 아니와요. 4GB 이상 버퍼의 실제 처리도 이번 시험에는 포함되지 않사와요. 7개 기반 라이브러리의 완전한 x64 대체 완료 수는 여전히 0개랍니다.

## 작업 실행 API와 수명 계약

[OrderedBatch.h](../Source/Concurrency/OrderedBatch.h)의 `evaluate_ordered`는 입력 작업 목록을 값으로 받고 ID 순서로 정렬한 뒤, 각 작업자에 별도의 연산 객체 복사본을 제공하와요. 입력 형식 내부에도 게임 객체 포인터나 공유 가변 데이터를 넣지 않는 것이 호출자 계약이랍니다. C++의 `const`만으로 임의 콜백의 순수성을 보장하지는 않사와요.

- 허용 작업자 수는 1~64이며 실제 생성 수는 작업 개수 이하랍니다. 빈 배치는 작업자를 생성하지 않사와요.
- 각 결과 칸에는 하나의 작업자만 기록하며, 모든 작업자의 종료를 기다린 뒤 ID 순서로 결과를 모으와요.
- 작업자 예외는 배치 내부 취소 신호를 전달하고, 정상 결과 전체를 폐기한 `failed` 상태와 예외를 반환하와요. 이미 실행 중인 작업도 전달받은 취소 토큰으로 협조적으로 중단할 수 있답니다.
- 부모 세션의 취소는 배치로 전파되지만 배치 실패가 부모 세션을 취소하지는 않사와요. 다른 작업자 3개가 실패 신호를 받고 종료하는 사례와 부모 신호 보존을 검증했답니다.
- 외부 취소를 관측하면 `cancelled` 상태에 결과를 비워 반환하와요. 잘못된 입력이나 실행 준비 중 할당 실패는 작업 시작 전에 예외가 발생할 수 있답니다.
- 취소는 강제 스레드 종료가 아니므로 연산은 유한 시간에 끝나거나 취소 토큰을 확인해야 하와요. 결과 조립의 최종 취소 검사 이후 도착한 취소와 세션 변경은 향후 상태 소유자의 반영 관문에서 다시 검사해야 하와요.

이번 실행기는 배치마다 스레드를 만들고 반환 전에 기다리는 **동기식 기반 구성요소**랍니다. 지속적인 작업 풀·게임 스케줄러·게임 상태 반영 API는 아니와요. 완료 순서와 실행 통계는 게임 판단의 입력으로 사용하지 않사와요. 스레드 수명은 `join`으로 관리하와요. [Microsoft thread 문서](https://learn.microsoft.com/en-us/cpp/standard-library/thread-class)

시험에서는 첫 작업들의 완료 순서를 의도적으로 뒤집었으며, 결과 내용은 별도의 Python 계산과 대조하였사와요. `peak_inflight`는 대기 구간을 포함한 콜백 실행 구간의 중첩이랍니다. **물리 코어에서 명령이 동시에 실행됐다는 추적이나 게임 턴 성능 향상 증거로 사용하지 않사와요.**

## 남은 관문과 회귀 위험

1. 실제 GameCore에 연결할 제공자·타입 어댑터와 호출 지점을 확정해야 하와요. CRC가 사용하는 바이트 배열의 생성 순서와 문자열 인코딩도 보존해야 하와요.
2. 결과 반영 전에 세션·턴·단계·리비전·객체 세대가 현재 입력과 일치하는지 확인하고, 한 번만 반영하는 상태 소유자 계약이 필요하와요.
3. 실제 게임 계산을 선택하기 전 입력의 소유권·캐시 수정·Lua·DB·공유 난수 의존성을 검사해야 하와요. 현재 시험 작업은 독립 CRC 계산이랍니다.
4. 운영체제의 스레드 생성 실패를 강제로 일으키는 시험과 경쟁 상태 검사 도구는 수행하지 않았사와요. 해당 오류 처리 경로는 코드에 있지만 모든 환경의 동시성 결함이 없다는 증거는 아니와요.
5. 게임 통합 뒤 직렬 기준과 실제 턴·저장·모드·UI 결과를 비교하고, 스냅샷 복사·스레드 생성·취합 비용까지 포함해 성능을 측정해야 하와요.

검증된 두 헤더는 Source → Build → Stage로 추적하며, 원본 CRC 참조 실행 파일과 자체 시험 실행 파일은 Build에만 보관하와요. 기존 Civ V와 설치 MODS에는 배포하지 않았사와요.
