# M2: 임시 메모리의 x64 구현과 동시 반납 보완

이 문서는 제공자 연결 단계의 기록이랍니다. 여기서 남겼던 BNW 호출부·임시 배열 결함은 이후 [호출부 수정 기록](M2_TEMP_HEAP_CALLERS.md)에서 구현·독립 검증했사와요. 현재 이식은 458개 패치·57개 SDK 파일·정합성 94개 검사이며 연결 미해결 이름은 137개 그대로랍니다.

2026-09-24 기준으로 실제 SDK의 `TempHeap` 형식을 사용하는 x64 제공자를 구현했사와요.
기존 GameCore 오브젝트 161개와 다시 연결하여 미해결 심볼을 **140→137개**로 줄였답니다.
해소한 이름은 `GetTempHeap`, `TempHeap::Allocate`, `TempHeap::DeAllocate` 세 개이며 추가된 미해결 이름은 없사와요.
전체 GameCore DLL 생성과 64비트 실행부·게임 턴 병렬화는 아직 미완료랍니다.

## 요구사항과 영향 범위

| ID | 요구사항 | 이번 수용 근거 |
|---|---|---|
| TH01 / F02 | SDK의 정상 할당·반납·공간 재사용 규칙 보존 | 실제 x86 SDK·x64 제공자·별도 모델의 13,520개 동작 기록 일치 |
| TH02 / F05 | 여러 작업자의 대여가 겹쳐도 주소·데이터를 보존하고 마지막 반납 뒤 재사용 | 작업자 1·2·4·8개, 정상 할당 122,880건, 공간 부족 거부 15,360건 |
| TH03 / N01 | 크기·대여 수 넘침과 마지막 반납의 경쟁 상태 방어 | 크기 넘침 15건, 동시 대여 65,535개 경계, 작은 공간에서 400,000회 경쟁 |
| TH04 / F02 | 64비트 주소와 SDK의 unsigned 32비트 내부 위치 보존 | 높은 가상 주소에서 2GiB·4GiB 직전 위치, 실패 후 상태·전체 반환 확인 |
| TH05 / F01 | 실제 실행부의 임시 메모리 서비스 연결 및 잘못된 연결 거부 | 독립 실행 파일의 실제 export 호출, 작업자 8개의 첫 연결, export 누락·NULL 반환·복구 |
| TH06 / N03 | 소스·빌드·비교 시험·실제 연결·Stage 추적 | 제공자 증거 관문, 연결 이름 3개 대조, 프로젝트 정합성 87개 검사 |

변경은 독립 프로젝트의 `Source/Providers/TempHeap`, 전용 시험·빌드·검증 도구,
연결·Stage·전체 정합성 도구와 기록에 한정했사와요.
이번에는 SDK 이식 패치를 추가하지 않아 **기존 452개 패치·56개 변경 SDK 파일**을 유지했답니다.
기존 161개 AMD64 오브젝트는 해시를 확인하여 재사용했사와요.
원본 SDK·설치 게임·MODS·Mod ID·버전·저장 키·스키마·밸런스는 보존했답니다.
배포 범위는 이 프로젝트의 Source → Build → Stage 검토 묶음이랍니다.

## 원본 제공자 확인과 정상 동작

VC9 x86 참조는 원본 `FireWorksWin32.lib`의 `FTempHeap.obj`를 실제로 연결했사와요.
생성자·소멸자·시작·종료·할당·반납·범위 검사·호스트 연결의 여덟 이름을 링크 지도에서 확인했답니다.
동작을 대조한 같은 실행 파일의 해당 코드도 읽기 전용으로 판독하여 기록했사와요.
기존 GameCore DLL이나 Civ V는 로드하지 않았답니다.

SDK는 요청 크기를 16바이트 단위로 올려서 연속 공간을 배정하와요.
중간 블록을 반납해도 그 공간을 즉시 다시 빌려주지 않으며, 모든 대여가 끝나야 시작 위치로 돌아온답니다.
소유한 공간은 4KiB에 정렬하여 확보하고, 외부에서 빌려 온 공간은 종료 시 해제하지 않사와요.
`Startup`·`Shutdown`의 명시적 수명 계약과 아무 작업도 하지 않는 SDK 소멸자를 유지했답니다.
새 요청을 중단하고 모든 대여를 반납한 뒤 `Shutdown`을 호출하는 것은 소유자의 책임이와요.

크기 0도 대여 한 번으로 계산하며, 공간이 가득 찬 경우 끝 바로 뒤 주소가 나올 수 있사와요.
`OwnsAllocation`은 기존처럼 시작 이상·끝 미만의 주소 범위 검사이므로 이 끝 주소에는 false를 반환하와요.
반납 함수는 유효한 크기 0 대여의 끝 주소를 허용하도록 구현했답니다.
범위 안에 있다는 사실이 현재 살아 있는 대여의 증거는 아니므로, 중복 반납을 모두 검출하는 API로 해석하지 않사와요.

별도 Python 모델은 원본 함수나 새 구현을 호출하지 않고 할당 위치·대여 목록·남은 공간을 계산하와요.
0부터 선택한 경계값 65,536바이트까지 11개 용량과 소유·차용 방식 두 가지를 사용하여
22회 수명 동안 정상 할당 3,928건, 공간 부족 거부 5,620건, 반납 3,928건을 비교했사와요.
크기 0 대여 1,110건과 전체 반납 뒤 재사용을 포함한답니다.
세 기록은 각각 540,800바이트이며 내용 전체가 같았사와요.

## 동시 실행과 경계 보완

원본 코드에는 크기에 15를 더할 때의 unsigned 넘침 검사와 16비트 대여 수 한계 검사가 없사와요.
또한 반납 후 공유 writer 비트만 보고 재설정에 진입하는 경로와,
실패한 할당이 마지막 대여를 반납해도 사용 위치를 초기화하지 않는 경로가 있답니다.
이는 보관한 원본 코드 판독의 근거이며, 원본 게임에서 충돌을 재현했다는 뜻은 아니와요.

x64에서는 마지막 대여 수 1을 writer 상태로 **직접 비교·교환**하고,
그 전환에 성공한 작업자만 사용 위치를 0으로 만들고 다시 열도록 구현했사와요.
실패한 할당도 같은 반납 경로를 사용하므로 일시적으로 잡은 대여가 상태를 남기지 않사와요.
크기 반올림 넘침·65,536번째 동시 대여는 상태를 바꾸기 전에 NULL로 거부하와요.
사용 위치는 SDK의 32비트 비트를 유지하되, 부호 있는 덧셈 넘침이나 포인터 잘림 없이 계산하와요.
이 API의 개별 공간 용량이 64비트 정수로 늘어난 것은 아니랍니다.

동시 시험은 작업자 1·2·4·8개 각각 128묶음으로 진행했사와요.
모든 작업자가 블록을 보유한 상태에서 주소 범위가 겹치지 않고 기록한 내용이 보존되는지 검사한 뒤,
서로 다른 순서로 반납하고 매 묶음이 끝날 때 전체 공간을 다시 사용할 수 있는지 확인했답니다.
별도 32바이트 공간에는 작업자 8개가 총 400,000회 할당을 시도하여 성공과 부족 경로를 함께 실행했사와요.
성공·거부 건수는 스케줄에 따라 달라지며, 합계·주소 소유·내용·최종 초기화를 검증하와요.
이 결과는 임시 메모리 부품의 시험이며 전체 GameCore의 스레드 안전성이나 속도 향상은 아니와요.

높은 주소 시험은 **4GiB 가상 주소 범위를 예약하고 두 페이지, 총 8KiB만 커밋**했사와요.
2,147,483,648 및 4,294,967,280 위치를 다루고 실제 쓰기는 커밋한 두 페이지에만 수행했답니다.
4GiB의 물리 메모리를 채우거나 실제 메모리 고갈을 재현한 시험은 아니와요.
별도로 잘못된 재시작·차용 정렬·검출 가능한 잘못된 반납 여섯 건을 거부한 뒤 상태 복구를 확인했답니다.

## 실행부 연결과 오류 처리

`GetTempHeap`은 원본처럼 실행 파일의 같은 이름 export에서 실제 서비스 주소를 얻도록 구현했사와요.
자동으로 빈 공간을 대신 만들거나, 미래 실행부의 기본 용량을 임의로 정하지 않았답니다.
시험 실행 파일이 실제 TempHeap 객체를 소유하고 명시적으로 시작·종료하며,
할당 코드는 원본 SDK 또는 새 제공자에서 가져오와요.

x64 첫 연결은 한 번만 초기화하여 작업자 8개에 공개하고 총 8,192회 주소를 대조했사와요.
export가 없는 별도 실행 파일에서는 두 차례 모두 명확한 예외로 거부했답니다.
export의 NULL 반환도 두 차례 거부하고, 정상 반환으로 복구한 뒤 실제 할당·반납을 확인했사와요.
미래 실행부는 같은 ABI와 안정적인 객체 수명·용량·할당 영역을 제공해야 한답니다.
기존 게임 실행부의 작은 객체 할당기와 메모리 영역을 공유한 검증은 아직 없사와요.

## 남아 있는 호출부 결함과 후속 수용 조건

| 항목 | 현재 근거와 영향 | 다음 수정·회귀 관문 |
|---|---|---|
| TH-C01 / P1 후보 | `CvGame.cpp:9433`, `9609`에서 Allocate 뒤 NULL 확인 없이 ZeroMemory·파일 처리를 수행하는 정적 경로 | 부족할 때 안전한 대체 할당 또는 명시적 실패, 파일·버퍼 정리, 읽기/쓰기 실패와 저장 결과 비교 |
| TH-C02 / P1 후보 | `FTempArray`와 `FTempHeapFastVectorAllocator`가 범위 검사만으로 해제 경로를 선택하므로 가득 찬 공간의 크기 0 대여를 일반 해제에 넘길 수 있는 API 경로 | 크기 0 처리와 실제 할당 원천 보존; 해당 호출부 도달 여부 및 정상·부족·예외 회귀 |
| TH-C03 / P1 후보 | `FTempArray`의 원소 수×크기 결과를 uint 크기의 Allocate 인수로 전달하는 경로 | 곱셈·축소 변환 검사, 넓은 크기의 대체 할당, 정렬·실패·수명 검증 |

이 표는 확인한 소스 경로와 예상 영향을 기록하며 실게임에서 발생했다는 보고가 아니와요.
이번 제공자 구현만으로 이 호출부들이 수정되었다고 계산하지 않사와요.
원본 중첩 `HeapLock` 도우미 생성자 전체, 다른 대여가 살아 있는 동안의 임의 중복 반납,
새 요청이 계속 유입되는 중의 종료, 실제 메모리 고갈도 이번 수용 범위 밖이랍니다.

## 연결·기록·남은 엔진 관문

독립 실행 10회가 통과했고, x64 제공자와 시험은 `/MD`, C++14, `/W4 /WX`에서 경고 없이 빌드했사와요.
VC9 원본 참조에는 기존 SDK 헤더의 C4819 인코딩 경고만 허용·기록했답니다.
직접 DLL 의존성을 먼저 검사한 뒤 실행하여 GameCore·Steam·Lua DLL을 직접 가져오지 않는 것도 확인했사와요.
전체 GameCore에는 인코딩 325곳·구식 선언 5곳·구식 API 13곳, 합계 **343개 경고 위치**가 남아 있답니다.
이 수와 실제 링크 미해결 137개는 서로 다른 항목이와요.

남은 연결 이름은 DB 41개, 지도 편집·모드 필드 32개, 자동 상태 저장 24개,
현지화 16개, FString·인코딩 12개, Lua 래퍼 8개, 파일·로그·진단 4개랍니다.
이 개수는 남은 개발량이나 전체 완료율이 아니와요.
앞 단계의 순서 없는 목록 저장 순서 차이 6건도 아직 해결되지 않았답니다.
호스트·렌더러·게임 저장/불러오기·게임 턴 병렬 실행·성능 수용은 별도 관문으로 남겼사와요.
