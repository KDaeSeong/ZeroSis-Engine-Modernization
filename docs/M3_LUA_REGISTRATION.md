# 게임 Lua 라이브러리의 등록 실패 전달

현재 수명 관리 통합에서는 공통 차용 참조 템플릿 전체를 등록 시험에 사용하와요. 원본의 Lua 실패 위치는 기존 3,166곳, 수정본은 플레이어 2,032곳·팀 736곳을 포함한 3,474곳이며, 두 최적화 구성의 20개 실행에서 합계 243,512개 검사를 통과했사와요. 새 비공개 참조 표의 할당 경계가 추가된 결과이며, 메서드 1,228개·성공 메타데이터·일곱 실패 경계는 유지했답니다. 아래 223,184개 수치는 등록 단계 완료 당시의 이력이와요. [차용 참조 통합과 실행 범위](M3_LUA_BORROWED_OBJECTS.md)

등록 단계 완료 당시의 상태: 독립 검사 223,184개와 attempt_034의 GameCore 161개 파일 컴파일·미해결 0개 연결을 통과했사와요. 기존 603개 패치를 유지한 합계 613개·SDK 수정 파일 102개·지원 헤더 8개·제공자 16개였답니다. 현재 추가된 프랙탈 수명·선택 인수 변경은 [후속 단계](M3_LUA_FRACTAL.md)에서 추적하며, 실제 GameCore는 불러오지 않았사와요.

## 요구사항과 변경 범위

| 요구사항 | 수용 기준 |
|---|---|
| LR01 | 프랙탈·게임 정보·지도·게임·플레이어·팀의 보호 호출 실패를 등록 성공으로 보고하지 않음 |
| LR02 | 게임 정보의 액션 등록 실패 뒤 타입 등록을 중단하고, 전체 등록 순서에서 후속 라이브러리를 실행하지 않음 |
| LR03 | 정상 메서드 이름·액션 필드·타입 값·플레이어/팀 인덱스·기존 테이블/객체 참조를 보존 |
| LR04 | 실제 Lua·FLua로 할당 실패를 주입하고 스택·잠금·메모리 정리 및 새 VM 재생성을 검증 |
| LR05 | 원본과 수정본의 정확한 SDK 함수 본문 및 빌드 입력을 기록하고 Source → Build → Stage로 연결 |

변경 대상은 `CvLuaFractal.cpp`, `CvLuaGameInfo.cpp`, `CvLuaPlayer.cpp`, `CvLuaTeam.cpp`와 지도·게임이 공유하는 `CvLuaStaticInstance.h`이와요. 보호 호출이 실패하면 예외를 전달하여 상위 실행부가 미완성 VM을 폐기하도록 하와요. 부분 등록된 테이블을 복구한 것으로 취급하지 않사와요.

등록 성공 경로·메서드 목록·SDK 객체 배치·기존 Mod ID·저장 키·스키마·규칙·밸런스는 유지하와요. 별도 이식 프로젝트만 수정하며 설치 SDK·게임·MODS·저장 파일은 변경하지 않사와요.

## 시험 경계

시험에는 실제 SDK의 등록 함수·등록 메서드 목록·공유 템플릿의 등록/객체 푸시 본문과 `LuaSupport::RegisterScriptData` 순서를 사용하와요. Lua와 FLua는 실제 x64 제공자랍니다. 플레이어·팀·액션의 데이터 소유자와 게임 메서드의 실행 본문, 전체 순서 시험의 열거형 등록은 계측용 대체물이랍니다. 게임 메서드 실행이나 실제 GameCore 등록을 검증한 것으로 표시하지 않사와요.

Lua 오류 뒤 남을 수 있는 부분 테이블은 해당 VM과 함께 폐기해야 하와요. 이 단계는 실패 전달을 보완하며, 프랙탈 userdata의 형식·중복 소멸 방어와 게임 객체의 세대·수명 검증은 별도 작업으로 남아 있답니다. 실제 GameCore 로딩·지도 생성·턴·저장·멀티코어 성능 검증도 별도 관문이랍니다.

## 재현한 결함과 정상 결과

기존 보호 호출은 오류를 처리한 뒤 `false`를 반환하지만 여섯 등록 진입점은 그 값을 확인하지 않았사와요. `CvLuaGameInfo::Register`는 액션 등록 실패 뒤에도 타입 등록을 이어 갔으며, `LuaSupport::RegisterScriptData` 역시 뒤의 라이브러리를 계속 등록했답니다. 원본·수정본의 실제 등록 본문을 실행한 일곱 실패 경계에서 원본의 계속 진행과 수정본의 중단을 확인했사와요. 게임 정보의 두 내부 단계와 나머지 다섯 라이브러리가 대상이랍니다.

지도·게임의 수정은 공통 `CvLuaStaticInstance::Register` 한 곳에서 이루어지와요. 정상 등록 함수와 메서드 목록·테이블 쓰기는 바꾸지 않사와요. 오류의 메모리 할당 자체가 실패하는 경우에도 예외를 상위로 전달하와요. 실패가 난 VM의 부분 테이블을 다시 정상 상태로 인정하지 않는 실행부 계약이 필요하답니다.

| 독립 실행 검사 | 결과와 범위 |
|---|---|
| 실제 SDK 함수 본문 | 22개: 여섯 등록 경로·공유 템플릿·메서드 목록·전체 등록 순서 |
| 등록된 메서드 | 프랙탈 2·지도 36·게임 262·플레이어 787·팀 141, 합계 1,228개 이름/연결 비교 |
| 게임 정보 | 계측 액션 3행 × 28필드와 타입 4개; 숫자·불리언·빈 문자열·한국어 값 비교 |
| 객체 참조 | 플레이어·팀 각 64개, 차용 포인터·약한 캐시·메타테이블·반복 등록 시 참조 동일성 |
| Lua 할당 실패 | 구성별 프랙탈 8·게임 정보 75·지도 83·게임 540·플레이어 1,878·팀 582, 합계 3,166곳 |
| 부분 테이블 | 위 실패 중 3,147곳에서 이미 전역 테이블이 존재; 실패 VM 폐기 뒤 Lua 블록·C++ 힙 개수 복원 |
| C++ 할당 | 정상 등록에서 `operator new` 할당은 관측되지 않음; 별도 오류 메시지 생성의 할당 실패와 잠금/스택/힙 복원 확인 |
| 빌드 구성 | MSVC x64 `/EHsc /O2` 및 `/EHsc /Od`, 원본·수정본 각각 시험 |
| 실행 합계 | 네 실행 파일·20개 프로세스, 223,184개 단언 통과 |

이 결과는 게임 메서드 1,228개의 동작을 시험했다는 뜻이 아니랍니다. 그 함수들은 호출되지 않는 계측용 본문이며 실제 등록 목록과 Lua 연결을 검증했사와요. 계측 소유자의 접근 실패도 실제 게임 객체의 모든 실패를 대표하지 않사와요. 전체 순서 시험의 열거형은 순서 확인용 대체물이므로 실제 열거형 증거는 [별도 열거형 시험](M3_LUA_ENUMS.md)으로 추적하와요.

## 재현과 산출물

이 등록 단계의 기준은 `attempt_033`의 603개 패치이며 기존 항목을 그대로 보존하고 다섯 파일에 열 개를 추가했사와요. `define_lua_registration_patches.py`의 인수 없는 실행은 제안 기록만 만들고, `--apply`가 정식 패치 목록에 반영하와요. 후속 프랙탈 패치는 유지하며, 현재 전체 빌드·검토 갱신에는 [최신 재현 절차](REPRODUCING.md)를 사용하와요. 아래 명령은 등록 단계 당시의 순서랍니다.

```text
python tools/define_lua_registration_patches.py --apply
python tools/build_sdk_x64.py --vs "C:\Program Files\Microsoft Visual Studio\2022\Community" --phase all
python tools/refresh_lua_registration_integration.py --phase build
python tools/refresh_lua_registration_integration.py --phase stage
```

앞 명령이 종료하고 성공한 뒤 다음 명령을 실행하와요. 중단된 갱신은 해당 프로세스가 실제 종료한 것을 확인한 뒤 기록된 성공 단계부터 `--from-step`으로 재개하와요. 이 절차는 정식 DLL을 빌드·연결하고 독립 구성요소를 실행하지만 실제 GameCore DLL은 불러오지 않사와요. 실행 근거는 `evidence/lua_registration`, 검토용 사본은 `Stage/LuaRegistration`과 `Stage/GameCore_x64/Callers/LuaRegistration`으로 추적하와요.
