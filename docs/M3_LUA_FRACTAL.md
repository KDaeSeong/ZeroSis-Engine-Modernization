# 프랙탈 Lua 객체의 생성·형식·소멸

아래의 attempt_035 수치는 소유권·기본값 단계 완료 당시 기록이랍니다. 후속 [수치 경계 단계](M3_FRACTAL_NUMERICS.md)에서 실제 계산 함수의 입력·반복·산술과 Lua 예외 전달을 보강했으며, 현재 전체 재현은 [최신 절차](REPRODUCING.md)를 사용하와요. 현재 소유권 회귀 시험의 실제 계산 부분은 후속 수치 가드가 적용된 코드를 사용하며, 35차의 계산 본문을 변경하지 않았다는 표현을 후속 버전에 확대하지 않사와요.

정식 생성 SDK와 같은 Lua 바인딩 본문 10개를 실제 Lua·FLua로 실행하여 **48,986개 검사·22개 프로세스**를 통과했사와요. 수명 시험은 `/O2`와 `/Od` 양쪽에서 수행했고, 실제 프랙탈 계산 비교는 `/O2`에서 수행했답니다. 네이티브 수명 계측과 계산 어댑터의 범위는 아래에 구분하며, 전체 GameCore 로딩·지도 생성·게임 실행은 미검증이와요.

`attempt_035`의 GameCore 161개 컴파일과 제공자 16개 연결을 통과했으며 미해결 심볼은 0개랍니다. 합계 620개 패치·SDK 수정 파일 102개·지원 헤더 9개이며 DLL SHA-256은 `fd45dab43d363ba7f930287ea30f3a3f6728f028a1db1fb67cd0e2688e1504c4`이랍니다. 기존 전체 컴파일 경고는 343개 위치로 같으며, 프랙탈 시험 실행 파일 여섯 개는 경고를 오류로 취급하는 빌드를 통과했사와요.

## 요구사항과 변경 범위

| 요구사항 | 수용 기준 |
|---|---|
| LF01 | 프랙탈이 아닌 userdata·lightuserdata를 네이티브 프랙탈로 사용하거나 소멸하지 않음 |
| LF02 | 수동 소멸·자동 GC·VM 종료가 겹쳐도 네이티브 소멸은 한 번만 수행하고 소멸 뒤 메서드 사용은 거부 |
| LF03 | Lua 메타데이터 준비 중 실패하면 네이티브 객체가 아직 생성되지 않으며, 생성된 객체는 최종 정리 가능 |
| LF04 | 정상 Lua API와 프랙탈 계산·난수 소비는 기존 기준과 비교하여 보존 |
| LF05 | SDK 객체 배치·저장 형식·모드 식별자·밸런스를 유지하고 Source → Build → Stage로 추적 |

대상은 별도 x64 이식본의 `CvLuaFractal.cpp`와 내부 소유권 도우미이와요. 원본 SDK·게임·MODS·저장 파일은 변경하지 않사와요. `CvFractal` 자체의 배치와 계산 함수는 유지하며 Lua 내부 userdata에는 생성 여부를 보관할 공간을 추가하와요. 이 userdata는 저장 파일의 필드나 외부 엔진 ABI가 아니랍니다. VM을 살아 있는 상태에서 새 DLL로 교체하는 기능은 제공하지 않사와요.

private registry의 약한 키 표에 해당 VM이 만든 userdata를 등록하여 형식을 검사하와요. 소멸할 때 상태를 먼저 바꾸며, 소멸 뒤 조회와 다른 종류의 객체는 Lua 오류로 거부하와요. 메타테이블·클로저·등록 표의 Lua 할당을 끝낸 다음 네이티브 객체를 생성하와요. 정렬 조건과 예외 없는 네이티브 소멸을 컴파일 시 검사하며, Lua 5.1의 수거·VM 종료에서 약한 키의 유지와 회수를 별도 시험하와요. 메타테이블의 변경 가능성은 기존과 같으며, debug 기능을 이용한 의도적인 registry 변조까지 방어한다고 주장하지 않사와요.

`CreateRifts`는 프랙탈 객체 또는 nil/생략을 허용하와요. 기존에는 다른 자료형을 조용히 null로 해석하거나 임의의 native pointer를 사용했으며, 그 잘못된 인수는 명시적 오류로 바뀌와요. 기존 지도 자료의 정상 호출과 비교해야 하와요.

## 재현한 결함과 수정

기존 `lCreate`와 `lCreateRifts`는 결과 userdata를 스택에 넣은 다음 선택 인수를 읽었사와요. 인수 네 개만 전달한 `Create`는 새 userdata를 지수 인수로 읽어 0/0을 사용했고, `CreateRifts`는 방금 만든 결과를 입력 rifts로 오인했답니다. 수정본은 선택 인수와 입력 rifts를 먼저 읽고, 지수 기본값 7/6과 rifts 없음의 의미를 보존한 뒤 결과를 생성하와요. 기존의 잘못된 생략 호출과 결과를 같게 만드는 것이 수용 기준은 아니며, 기존 구현에 명시적으로 기본값을 준 결과와 대조하와요.

| 관측 | 원본 | 수정본 |
|---|---|---|
| 수동 소멸 두 번 뒤 VM 종료 | 계측 소멸자 호출 3회 | 소멸자 호출 1회; 소멸 뒤 메서드 거부 |
| 외부 userdata·복사한 메타테이블·lightuserdata | 종류별 네이티브 전달 3/3/1회 | 모두 네이티브 전달 전에 거부 |
| Lua 할당 실패 | 실패 위치 14개 중 계측 네이티브 정리 누락 11개 | 실패 위치 19개, 네이티브 정리 누락 0개 |
| 반복 수거·VM 종료 | 원본 비교 기록 | 객체 128개, 수거 중 추가 할당 금지 상태에서 회수·중복 정리 없음 |
| 선택 인수 생략 | 출력 객체를 입력으로 오인 | 기본 지수 7/6과 rifts 없음 |

수명 시험은 실제 Lua·FLua와 SDK 바인딩 본문을 사용하고 네이티브 객체의 생성·소멸은 계측하와요. 원본의 중복 소멸 관측은 해당 MSVC 시험 프로세스의 결과이며, 잘못된 C++ 객체 수명의 동작을 다른 플랫폼까지 일반화하지 않사와요. 네이티브 생성 예외 뒤 정리와 다음 생성 성공도 검사하와요.

계산 시험은 변경하지 않은 실제 `CvFractal` 클래스와 계산 함수 본문을 별도 실행하와요. 원본 난수의 수치 연산을 재현한 어댑터와 컨테이너·소유자 어댑터를 사용하므로 전체 `CvRandom` 서비스나 전체 GameCore를 실행한 결과는 아니랍니다. 시드 세 개에서 같은 정상 입력 12개와 생략 인수 대 명시적 기본값 비교 6개, 합계 18개 시나리오를 대조하와요. 시나리오마다 높이·백분위 표본 1,290개와 난수 시드·호출 수·범위/반환값 기록이 일치해야 하와요.

## 재현과 산출물

기준은 `attempt_034`의 613개 패치이며, 기존 항목을 그대로 보존하고 프랙탈 호출부 한 파일에 7개 패치를 더해 합계 620개가 되와요. 내부 소유권 지원 헤더는 `Source/Porting/ZeroSisLuaFractal.h`이랍니다. 생성된 SDK 파일에 직접 수정하지 않고 아래 순서로 재현하와요.

```text
python tools/define_lua_fractal_patches.py --apply
python tools/build_sdk_x64.py --vs "C:\Program Files\Microsoft Visual Studio\2022\Community"
python tools/refresh_lua_fractal_integration.py --phase build
python tools/refresh_lua_fractal_integration.py --phase stage
```

앞 명령의 실제 종료와 성공을 확인한 뒤 다음 명령을 실행하와요. 갱신 도중 관측이 끊겨도 같은 프로세스의 상태를 먼저 확인하며, 실제 종료한 실패 작업만 원인을 수정하고 기록된 단계부터 `--from-step`으로 재개하와요. 빌드 단계는 생성 SDK와 같은 프랙탈 본문을 `--production`으로 검사하며, 검토 단계는 실행부를 재빌드하고 GameCore를 로드하지 않는 독립 시험을 수행하와요.

실행 기록은 `evidence/lua_fractal`, 검토용 사본은 `Stage/LuaFractal`과 `Stage/GameCore_x64/Callers/LuaFractal`으로 추적하와요. 전체 검증은 `evidence/project_verification.json`에서 기록과 산출물의 일치 여부를 확인하며, 별도의 실게임 수용 관문을 대신하지 않사와요.

## 검증 경계와 남은 범위

실제 SDK Lua 함수 본문과 실제 Lua·FLua를 사용하되, 소멸 횟수와 생성 실패는 계측용 프랙탈로 분리하여 관측하와요. 실제 `CvFractal`의 현재 소멸자는 빈 `uninit`을 호출하므로, 계측 시험의 누락 소멸을 실제 동적 자원 누수로 확대해서 표현하지 않사와요. 실제 계산 비교는 별도 원본 계산 본문과 명시된 난수·컨테이너 어댑터의 범위를 기록하와요.

프랙탈 크기·지수·시드 수 등의 수치 검증, 플레이어·도시·유닛 참조의 세대 검사, 전체 GameCore 구동과 지도 생성·턴·멀티코어 성능은 이 소유권 수정만으로 완료되지 않사와요.
