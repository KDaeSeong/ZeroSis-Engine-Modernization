# M2: CRC·잠금·시간·정렬 메모리의 실제 x64 연결

이 문서는 기반 제공자 연결 당시의 150→140개 기록이랍니다. 이후 [임시 메모리 제공자](M2_TEMP_HEAP_PROVIDER.md)와 [호출부 수정](M2_TEMP_HEAP_CALLERS.md)을 진행했으며 현재 미해결 137개·정합성 94개 검사이와요.

2026-09-24 기준으로 SDK 클래스와 함수 이름을 유지한 기반 제공자를 연결하여
미해결 심볼을 **150→140개**로 줄였사와요. 새로운 미해결 심볼은 없답니다.
이번 해소는 CRC 2개, 임계 영역 4개, 시간 측정 2개, 정렬 메모리 2개이와요.
전체 GameCore DLL 연결과 64비트 실행부·렌더러·게임 멀티코어 실행은 아직 미완료랍니다.

## 원본 제공자와 빌드 근거

x86 참조는 원본 `FireWorksWin32.lib`의 `FCrc32.obj`, `FCriticalSection.obj`,
`FTimer.obj`, `FMemHooks.obj`를 VC9 /MD로 연결했사와요.
링크 지도에서 생성자·소멸자·연산 함수·정적 데이터 등 **18개 이름**의 실제 제공자를 확인했답니다.
공유 문자열의 초기화 연결에는 기존 시험용 빈 FString 저장소만 사용했사와요.

x64 구현과 시험은 VS2022 /MD, SDK와 맞는 C++14 설정으로 빌드했고 경고가 없었사와요.
VC9 참조에는 기존 SDK `FDataStream.h`의 문자 인코딩 경고 C4819가 남아 기록했답니다.
참조에서 이 경고만 허용하며 다른 경고·오류가 있으면 검증을 중단하와요.
SDK 원본의 구조를 바꾸거나 경고를 새 x64 구현의 성공으로 숨기지 않았사와요.

실행 전에 시험 파일의 직접 DLL 의존성을 판독했사와요.
참조는 KERNEL32·VC90 런타임, x64는 KERNEL32·VC140/UCRT 런타임을 가져오며,
Civ V·GameCore·Steam·Lua DLL은 직접 연결하지 않았답니다.
이번에는 새 독립 시험 실행 파일만 실행했사와요.

## 보존한 계약과 보완한 동작

### CRC

`FCRC`의 256개 표·다항식·magic 값은 기존처럼 총 **1,032바이트**이며,
9개 다항식에서 원본 객체 전체의 바이트와 같았사와요.
기본 CRC는 최종 비트 반전을 하지 않는 SDK의 원시 상태 규칙을 유지했답니다.
`Calc`, `CalcBits`, 분할 입력, 전역 `g_CRC32`를 직접 호출해 비교했사와요.
기본 다항식은 Python zlib, 나머지는 별도의 비트 단위 계산을 기준으로 사용했답니다.
기본 입력 5,381개와 추가 다항식 입력 3,600개를 포함하와요.

길이 0은 입력 포인터가 NULL이어도 기존 상태를 그대로 반환하와요.
음수 길이 또는 길이가 양수인 NULL 포인터는 x64에서 예외로 거부한답니다.
원본의 음수 길이 경로는 길이를 0까지 감소시키며 잘못된 메모리를 읽을 수 있어 실행하지 않았사와요.
이 거부를 원본의 잘못된 입력 동작과 동일하다고 주장하지는 않사와요.
파일 CRC 함수인 `CalcFile`은 현재 GameCore의 미해결 요구에 없으며 아직 구현·검증 대상 밖이랍니다.

### 잠금

`FCriticalSection`은 원본과 같은 Windows 재귀 임계 영역을 소유하와요.
Try는 소유한 스레드에서 재진입할 수 있고, 다른 스레드가 소유하면 실패한답니다.
두 번 잠근 소유자가 한 번만 해제했을 때 다른 작업자가 진입하지 못하는지,
마지막 해제 뒤 실제 진입하는지 이벤트로 확인했사와요.
공유 값 갱신 시험에서는 잠금 안에 두 작업자가 동시에 들어오면 실패하도록 검사했답니다.
SDK의 `FScopedCriticalSection`이 예외로 범위를 벗어날 때도 잠금을 해제하는지 확인했사와요.

`GetLockCount`와 `GetRecursionCount`는 기존 Windows 필드 값을 반환하와요.
LockCount를 이식 가능한 소유자 수로 재해석하지 않았답니다.
살아 있는 잠금을 복사하거나 소유자가 있는 상태에서 파괴하는 사용법은 지원·검증하지 않았사와요.
이 시험은 GameCore의 도시·유닛·Lua 호출 전체가 스레드 안전하다는 증거가 아니와요.

### 시간 측정

offset 0은 첫 호출의 기준 카운터를, 다른 offset은 전달받은 기준을 사용하와요.
카운터 차이에 주파수의 역수를 곱해 초를 반환하며, 극단적인 offset에서도 SDK의
64비트 감산 비트값을 명시적으로 보존하여 C++의 부호 있는 정수 넘침을 피했사와요.

원본의 첫 호출은 공유 필드에 보호 없이 쓰므로 참조 시험은 먼저 직렬로 초기화했사와요.
x64 구현은 함수 내부의 초기화 장벽을 사용해 한 번만 준비하고, 이후 작업자에게 공개하와요.
작업자 8개가 첫 호출을 시작하는 경우와 각 작업자의 단조 증가 읽기를 확인했답니다.
공개 주파수·기준 필드를 외부에서 동시에 다시 쓰는 사용법까지 보장하지는 않사와요.

시간 비교는 호출 전후 실제 QPC 값의 범위 안에 결과가 들어오는지 검사하와요.
부동소수점 허용치는 4 ULP + 10^-12초이며, 두 프로세스의 서로 다른 실제 시각을
같은 비트값으로 비교한 시험은 아니랍니다.
Start, 양의 시작 offset, Stop의 기록값, Stop 뒤에도 진행하는 Peek를 확인했사와요.
카운터 API 실패 시에는 잘못된 단위의 값 대신 예외를 내도록 구현했지만,
실제 QPC 실패·메모리 고갈·모든 부동소수점 반올림 모드의 강제 시험은 아직 없답니다.

### 정렬 메모리

원본 VC9 경로는 **정렬 0을 기본 정렬로 처리하고, 크기 0에도 해제 가능한 블록을 반환**했사와요.
처음 만든 거부 정책을 수정하여 x64에서도 이 동작을 유지했답니다.
요청한 크기·정렬을 새 CRT에 맞게 정규화하되, 일반 호출은 같은 /MD CRT 할당·해제 쌍을 사용하와요.
CRT에서 직접 할당한 블록을 제공자로 해제하고, 제공자 블록을 CRT로 해제하는 방향도 확인했사와요.

21개 크기와 18개 정렬 조합 378개에서 주소 정렬·쓰기·읽기·해제를 확인했사와요.
크기는 0부터 선택한 경계값 65,537바이트까지, 정렬은 0부터 선택한 거듭제곱 65,536까지랍니다.
x64 주소 378개 모두 4GB 가상 주소 경계보다 높았으며, 4GB 물리 메모리를 할당한 시험은 아니와요.
작업자 4개가 추가로 4,096개 블록을 할당·검사·해제했사와요.

잘못된 정렬은 원본과 같은 NULL/EINVAL을 반환하되, x64에서는 프로세스 전체의
CRT 오류 콜백을 부르지 않고 함수 경계에서 거부하와요.
참조의 콜백 3회와 x64의 0회를 의도한 차이로 기록했답니다.
네이티브 크기 넘침은 NULL/ENOMEM으로 거부하며, 실제 메모리 고갈을 재현한 결과는 아니와요.

이 제공자는 새 CRT의 메모리 영역을 사용하며 기존 실행부의 작은 객체 할당기와 연결하지 않았사와요.
`TempHeap`의 소유권·수명 계약과 향후 실행부의 메모리 영역 공유는 다음 구현 대상이랍니다.

전체 GameCore의 기존 경고는 고유 위치 기준 **343곳** 그대로이며 이번 연결 해소와 별개랍니다.
앞 단계에서 발견한 해시 기반 목록의 저장 순서 차이 6건도 미해결로 유지하와요.
남은 연결 이름은 DB 41개, 지도 편집·모드 필드 32개, 자동 상태 저장 24개,
현지화 16개, FString·인코딩 12개, Lua 래퍼 8개, TempHeap 3개, 파일·로그·진단 4개랍니다.
이 개수는 이름 분류이며 전체 실행부 서비스나 개발 난도의 비율은 아니와요.

다음은 임시 메모리와 자동 상태 저장의 실제 계약을 구현하고, DB·현지화·지도·실행부 연결을 이어갈 차례랍니다.
기반 라이브러리의 독립 실행을 전체 엔진 전환·게임 턴 병렬화·성능 개선의 완료로 계산하지 않사와요.
