## 인터페이스 조사 범위

`CvDllInterfaces.h`, `CvDllInterfaces2.h`, `ICvDLLUtility.h`, `ICvDLLScriptSystem.h`, `ICvDLLUserInterface.h`, `ICvDLLDatabaseUtility.h`를 조사했사와요. 주석과 문자열을 제외한 뒤 클래스 상속과 순수 가상 함수 선언을 모으고, BNW의 `gDLL`, `DLLUI`, 직접 UI 접근 및 명시적 인터페이스 포인터 변수의 호출 후보와 연결했답니다.

| 선언 분류 | 수량 |
|---|---:|
| 공통 수명 인터페이스 | 2 |
| 실행부 유틸리티 | 258 |
| 실행부 스크립트 | 24 |
| UI, 기존 인터페이스 포함 | 298 |
| GameCore가 외부에 노출하는 인터페이스 | 997 |

포착한 호출에서 선언 이름을 찾지 못한 항목은 0개였사와요. 하지만 이것은 컴파일러의 형식 검사, 전체 프로그램의 호출 관계 확인, 소유권·스레드 안전성 검토 완료를 뜻하지 않사와요. 전처리 분기, 간접 호출, 같은 이름을 가진 지역 변수, 오버로드 선택은 추가 확인 대상이랍니다.

오버로드 검토 91개는 `CallAccumulator` 2개, `CreateArgs` 2개, `IsModActivated` 28개, `sendPurchase` 1개, `AddPopup` 57개, `nextSelectedCitiesNode` 1개이와요. 이름만으로 어느 선언이 선택되는지 확정하지 않았사와요.

## 원본 SDK 기준 빌드와 실제 연결 요구사항

SDK 1,105개 파일을 `Source/SDK_BNW_Original`에 바이트 그대로 복사하고, 원본 프로젝트·v90 개발 도구를 사용하여 BNW 소스 161개와 x86 DLL을 빌드했사와요. 생성물은 `Build/SDK_Reference/out/CvGameCoreDLL_Expansion2Win32Mod.dll`이며 PE32 / x86 / LAA로 확인했답니다. [빌드 기록](../evidence/sdk_reference/build_result.json)

원본 코드의 변경 없이 빌드 환경만 다음과 같이 보완했사와요.

1. Windows SDK v7.0A의 실제 설치 경로를 지정하여 불필요한 사용자 SDK 자동 탐색을 피했사와요.
2. 경로의 `ZeroSis'` 아포스트로피를 MSBuild 리터럴로 전달하도록 처리했사와요. [Microsoft의 MSBuild 특수문자 처리](https://learn.microsoft.com/en-us/visualstudio/msbuild/how-to-escape-special-characters-in-msbuild)
3. 설치되지 않은 MFC의 `afxres.h` 대신, 버전 리소스에 필요한 표준 Windows 정의를 `WinResrc.h`에서 받는 **리소스 전용 연결 헤더**를 추가했사와요. 이 헤더는 C++에서 사용하면 오류를 내며 MFC 구현을 제공하지 않사와요.
4. 별도 targets 파일에서 링크 지도를 생성하도록 했사와요. 원본 SDK의 프로젝트·소스·리소스 파일은 그대로랍니다.

빌드 기록의 고유 경고 행은 C4819 343개, D9040 1개, LNK4099 27개이와요. 이 숫자는 시도별 중복 제거 행 수이며 결함 개수가 아니랍니다. C4819는 현재 코드 페이지로 표현할 수 없는 소스 문자, D9040은 해당 컴파일러에서 `/analyze` 미지원, LNK4099는 제공 라이브러리의 PDB 누락을 보고하와요. **기준 빌드를 경고 없는 빌드나 정적 코드 분석 통과로 보고하지 않사와요.** 최종 DLL 생성은 성공했지만 문자·런타임 영향은 별도 검토 대상이랍니다. 이전 전체 컴파일 기록과 마지막 리소스·링크 기록은 `evidence/sdk_reference/attempts`에 보존했사와요.

## 수치 구성요소의 구현 계약

`CvCompatibleRandom`은 헤더만으로 사용할 수 있는 독립 C++17 구성요소랍니다. 기존 CvRandom과 같은 클래스 배치·바이너리 인터페이스·저장 형식을 제공한다고 주장하지 않사와요.

- 시드·호출 횟수·초기화 횟수는 명시적 32비트 정수로 보존하였사와요.
- 시드는 SDK의 상수와 32비트 넘침 규칙을 적용하였사와요.
- 0 범위 요청도 시드와 호출 횟수를 한 번 진행시키도록 유지하였사와요.
- reset과 reseed는 호출 횟수를 지우지 않으며, 초기화 횟수만 증가시키도록 유지하였사와요.
- 기본 생성자는 초기화 횟수 1, bool 인자가 있는 생성자는 인자 값과 관계없이 synchronous=true·초기화 횟수 0을 보존하였사와요.
- 동등 비교는 SDK와 같이 시드만 비교하와요. 전체 상태를 비교하려면 snapshot의 각 필드를 비교해야 하와요.
- getFloat의 계산 순서와 단정도 결과를 유지하였사와요.
- 인스턴스는 하나의 게임 상태 소유 스레드에서 관리하는 계약이며, 동시 호출에 안전한 난수기로 만들지는 않았사와요.

`numeric_snapshot`과 `restore_numeric`은 새 구성요소의 메모리 내 값 전달 API이랍니다. `RandomSnapshot` 구조체의 메모리를 그대로 파일에 기록하거나 기존 Civ V 저장 데이터로 해석해서는 안 되와요. 구조체 패딩과 원본 스트림 형식은 서로 다른 문제랍니다.

x86 참조는 설치된 CvRandom.cpp에서 산술식과 상수를 추출하고 별도의 수치 래퍼로 감싼 프로그램이랍니다. **원본 CvRandom 클래스 전체나 설치된 GameCore DLL을 그대로 실행한 비교는 아니와요.** 참조 래퍼의 생성자·카운터 동작은 소스와 대조했고, 원본 해시가 M0 조사와 다르면 생성을 중단하도록 하였사와요. [참조 추출 근거](../evidence/numerics/reference_provenance.json)

초기 빌드에서 응답 파일의 `/link` 뒤 설정이 컴파일러 옵션으로 해석되는 경고를 발견하였사와요. 링커 옵션을 명령행에 분리하고 경고 검사도 추가하여 두 아키텍처를 다시 빌드·실행했으며, 최종 로그에는 그 경고가 없답니다.

## 남은 개발 관문

1. 오버로드 91개와 간접 연결을 형식·호출 지점 기준으로 확정하고, 각 객체·서비스의 소유권과 실패 처리를 더 세분화해야 하와요.
2. 확보한 실제 외부 요구 후보 341개·최종 SDK 지도 항목 683개를 바탕으로 약한 참조·전이 연결·데이터 ABI·필수 제공자 의미를 확정해야 하와요.
3. 메모리·문자열·스트림의 x64 기반 서비스를 구현하고 DB·현지화·Lua와 연결해야 하와요.
4. 실제 GameCore 초기화·지도·도시·유닛·턴 진행까지 도달한 후 단일 스레드 결과를 비교해야 하와요.
5. 측정한 병목의 순수 계산부터 병렬화하고, 작업자 수에 따른 결과 동일성과 전체 턴 성능을 검증해야 하와요.

수치 구성요소 하나의 통과를 M3의 ‘화면 없는 실제 GameCore 실행’이나 M5의 ‘멀티코어 게임 실행’으로 올려 보고하지 않사와요.
