# 병렬 계산 결과의 상태 반영 계약

2026-09-24 작업 범위이와요. 기존 병렬 실행기는 결과 계산까지만 담당했으며, 이번 변경은 결과가 현재 입력에 대응하는지 확인하고 한 번만 반영하는 독립 상태 소유자랍니다.

## 변경 전 요구사항

| ID | 요구사항·수용 기준 |
|---|---|
| S01 | 세션·리비전·턴·단계·발급 주체가 바뀐 결과는 준비 함수를 실행하기 전에 거부해야 하와요. |
| S02 | 복사된 요청이나 결과를 반복 전달해도 동일 요청의 반영은 최대 한 번이어야 하와요. |
| S03 | 예상 작업 ID·수량·순서, 성공 상태와 오류 정보를 확인하고 누락·중복·다른 작업 결과를 거부해야 하와요. |
| S04 | 준비 함수의 거부·예외·복사 실패·취소에서는 현재 상태와 리비전이 그대로여야 하와요. 성공은 준비 완료 후 예외 없는 포인터 교체로 공개해야 하와요. |
| S05 | 소유 스레드 외 반영과 준비 중 재진입을 거부해야 하와요. 취소는 다른 스레드에서 요청할 수 있어야 하와요. |
| S06 | 새 세션, 문맥 변경, 직접 상태 교체도 같은 소유자 경계를 거치며 리비전·세션 번호가 넘쳐 조용히 재사용되지 않아야 하와요. |
| S07 | 실제 `OrderedBatch`와 결합한 독립 값 상태를 작업자 1·2·4개로 진행하여 상태 기록을 별도 Python 계산과 대조해야 하와요. |

영향 범위는 이 독립 프로젝트의 `Source/State`, `Tests`, `tools`, 문서와 Build·Stage·evidence이와요. 기존 게임·모드 파일, Mod ID·버전·밸런스·저장 키·저장 스키마를 변경하지 않사와요. 기존 GameCore의 가변 객체를 직접 감싸거나 실제 게임에 배포하는 범위도 아니랍니다.

상태와 작업 결과는 내부 데이터까지 값으로 소유해야 하와요. 준비 함수는 전달받은 후보 상태만 수정하고 외부 파일·DB·Lua·게임 객체에 효과를 발생시키지 않아야 하와요. 이 계약을 위반하는 임의 콜백의 외부 효과까지 일반 C++ 래퍼로 되돌릴 수는 없사와요.

## API·소유권·상태 전이

[VersionedState.h](../Source/State/VersionedState.h)는 C++17 값 상태 소유자랍니다. 현재 상태는 `shared_ptr<const State>`로 보관하고, 소유자를 만든 스레드만 현재 상태 조회·요청 발급·변경·반영 API에 접근할 수 있사와요. 작업자에게 전달하는 요청에는 해당 시점의 불변 스냅샷과 고정 작업 ID 목록이 있답니다.

| API | 동작·실패 계약 |
|---|---|
| `begin(ids, token)` | 비어 있지 않은 고유 64비트 ID를 정렬하고 요청 발급. 같은 값을 가진 별도 소유자도 섞일 수 없도록 소유자별 객체 식별자 사용 |
| 요청의 `snapshot`, `stamp`, `job_ids`, `cancellation`, `phase` | 요청 복사본이 같은 발급 정보와 종료 상태를 공유. 소유자 파괴 뒤에도 스냅샷 읽기는 가능하지만 다른 소유자에서 반영 불가 |
| `set_context(turn, phase)` | 실제 변경만 리비전 증가. 기존 요청은 오래된 요청이 됨 |
| `replace(value)` | 새 값 상태를 준비한 뒤 한 번에 교체하고 리비전 증가 |
| `new_session(value, turn, phase)` | 세션 증가·리비전 초기화·문맥 교체. 배치 번호는 초기화하지 않음 |
| `commit(request, result, prepare)` | 발급 정보·현재 상태·작업 목록 검증 → 후보 복사 → 준비 함수 → 최종 취소 검사 → 예외 없는 포인터 교체 |

요청 상태는 `pending → preparing → committed` 또는 `pending/preparing → discarded`로 바뀌와요. 소유 스레드 오류·다른 소유자·재진입 거부는 해당 요청을 소모하지 않으며, 발급 소유자에서 유효한 요청의 내용·시점·준비가 거부되면 `discarded`로 종료하와요. 실패 요청의 재시도는 현재 상태에서 새 요청을 발급하는 방식이랍니다.

반환 코드의 검사 순서는 소유 스레드 → 재진입 → 발급 주체 → 이미 종료된 요청 → 현재 세대·스냅샷 → 취소 → 결과 표시 → 성공 상태 → 오류·작업 목록 → 리비전 여유 → 후보 준비이와요. 예를 들어 이미 반영한 요청을 뒤늦게 취소해 다시 보내면 `already_finalized`가 우선하와요. 호출자가 여러 오류 중 하나를 임의로 선택했다고 해석하지 않도록 이 순서를 계약으로 남겼사와요.

후보 준비에서 예외가 발생하면 `preparation_failed`와 `exception_ptr`를 반환하고 현재 상태를 보존하와요. 결과·준비 객체의 값 전달 인자 구성 중 예외는 함수 진입 전 호출자에게 전달될 수 있으며, 그 시점에 요청을 종료하지는 않사와요. 발급·직접 교체·세션 변경의 잘못된 입력, 번호 고갈, 메모리 준비 실패도 예외로 보고하와요.

## 반영 경계와 취소 규칙

준비 함수는 `bool(State& candidate, const vector<JobResult<Output>>& rows)` 형식이랍니다. 결과 행의 작업 ID는 기반 구성요소가 검사하고, **객체 세대·현재 소유자·입력 기준값·합법적인 변경량·계산 넘침**은 도메인 준비 함수가 검사하와요. 이번 시험의 `World`·`Entity`는 이 경계를 시험하기 위한 별도 값 자료이며 실제 `CvCity`·`CvUnit`의 규칙을 구현한 자료가 아니와요.

현재 상태는 후보 작성 중에도 그대로 남아 있사와요. 모든 후보 메모리 준비를 마친 뒤 취소를 한 번 더 확인하고, 이후 예외 없는 포인터 교체와 리비전 증가로 공개하와요. **마지막 취소 검사에서 관측된 취소까지 미반영으로 처리**하며, 그 검사 이후 도착한 취소는 이번 반영을 되돌리지 않사와요. 다른 스레드는 현재 소유자를 직접 읽지 않고 전달받은 요청의 스냅샷·취소 토큰을 사용해야 하와요.

이 구성요소의 ‘최대 한 번’은 살아 있는 프로세스 안에서 공유 요청별로 보장하는 계약이와요. 디스크 원장, 프로세스 재시작 뒤 재전달 방지, 저장 파일 복구를 제공하는 계약은 아니랍니다. 요청 번호와 객체 식별자는 직렬화 포맷으로 정의하지 않았사와요.

## 독립 통합 시험과 추적성

[state_commit_test.cpp](../Tests/state_commit_test.cpp)는 실제 `OrderedBatch`를 사용해 스냅샷의 객체 값을 작업자에서 계산한 뒤 소유 스레드에서 반영하와요. 계산에는 앞서 대조한 CRC 구현을 사용하며, 세션 전환·문맥 변경·객체 세대와 소유자 변경을 32단계에 포함했사와요. 중복 전달은 모든 정상 반영 뒤에 다시 검사했답니다.

[verify_state_commit.py](../tools/verify_state_commit.py)의 기준 계산은 C++ 출력값을 재사용하지 않는 Python 정수·zlib 구현이랍니다. 객체별 값과 누적 반영 작업 수, 세션·리비전을 명시적 리틀엔디언 52바이트 레코드로 비교하와요. C++ 구조체 패딩이나 포인터를 기록에 넣지 않사와요. 입력 코드·빌드 도구·컴파일러·실행 파일·컴파일 로그·출력·Stage의 해시를 실행 기록에 연결했답니다.

검증된 헤더는 `Source/State → Build/StateCommit/x64 → Stage/State`로 추적하며, Stage의 기존 작업 실행기·CRC 의존성도 시험에 사용한 소스와 같은지 확인하와요. 실제 제품 의존성은 `OrderedBatch.h`이고 CRC는 이번 통합 시험의 계산 의존성이랍니다. `verify_project.py`는 이 기록들과 원본 입력의 정합성을 확인하며 자체적으로 네이티브 시험을 재실행하지는 않사와요.

## 남은 관문과 회귀 위험

- 실제 GameCore에서 읽기 전용 스냅샷을 만들 위치와 반영 전제조건, 객체 생성·삭제·점령에 따른 세대 관리가 필요하와요. 현재 소유자에 기존 가변 객체 포인터를 넣는 것만으로 이 경계가 충족되지는 않사와요.
- 상태 복사·이동·소멸자와 준비 함수는 외부 상태에 효과를 남기지 않아야 하와요. 가변 포인터·공유 저장소를 얕게 복사하거나 준비 함수에서 Lua·DB·화면 이벤트를 호출하면 후보 폐기로 되돌릴 수 없사와요. C++ 타입 검사만으로 이 순수성 계약 전체를 강제하지는 못한답니다.
- 전체 값 상태를 복사하는 방식의 시간·메모리 비용은 측정하지 않았사와요. 실제 게임에서는 필요한 범위만 분리한 자료와 변경 집합으로 바꾼 뒤 같은 실패 격리 계약을 다시 검증해야 하와요.
- 메모리 부족은 상태 복사에서 `bad_alloc`를 주입하고 이동에서 예외를 주입한 경로 시험이와요. 실제 시스템 메모리 고갈, 배치 번호 최대값까지 발급, 경쟁 상태 검사 도구·정형 증명은 수행하지 않았사와요.
- 실제 GameCore 상태 반영, 직렬 재평가 스케줄러, 저장 복구, 모드·UI 연결 및 성능 향상 검증은 미실시랍니다. 7개 기반 라이브러리의 전체 x64 대체 완료 수도 여전히 0개랍니다.
