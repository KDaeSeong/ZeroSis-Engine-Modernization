# M2: 임시 배열과 내장 데이터베이스 호출부의 실패 처리

2026-09-24 기준으로 BNW의 실제 저장·불러오기 호출부 두 곳과 SDK 임시 배열·벡터 할당기를 수정했사와요.
작은 임시 공간이 부족하면 정렬된 일반 메모리로 넘어가고, 그래도 할당할 수 없으면 명시적으로 실패하와요.
내장 데이터베이스는 모든 바이트를 확인하고 교체할 파일을 준비한 뒤에만 기존 캐시를 교체한답니다.
기존의 **4바이트 길이 + 원시 데이터** 형식과 게임 버전·저장 키·스키마는 유지했사와요.

실제 GameCore 161개 소스는 `attempt_013`에서 모두 x64 컴파일을 통과했고,
새 시험 두 개는 각각 경고 없이 빌드했사와요.
연결 미해결 이름은 **137개로 동일**하며 전체 GameCore DLL·실게임 검증은 아직 미완료랍니다.

## 요구사항·변경·배포 범위

| ID | 요구사항 | 수용 근거 |
|---|---|---|
| TC01 / TH-C01 | 부족한 메모리를 사용하지 않고 버퍼·파일 수명을 관리 | 실제 정상 할당기와 별도 실패 주입 실행 파일; 할당 실패 5건, 예외 전후 자원 확인 |
| TC02 / TH-C02 | 크기 0이 끝 주소 대여나 잘못된 일반 해제를 만들지 않음 | 가득 찬 공간과 NULL 호스트 반환 상태에서 0 크기 배열·벡터·NULL 반납 확인 |
| TC03 / TH-C03 | 곱셈·축소 변환 전에 크기 검사, 실제 할당 원천 보존 | native 곱셈 넘침 거부, 8,589,934,590바이트 요청을 좁히지 않고 실패 할당기에 전달 |
| TC04 | 정상 저장 필드 보존 | 11개 크기 × endian 3개, 실행 파일마다 33건, 별도 바이트 모델 272,547바이트 일치 |
| TC05 | 읽기·쓰기·교체 실패를 조용한 성공으로 처리하지 않음 | 실행 파일마다 입출력 실패 26건, 이전 캐시 보존·손잡이 종료·임시 파일 제거 확인 |
| TC06 | 원본과 앞선 이식 패치 보존 및 추적 | 기존 452개 패치 보존, 새 6개, 총 458개·변경 SDK 파일 57개, 정합성 검사 94개 |

SDK 변경의 정식 입력은 `define_temp_heap_caller_patches.py`와 `sdk_x64_patches.json`이며,
생성 대상은 `FTempHeap.h`와 BNW `CvGame.cpp`이와요.
별도 지원 헤더 `CvEmbeddedDatabaseIO.h`가 두 실제 호출부에서 사용되는 것도 확인했답니다.
기존 숫자 변환 패치 443개와 직렬화 패치 9개는 그대로 보존했사와요.
원본 SDK·게임 설치물·MODS·Mod ID·버전·밸런스·UI는 변경하지 않았답니다.
Source → Build → Stage의 검토 묶음이며 설치 가능한 게임 패키지는 아니와요.

## 임시 배열·벡터의 계약

배열의 원소 수×원소 크기를 native 크기로 검사하고, SDK의 uint 요청으로 표현할 수 있을 때만
임시 공간을 사용하와요. 더 큰 요청과 16바이트보다 큰 정렬은 맞는 크기·정렬의 대체 할당을 사용한답니다.
실제 임시 공간에서 받은 경우 해당 객체 주소를 보관하여 소멸 시 같은 객체에 반납하와요.
일반 메모리에서 받은 경우에는 반드시 같은 정렬 해제 경로를 사용하와요.
호스트가 이후 NULL을 반환하는 시험에서도 이미 빌린 배열이 원래 공간에 반납되는 것을 확인했답니다.

크기 0은 NULL을 보관하고 메모리를 빌리거나 호스트를 조회하지 않사와요.
벡터도 0 크기 할당·NULL 해제를 바로 처리하며, 잘못된 정렬은 명확하게 거부하와요.
0 크기가 아닌 벡터의 반납은 안정적으로 유지되는 같은 호스트 공간과 일반 메모리의 범위 구분을 사용하와요.
살아 있는 블록이 있는데 호스트 공간 자체를 교체·종료하는 사용법까지 지원하지는 않사와요.

기존처럼 원시 저장 공간만 제공하며 T의 생성자·소멸자를 호출하지 않사와요.
`FTempArray`에는 원래 임시 공간을 보관하는 포인터가 추가되었지만 저장 필드로 기록하지 않으며,
실제 TempHeap 클래스의 배치는 변경하지 않았답니다.
수정한 x64 헤더를 사용하는 네이티브 모듈들은 함께 다시 빌드해야 하와요.

## 내장 데이터베이스의 읽기·쓰기

저장 시 파일 크기를 64비트 API로 확인한 뒤 기존 uint32 저장 범위보다 크거나 음수이면 거부하와요.
파일을 전부 읽고 길이를 다시 확인하며 손잡이를 닫은 뒤에 길이와 데이터를 기록하와요.
파일이 없는 경우는 기존처럼 길이 0을 기록하지만, 접근 거부 등 다른 열기 오류를 없는 파일로 취급하지 않사와요.
부분 읽기는 나머지 데이터를 계속 읽으며, 데이터가 남았는데 0바이트가 나오면 실패하와요.
할당·크기 조회·파일 읽기 실패는 데이터베이스 필드를 기록하기 전에 발생하도록 구성했답니다.
출력 스트림이 중간에 실패한 경우 전체 저장은 여전히 폐기해야 하와요.

불러올 때는 남은 스트림 범위를 검사하고 전체 입력을 먼저 확보하와요.
같은 디렉터리에 `CREATE_NEW`로 새 파일을 소유한 다음, 모든 데이터를 쓰고 Flush·Close에 성공해야
기존 캐시와 교체하와요. 준비 단계의 실패는 그 시도에서 소유한 파일만 제거하와요.
동일한 임시 이름이 이미 있으면 새 이름을 시도하며, 충돌한 기존 파일을 제거하지 않는 것도 확인했답니다.
크기 0 입력은 기존 SDK처럼 캐시를 변경하지 않사와요.
한글이 포함된 실제 파일 경로에서 전체 시험을 수행했답니다.

## 시험 근거

정상 실행 파일은 검증된 Foundation·TempHeap·Streams 제공자를 실제 연결하여 **1,009개 검사**를 통과했사와요.
별도 실패 주입 실행 파일은 실제 SDK 래퍼를 그대로 사용하되 정렬 할당 함수만 제어 가능한 시험용으로 연결하여
**1,061개 검사**를 통과했답니다. 두 할당 함수의 제공자는 링크 지도에서 각각 확인했사와요.
주입 경로를 실제 메모리 고갈이라고 보고하지 않사와요.

| 계층 | 결과 |
|---|---|
| 원시 메모리 계약 | 임시 공간·일반 대체·64바이트 정렬·0 크기·예외 해제·원래 소유자 반납·크기 넘침 통과 |
| 실제 파일·스트림 정상 경로 | 실행 파일마다 33개, 기존 길이 폭·세 endian 모드·payload·빈 파일·없는 파일·0 입력 대조 |
| 파일 실패 주입 | 열기·크기·너무 큰 크기·음수 크기·읽기·일부 읽은 뒤 실패·길이 변경·생성·쓰기·flush·close·교체·이름 충돌 한계 |
| 스트림 실패 주입 | 예외·짧은 읽기·헤더 또는 payload의 짧은 쓰기·범위 밖 입력을 명시적 실패로 처리 |
| 할당 실패 주입 | 배열·벡터·넓은 크기·파일 저장·파일 복원 5건; 손잡이·버퍼 누수와 캐시 변경 없음 |
| 연결·회귀 | 실제 161개 AMD64 오브젝트, 숫자 경고 관문 통과, 기존 숫자·할당기·스트림·직렬화·기반·TempHeap 회귀 통과 |
| Source→Build→Stage | 테스트에 사용한 소스와 코드 생성·컴파일·연결·검토 묶음의 해시 및 보고서 정합성 |

8,589,934,590바이트 요청은 실제로 그 크기의 메모리를 잡지 않고 실패 주입 지점까지 전달된 값을 확인했사와요.
정상 파일 자료는 독립적으로 만든 바이트열이며 실제 SQLite 쿼리나 전체 Civ V 저장을 검증한 것은 아니랍니다.
이번에는 새로운 독립 시험 실행 파일만 실행했으며 GameCore DLL·Civ V는 로드하지 않았사와요.
기존 GameCore 경고는 인코딩 325곳·구식 선언 5곳·구식 API 13곳, 총 **343곳** 그대로랍니다.

## 남은 수용 관문과 회귀 위험

실제 실행부는 저장 실패 시 전체 결과를 폐기하고, 불러오기 실패 시 부분 변경된 게임 상태를 사용하지 않아야 하와요.
이번에는 캐시 교체 전의 실패를 다뤘으며 GameCore 전체 상태를 되돌리는 트랜잭션을 구현한 것은 아니랍니다.
향후 실행부 연결에서 예외 경계·실제 저장/불러오기·새 로그를 함께 검증해야 하와요.

다른 작성자가 같은 길이의 SQLite 내용을 바꾸는 중의 일관된 스냅샷, 종료·전원 손실·저장장치 실패 도중의 복구,
운영체제가 Close/Delete를 계속 거부하는 상황, 실제 물리 메모리 고갈은 아직 검증하지 않았사와요.
현재 수정·컴파일 대상은 BNW이며 Vanilla·Expansion1 호출부는 별도 이식 대상이랍니다.
오래된 호스트 메모리 영역·전체 엔진 실행·게임 턴 병렬화·성능 향상·장경로 정책도 별도 관문이와요.
이전 직렬화 단계의 순서 없는 목록 저장 순서 차이 6건과 연결 미해결 137개는 남아 있답니다.
