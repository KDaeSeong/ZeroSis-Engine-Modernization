# M2: 메모리·직렬화 스트림 x64 제공자

현재 상태: 후속 직렬화·기반 제공자 단계까지 미해결 심볼은 140개, 정합성 검사는 80개이와요. 아래 302→278개와 66개 검사는 스트림 단독 추가 단계의 기록이랍니다. [최신 기반 제공자 기록](M2_FOUNDATION_PROVIDER.md)

2026-09-24 기준으로 FMemoryStream과 FDataStream의 기본 숫자·표준 문자열 처리 코드를
독립 x64 라이브러리로 구현하고 실제 GameCore 연결에 반영했사와요.
미해결 함수는 **302→278개**, 새 미해결 이름은 **0개**랍니다.
GameCore DLL·실행부·렌더러·실제 게임 멀티코어 실행은 아직 완성되지 않았사와요.

## 범위와 수용 기준

| ID | 요구사항 | 이번 근거 |
|---|---|---|
| STR01 / F07 | 기존 숫자 폭과 직렬화 바이트 보존 | 실제 SDK x86·새 x64·별도 Python 바이트 기준 대조 |
| STR02 / F02 | 포인터는 네이티브 크기, 논리 길이는 SDK의 uint32 계약 유지 | AMD64 오브젝트, 4GB보다 높은 가상 주소에서 읽기·쓰기·확장·해제 |
| STR03 / N01 | 잘못된 위치·크기·버퍼는 거부하고 정상 상태 보존 | 실패·수명 관련 단언 31회, 거부 13회 |
| STR04 / N03 | 참조·소스·빌드·실행·링크·Stage 연결 | 해시 대조와 제공자 검증 관문, 전체 정합성 검사 66개 |

변경 범위는 이 프로젝트의 `Source/Providers/Streams`, 시험·빌드·검증 도구와 기록이랍니다.
기존 SDK 헤더와 GameCore 161개 오브젝트를 그대로 사용하였고 원본 SDK·게임·MODS·저장 파일은 보존했사와요.
Source → Build → Stage까지만 반영하였으며, 이 묶음은 설치 가능한 게임 DLL이 아니와요.
기존 Mod ID·버전·저장 키·스키마·밸런스는 변경하지 않았답니다.

## 실제 참조와 바이트 계약

참조는 SDK의 `FireWorksWin32.lib`에 들어 있는 실제 FMemoryStream·FDataStream 코드랍니다.
VC9 /MD로 별도 실행 파일을 만들고 링크 지도에서 `FireWorksWin32:FMemoryStream.obj`와
`FDataStream.obj`를 확인하였사와요. 게임이나 GameCore DLL을 불러오지 않았답니다.

SDK 라이브러리는 시작 시 실행 파일에서 `FStringA_GetStringInitData`를 찾아 빈 문자열의
공유 저장소를 얻으려 하였사와요. 시험용 실행부는 공개 SDK 구조에 맞는 고정된 빈 문자열
저장소 두 개만 제공하와요. 스트림 함수를 시험용 대체 코드로 바꾸지는 않았사와요.
이 초기화 연결이 없던 첫 실행의 null 호출 원인도 독립 자식 프로세스에서 확인했답니다.
또한 헤더의 `std::exception`과 아카이브의 `stdext::exception` 차이 때문에 참조 객체의
가상 함수표를 다시 만드는 상속 객체를 사용하지 않았사와요.

| 관측 항목 | 실제 SDK에서 확인한 규칙 |
|---|---|
| bool / char | 1바이트 |
| short / WCHAR | 2바이트 |
| int / unsigned int / Windows unsigned long | 4바이트 |
| signed / unsigned 64비트 정수 | 8바이트 |
| 기본 바이트 순서 | little endian |
| big / unknown endian | 대부분의 다중 바이트 숫자 순서 반전; **UINT64와 GUID는 그대로** |
| 문자열 | 4바이트 문자 수 뒤에 본문, 끝의 NUL은 저장하지 않음 |
| wide 문자열 | 문자 수만 지정 endian 적용; 본문은 Windows의 2바이트 문자 배열 순서 유지 |
| 표준 문자열 내부 NUL | 문자 수에 포함하여 보존 |
| Truncate | 현재 위치와 무관하게 내용 전체를 비우고 처음으로 이동 |
| CopyToMem | 현재 위치에서 끝까지 복사하며 위치는 유지 |
| 복사 생성 | 내용은 별도 버퍼로 복사하고 새 위치는 끝 |
| Init의 data / grow=false | 호출자 버퍼를 빌려 사용 |
| Init의 data / grow=true | 전달한 malloc 호환 버퍼를 인수하고 해제 책임도 인수 |
| ReadIt / 고정 버퍼 WriteIt 범위 초과 | 복사 전에 예외, 해당 시험에서 내용·위치 보존 |

특히 grow=true가 입력 내용을 자동 복제한다는 가정은 틀렸사와요.
호출자가 스택 버퍼를 넘기면 안 되며, 참조 시험의 인수 대상도 같은 CRT의 malloc 버퍼랍니다.
기존의 작은 객체 할당기·추적용 메모리 풀 연결은 이번 실행 범위에서 제외했사와요.

## 실행 검증과 오류 처리

2,048개 기록을 little·big·unknown endian 세 설정으로 비교하였사와요.
각 기록에는 숫자·GUID 15개 필드, 총 66바이트가 있답니다.
정수 경계, 음수, 부호 비트, 부동소수점의 ±0·무한대·quiet NaN·작은 값과
고정 시드로 생성한 입력을 포함하였사와요.

| 검증 | 결과 |
|---|---|
| 숫자·GUID 필드 비교 | 92,160개 모두 일치 |
| 직렬화 바이트 | 405,504바이트 모두 Python 기준과 일치 |
| x86·x64 읽기 왕복 | 설정마다 2,048개 기록, 불일치 0개 |
| 일반 동작·문자열·배열·스트림 복사·오류 시나리오 | 12개 시나리오의 전체 출력 일치 |
| 잘못된 위치 이동 | 원본과 의도적으로 다른 상태 보존 2개 시나리오 별도 기록 |
| x64 추가 경계·수명 시험 | 단언 31회, 예외 거부 13회 통과 |
| x64 제공자 자체 빌드 | /MD /W4 /WX, 오브젝트 2개·시험 프로그램 경고 0건 |
| GameCore 연결 | 24개 미해결 이름 해결, 총 278개 남음 |
| 기록 정합성 | 66개 검사 통과; 시험 재실행이나 실게임 수용을 뜻하지 않음 |

원본의 Skip·SetPosition은 끝을 넘으면 위치를 먼저 옮긴 뒤 예외를 던져 남은 길이가
4,294,967,292로 보였사와요. 새 구현은 이동 전에 범위를 검사하여 원래 위치를 유지하와요.
원본 Uninit의 남은 포인터·카운터를 그대로 흉내 내지 않고 모든 값을 초기화하며,
자기 버퍼 확장 복사·겹친 복사·자기 대입도 안전하게 처리하와요.
이 차이는 정상 파일의 저장 바이트를 바꾸지 않는 실패 처리 보완으로 기록했답니다.

문자열 읽기 실패 시 출력 문자열을 보존하고, 음수로 해석되는 개수·범위를 넘는 크기·
잘못된 bool 값도 거부하와요. 문자열 길이 헤더를 이미 읽은 경우에는 스트림 위치가
그만큼 진행되어 있을 수 있답니다. 모든 복합 저장 작업의 전체 롤백을 입증한 것은 아니와요.
실제 메모리 고갈을 강제로 주입한 검증도 아직 남아 있사와요.

SDK 외부 헤더의 기존 경고는 제공자 빌드에서 `/external:W0`로 분리하였사와요.
전체 GameCore의 기존 경고 **343개 위치**는 그대로 기록되어 있으며,
이를 새 제공자의 경고 0건과 혼동하지 않사와요.
