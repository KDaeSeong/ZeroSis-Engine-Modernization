# DB 후처리의 오류 전달과 변경 복구

2026-09-26 / 원본 SDK의 후처리는 SQL 오류를 여러 곳에서 무시한 뒤 항상 true를 반환하와요. 실제 DB를 사용하는 추출 본문 시험에서 부분 변경과 성공 오보고를 재현하고, 실패 시 되돌리는 처리를 구현했사와요. 기존 560개 패치를 보존하고 3개를 추가한 563개 패치이며, GameCore C++ 161개 재컴파일을 통과했답니다. 정식 attempt_027에서 제공자 16개와 연결해 미해결 0개·AMD64 DLL 생성을 확인했사와요. 수정 SDK 파일은 94개·지원 헤더는 6개이며 기존 경고는 343곳이랍니다.

| ID | 요구사항 | 구현·수용 기준 |
|---|---|---|
| DBPOST01 | 완전한 후처리만 성공 | 조회 준비·바인딩·실행·초기화·자원 분류 변경·상수 기록·커밋 결과 검사 |
| DBPOST02 | 일부 변경을 남기지 않음 | 작업 전용 savepoint를 만들고 복구 가능한 실패 시 해당 범위만 복구; 호출자가 시작한 바깥 트랜잭션 보존 |
| DBPOST03 | 정상 규칙 보존 | 기존 자원 분류 순서와 12개 게임 상수 유지; 키가 없는 정상 조회는 기존처럼 해당 Define을 유지 |
| DBPOST04 | 문자열 의미 보존 | 테이블 식별자의 따옴표를 이스케이프하고 키는 바인딩; 작은 고정 SQL 버퍼 제거 |
| DBPOST05 | 잘못된 입력과 실패 후 재시도 | null/닫힌 DB, 누락 열·테이블, null 메타데이터 거부; 오류 원인 제거 후 성공 |
| DBPOST06 | 범위와 호환성 | 인터페이스 배치·Mod ID·저장 키·스키마·밸런스 수치 유지; 설치 게임·SDK·MODS·원본 DB 변경 없음 |

## 실제 시험 결과

실제 SDK의 InsertGameDefine와 PerformDatabasePostProcessing 본문 및 12개 상수 정의를 추출했사와요. 원본과 수정본 알고리즘 모두 검증된 같은 x64 DB 제공자와 SQLite를 사용하와요. GC.GetGameDatabase 접근만 시험용 연결로 바꾸었으며, 원본 게임 실행 파일이나 Win32 GameCore를 실행한 시험은 아니랍니다.

| 시험 | 결과 |
|---|---|
| 원본 오류 재현 | PostDefines 반영, 전략 자원 분류, 사치 자원 분류, 하드코딩 상수 기록에 SQL 오류를 넣은 8개 경우에서 일부 변경 후 true 반환 |
| 수정본 복구 | 같은 8개 경우에서 false 반환과 변경 전 내용 복원; 오류 트리거 제거 후 재시도 성공 |
| 바깥 트랜잭션 | 위 경우 중 4개는 호출자가 먼저 시작한 트랜잭션과 기존 변경을 보존 |
| 추가 입력 경계 | 누락 테이블·열, null Name/Key, 빈 Table 등 5개 경우에서 원본 내용 보존 |
| 긴 키·따옴표·한국어 | 2,048자 이상 키와 작은따옴표·한국어, 큰따옴표가 들어간 테이블 이름을 그대로 조회 |
| 예외·커밋 실패 | DB 로그 콜백 예외와 실제 지연 외래키 제약에 의한 커밋 실패 후 변경 전으로 복구 |
| 복구 불가능한 경로 | SQLite RAISE(ROLLBACK)으로 바깥 트랜잭션까지 취소된 실제 경우에서 명시적 예외 전달과 연결 종료 확인; 복구 성공으로 오보고하지 않음 |
| 정상 동작 | 원본·수정본의 Defines와 자원 분류 결과 일치, 반복 실행 결과 동일 |
| 보유 게임 DB 자료 | Civ5CoreDatabase.db와 Civ5DebugDatabase.db의 별도 복사본 각각에서 원본·수정본 결과 일치 |
| 합계 | 원본 820개 + 수정본 1,109개 + 전체 트랜잭션 취소 64개 = 1,993개 검사, 자료 DB 실행 4회 |

시험은 /W4 /WX에서 경고 없이 빌드했으며, 시험 실행 파일과 DB DLL의 가져오기를 검사한 뒤 실행했사와요. 자료 DB의 원본 보존본을 별도 디렉터리에 다시 복사해 그 복사본에만 후처리를 적용했답니다. 실제 사용 중인 게임 캐시나 저장 파일을 열어 수정하지 않았사와요.

## 남은 초기화 관문

**CvGlobals::init은 현재 DB 후처리·캐시 준비의 반환값을 여전히 검사하지 않사와요.** 이번 수정은 후처리 함수가 자체 작업을 복구하고 실패를 정확히 반환하도록 하는 단계랍니다. 상위 초기화의 오류 전달·부분 객체 정리·상태 전이와 재시도는 이어서 구현해야 하와요. 전체 GC 초기화가 복구된다고 표시하지 않사와요.

복구 SQL 자체가 실패하면 연결을 정상으로 취급할 수 없으므로 명시적 예외를 발생시키와요. 일반 예외가 발생한 경로에서도 소멸 시 복구를 시도하되 원래 예외를 대체하지 않사와요. 저장 장치 손상·지속적 메모리 부족·SQLite가 바깥 트랜잭션 전체를 자동 취소하는 오류까지 복구가 보장된다는 의미는 아니랍니다. 이런 경우의 연결 폐기와 전체 초기화 중단은 실행부 상태 관리의 후속 계약이랍니다.

같은 Connection/Results에 대한 호출은 소유 실행 주체가 직렬화해야 하와요. 이번 처리를 게임 DB의 동시 수정 허용이나 게임 계산의 멀티코어 검증으로 해석하지 않사와요.

GameCore DLL 로드·새 게임·턴 진행·실제 모드 적용·게임 성능은 이번 시험에서 수행하지 않았사와요.

## 근거와 재현

- tools/define_database_postprocess_patches.py: 기존 560개 보존과 SDK 호출부 3개 수정
- tools/build_database_postprocess.py 및 tools/verify_database_postprocess.py: 본문·상수 추출, 실제 SQL 오류·복구, 별도 자료 DB 비교
- tools/database_postprocess_evidence.py: 시험 본문과 실제 컴파일 소스·DB 제공자의 일치 확인
- evidence/database_postprocess/: 빌드·실행·자료 비교·통합 기록
- tools/refresh_database_postprocess_integration.py 및 tools/refresh_database_postprocess_stage.py: 기반 의존성 갱신 뒤 연결·회귀·검토본 검사
- Stage/DatabasePostprocess 및 Stage/GameCore_x64: 검증된 소스·바이너리·증거의 검토 묶음

기반 의존성 갱신 22단계와 관련 통합·회귀 35단계를 통과했사와요. 기존 연결 수명·생성 실패·초기화·지도·파일·로그·디버그 검사도 보존했답니다.

후속 [GC 초기화 소스 조사](../evidence/gc_initialization/source_audit.json)는 현재 함수 본문 20개와 규칙 정보 배열 정리 대상 40개를 기록하와요. 처음 발견한 DB 로더 참조·캐시 잔존은 [로더 소유권 수정](M3_DATABASE_LOADER.md)에서 별도로 재현하고 보완했사와요. 직접 정보 배열의 종료 정리는 [후속 정보 정리 단계](M3_INFO_CLEANUP.md)에서 보완했사와요. 상위 초기화의 DB 실패 처리와 플레이어·팀 부분 생성 복구는 남아 있답니다. 소스 조사와 전체 GameCore 실행 검증은 구분하와요.
