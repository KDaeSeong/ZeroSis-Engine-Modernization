# 실행부 Lua 서비스 계약

기존 `ICvEngineScriptSystem1`의 13개 메서드와 인수 인터페이스를 그대로 구현하와요. 대상은 새 실행부이며 SDK 배치·게임 저장·모드 ID·규칙·밸런스를 변경하지 않사와요. 기존 GameCore의 실제 로딩 허가는 아직 답변을 기다리고 있답니다.

## 수용 기준

| ID | 요구사항 |
|---|---|
| LS01 | 실제 검증된 x64 Lua 5.1 제공자로 이름 있는 VM 생성·반납, 인수 생성·반납, 등록한 파일 적재, C 함수·Lua 함수 호출 |
| LS02 | SDK 인수의 bool/int/float/null/길이 있는 문자열 구분; 잘못된 조회는 출력 보존 |
| LS03 | GameEvents Add/Remove와 등록 순서의 Hook/TestAll/TestAny/Accumulator 전달; 호출 중 목록 변경은 현재 호출의 스냅숏에 영향 없음 |
| LS04 | Lua 오류·메모리 부족·보호한 C++ 콜백 예외에서 스택 복원과 반환값 보존; 오류를 성공으로 처리하지 않음 |
| LS05 | 단일 소유 스레드의 VM 접근, 호출 중 VM 파괴·전체 종료 거부, 종료 후 인수·VM 정리 |
| LS06 | 실행부에 실제 제공자 연결, 데이터 점검에서 서비스 호출, Source→Build→Stage와 독립 실행 증거 |

이 단계는 실행부의 실제 Lua VM과 이벤트 전달을 구현하와요. GameCore의 실제 게임 객체 라이브러리 등록 실행·설치 스크립트/모드의 전체 자산 경로·실게임 동등성은 이어서 검증·연결해야 하며, 독립 VM의 성공으로 대신하지 않사와요.

새 서비스의 명시적 이벤트 규약은 다음과 같답니다. 등록한 VM의 생성 순서와 각 VM의 함수 등록 순서를 지키며, 같은 함수의 중복 Add는 별도 등록으로 취급하와요. Remove는 해당 함수의 모든 등록을 제거하와요. Hook과 TestAny는 Lua 참값의 OR, TestAll은 AND이며 숫자 누적은 콜백 반환값의 합이랍니다. 구독자가 없는 이벤트는 기존 출력값을 유지하고 false를 반환하와요. 인수가 없는 이벤트도 구독자가 있으면 전달하와요. 인수는 콜백의 원래 인수 순서로 전달하며 누적 초기값을 앞에 추가하지 않사와요. 모든 VM의 구독 목록을 먼저 고정하고, 모든 콜백이 끝난 뒤에만 네이티브 출력값을 게시하와요.

위 복수 구독자·중복·제거·nil·수치 누적 규약은 기존 비공개 실행부와의 실행 비교가 아직 필요하답니다. 설치 시나리오의 실제 콜백 인수와 SDK 호출부는 참고하되 완전한 원본 동등성으로 표시하지 않사와요. 앞서 실행된 콜백의 임의 Lua/게임 상태 변경을 되돌리는 트랜잭션도 아니랍니다.

파일 적재는 호스트가 등록한 파일과 후속 단계에서 연결한 선택된 보유 스크립트 카탈로그로 수행하와요. 기본 VM은 base/table/string/math 라이브러리와 GameEvents를 제공하며 일반 파일·프로세스 실행 기능은 제공하지 않사와요. 게임 객체의 실제 등록·전체 UI/모드 자산은 후속 범위랍니다. 기본 지도 18종의 원본 적재·정보 실행과 게임 라이브러리 바인딩 코드는 [자료 연결 단계](M3_HOST_SCRIPT_ASSETS.md)에 기록하와요.

## 소유권과 실패 계약

`HostState`가 실제 `ScriptSystem`을 소유하고 `GetScriptSystem`은 같은 서비스의 빌린 포인터를 반환하와요. `CreateLuaThread`는 이 호스트에서 독립 Lua 상태를 만들며, 원본 실행부의 스레드 간 전역 공유 의미는 아직 비교하지 않았답니다. 인수 `Push`는 추가한 항목의 0부터 시작하는 인덱스를 반환하며, 해당 반환값의 원본 의미도 후속 비교 범위랍니다. 문자열은 내부 NUL을 포함한 길이를 보존하며 `GetString`으로 받은 포인터는 해당 인수 변경·파괴 전까지만 유효하와요.

종료 전에는 모든 Lua 호출이 끝나 있어야 하며, 호출 중 종료는 GameCore를 정리하기 전에 거부하와요. GameCore의 Uninit이 빌린 VM을 반납한 다음 남은 VM을 닫고, 이후 엔진 연결·DB 연결·모듈을 해제하와요. `Close`는 중복 호출에 안전하고 종료한 서비스를 다시 열지 않으며, 새 세션에는 새 서비스를 구성하와요. 게임 객체 등록 후에는 finalizer가 이미 종료한 게임 객체를 접근하지 못하도록 객체 수명·세대 검증이 추가로 필요하답니다.

Lua 할당·파싱·구독 목록 고정과 호출은 보호 경계 안에서 실행하와요. 직접 `CallFunction`의 입력·스택 준비 실패는 기존 스택을 보존하며, 함수 실행 실패는 함수와 인수를 제거하고 그 아래 값을 보존하와요. 중첩 호출과 이벤트 준비 실패는 이미 확보한 구독 참조를 반납하와요. 숫자 누적의 범위 초과·소수 정수 변환·무한대·잘못된 반환형은 출력 변경 없이 거부하와요.

이 Lua 제공자는 C로 빌드되어 오류 전달에 longjmp를 사용하와요. 보호 래퍼로 등록한 C++ 함수의 예외는 C++ 정리를 마친 뒤 Lua 오류로 전달하지만, 임의 SDK C++ 콜백 내부에서 직접 Lua 오류를 발생시키는 경우의 지역 객체 정리까지 보증하지 않사와요. 실제 게임 라이브러리 등록 때 해당 호출부를 검토해야 하며, 원본 게임 이벤트와의 의미 동등성·실게임 검증은 별도 관문이랍니다.

## 실제 실행 결과

2026-09-27의 `Tests/sdk_host_script.cpp`는 실제 Lua 정적 라이브러리를 연결한 x64 실행 파일에서 **3,201개 단언**을 통과했사와요. VM 생성·소멸과 인수 형식, 내부 NUL, 512개 인수, 등록 파일·구문/실행 오류, 중첩 Lua 호출과 이벤트, 서로 다른 VM의 구독 변경, 다중 반환값·4,000개 반환 슬롯, 중복 등록/제거와 누적값 범위, C++ 예외 뒤 지역 정리를 확인했답니다.

| 실패·수명 검사 | 결과 |
|---|---|
| Lua 상태 생성·라이브러리 초기화의 할당 실패 | 423개 실패 지점, 반쯤 만든 VM 미등록·할당 잔존 0 |
| Lua 코드 적재·실행의 할당 실패 | 135개 실패 지점, 스택 아래 값 보존·다음 실행 성공 |
| 이벤트 준비·호출의 할당 실패 | 117개 실패 지점, 네이티브 출력 보존·다음 이벤트 성공 |
| C++ 인수 생성·이벤트 준비의 할당 실패 | 6개 실패 지점, 소유 인수·출력·호출 상태 보존 |
| 다른 스레드의 접근 | 160회 거부, 소유 스레드의 VM·인수 보존 |
| 독립 서비스 생성·사용·종료 | 32회 |
| GameCore 종료 순서 | 계측 문맥의 추가 36개 단언; Lua 콜백 중 종료 거부, Uninit 뒤·모듈 해제 전 finalizer 실행 |

실행부 `--check-data`도 SDK `GetScriptSystem`을 통해 실제 Lua를 호출하와요. DB의 문명 수 45와 현지화 표본을 인수로 보내고, Lua가 문자열 바이트 수를 더한 결과를 별도 Python 계산과 비교했사와요. 영어는 45+13=58, 한국어는 45+16=61로 일치했답니다. 이 표본 함수는 호스트 연결 진단이며 설치된 게임 스크립트를 실행했다는 증거는 아니랍니다.

실행부 전체는 수명 검사 4,056개·지도/음향 12,615개·스크립트 3,201개·자료/등록 1,076개, **합계 20,948개 단언과 24개 프로세스 실행**을 통과했사와요. 다섯 실행 파일의 빌드는 경고 0개이며 실제 Lua 진입점·소비 헤더·라이브러리·실행 로그를 기록했답니다. GameCore·원래 게임 실행과 게임 계산 병렬화는 모두 미검증 상태로 유지하와요.

재현은 `docs/M3_NATIVE_HOST.md`의 빌드·묶음 준비·검증·Stage 절차를 사용하와요. 기록은 `evidence/host/conformance.json`, `scripts_execution.log`, `tests_execution.log`, `build_result.json`에 있답니다. 게임 객체 라이브러리의 실제 등록·실패 복구, 활성 UI·모드 파일 탐색, 원본 VM 공유·이벤트 의미·난수 연결이 다음 작업이와요.
