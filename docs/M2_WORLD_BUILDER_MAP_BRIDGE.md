## 파일과 객체의 계약

- `LoadMapBytes`는 파일 구조를 검증하고 별도 지도에 변환을 준비한 뒤 상태를 반영하와요. 마지막 할당 가능 작업인 부가 데이터 읽기가 성공한 뒤 고정 필드 복사와 포인터 교환만 수행하와요. 예외가 나면 대상 지도의 기존 상태가 유지된답니다.
- 일반 지도 읽기와 시나리오 읽기를 구분하와요. `scenario=false`에서는 원본처럼 기존 시나리오 상태를 보존하와요. 타입 목록의 순서 변경·누락과 기존 객체 재사용을 원본의 12개 실행과 대조했사와요.
- 파일에 없는 구형 필드는 정의된 이전 상태를 유지하와요. 버전 6/7 플래그와 구형 도시·플레이어·유닛 변환은 관측한 원본 의미를 따르와요. `UnitV2`는 사용자 이름 참조를 지우는 원본 동작을 유지하며 이름 풀 자체는 버리지 않사와요.
- 타입 식별자와 기술·정책·건물·승급 비트는 이름 목록을 기준으로 재배치하와요. 모르는 타입은 해당 SDK의 무효 값으로 바꾸와요.
- 시나리오 풀이 교체되면 축소된 지도 밖의 유닛·도시 참조도 무효화하여 해제된 슬롯을 다시 참조하지 않도록 하와요.
- 저장은 네이티브 객체 메모리를 복사하지 않고 필드별로 버전 12를 생성하와요. 원본 x86과 x64의 객체 크기 차이가 파일에 들어가지 않사와요. 고정 문자열의 여분과 레코드 패딩은 0으로 쓰므로 원본 파일 전체의 바이트 동일성을 주장하지 않사와요.
- SDK `Load`는 엄격한 검증을 사용하와요. 설치 지도 3개의 잘못된 빈 슬롯 목록은 별도 `RebuildInvalidFreeLists` 호출로만 복구하고 비트 마스크를 반환하와요. 설치 원본을 조용히 고치거나 덮어쓰지 않사와요.
- `PreviewPlayableCivCount`는 지원 버전·크기·참가자 수를 확인한 10바이트 헤더 미리보기랍니다. 전체 파일의 유효성을 보증하지 않사와요.
- SDK 파일 길이·위치가 x64에서도 32비트이므로, 이 범위를 넘는 출력은 파일을 열기 전에 거부하와요. 4GB 초과 파일을 실제 생성한 시험은 이번 검증에 포함하지 않았사와요.

## 원본 버전 9의 시야 읽기 결함

`LateGameTest.Civ5Map`은 66×42 타일·플레이어 2명·팀 2개이와요. 독립 파일 해석 기준으로 시야는 오프셋 42,168부터 693바이트이며, 이 버전에는 영향력 배열이 없답니다.

그런데 실제 원본 `Load9`는 플레이어 수를 8비트 왼쪽 이동한 512바이트를 영향력으로 복사하고, 시야의 시작점도 512바이트 뒤로 옮기와요. 마지막에는 해당 읽기 블록 밖의 512바이트를 참조하게 된답니다. 연결된 원본 명령의 `00408938`, `00408944`, `0040895E`, `00408962`와 원본 함수 연결 지도를 보존했사와요.

원본의 시야 앞 1,448비트가 실제 파일 시야의 4,096번째 비트부터 일치하고, 같은 원본 파일의 재실행 5회에서 시야 기록이 각각 달랐사와요. 이 지도에서는 나머지 관측 상태가 같았답니다. 후보는 실제 파일의 5,544개 시야 비트와 정확히 같고, 잘못 읽은 임의 메모리는 재현하지 않사와요.

별도의 작은 버전 9 자료에서는 60개 시야 비트를 알려진 무늬로 만들고 이전 영향력 2,048개를 각각 다른 값으로 설정했사와요. 파일의 시야가 정확히 반영되고 파일에 없는 영향력은 보존되며, 버전 12 저장 후 다시 읽어도 관측 상태가 같았답니다.

## 검증 결과와 범위

- 설치 지도 128개와 원본 SDK 생성 시험 자료 2개, 합계 130개를 실제 원본 x86 아카이브와 x64 구현으로 읽었사와요. 129개는 관측 상태가 정확히 같고 버전 9의 1개는 위 명시적 수정으로 구분하와요.
- 후보가 저장한 130개 모두 원본 SDK에서 다시 읽었고 후보의 관측 상태 기록과 정확히 같았사와요. 여기서 관측 상태는 타일·참조된 유닛/도시·플레이어·관계·시야·부가 데이터·옵션 등의 고정 폭 기록이며 모든 비활성 슬롯이나 모든 비공개 필드를 뜻하지 않사와요.
- 정상/시나리오 제외/타입 역순/타입 없음/기존 객체 재사용을 자료 2개에 적용한 12개 비교가 일치했사와요.
- 실패·경계 시험 16,669회를 통과했사와요. 잘린 입력 6,530건, C++ 할당 실패 267건과 성공 재시도 3건, 읽기·미리보기 오류 10종, 쓰기 오류 8종, 7바이트 단위의 짧은 입출력, 잘못된 객체의 출력 열기 전 거부를 포함하와요.
- 형식 이름을 프로세스 수명 동안 보관하는 기존 공용 표를 준비한 뒤 할당 수를 추적했사와요. 작업 종료의 생존 할당 수가 준비 직후와 같았고, 각 할당 실패에서도 기존 값과 풀 바이트가 유지되었답니다. C `malloc` 실패 주입은 이번 검증에 포함하지 않았사와요.
- 작업자 4개의 독립 지도 128개에서 읽기·쓰기·상태 기록이 같았사와요. 같은 지도 객체의 동시 변경이나 게임 턴 병렬화의 검증은 아니와요.
- 제품과 후보 시험 프로그램은 `/MD /W4 /WX /fp:strict`로 경고 없이 빌드했사와요. 원본 SDK 헤더의 기존 경고는 원본 빌드 기록에 남아 있답니다. 시험 실행 파일의 의존 모듈을 점검했으며 GameCore DLL과 게임을 로드하지 않았사와요.

## 실제 GameCore 연결 영향

정식 attempt_020의 GameCore 오브젝트 161개에서 지도 제공자를 제외하면 누락 17개, 객체 구현만 추가하면 7개, 파일 연결까지 추가하면 4개랍니다. 지도 객체 10개에 파일 API 3개가 더해져 총 13개가 해소되었사와요. 시험용 파일 시스템 바인딩은 정식 연결이나 이 비교에 넣지 않았사와요.

남은 4개는 `FIFileSystem::GetInstance`, `FILogFileMgr::GetInstance`, `FDebugHelper::GetInstance`, `FDebugHelper::LoadSymbols`랍니다. 정식 연결과 비교 실행 모두 DLL 미생성 상태이며 GameCore를 로드하지 않았사와요.

## 남은 관문과 회귀 위험

1. 접근 선언과 정식 SDK 통합·재빌드는 완료했으며, 향후 해당 헤더 변경 시 같은 전체 회귀 경로를 유지해야 하와요.
2. 실제 파일 시스템·로그·디버그 서비스와 실행부 초기화를 구현해야 하와요. 현재 파일 전송부는 시험용 메모리 장치랍니다.
3. `Save`는 직렬화·검증을 출력 열기 전에 마치지만, 출력 쓰기나 닫기에 실패하면 부분 파일이 남을 수 있사와요. SDK `FIFile`에는 원자적 파일 교체 API가 없으므로 실제 파일 서비스에서 임시 파일·교체·복구 계약을 구현해야 하와요. 원자적 파일 저장 검증은 통과로 표시하지 않사와요.
4. 버전 0–5·8·13 이상, C 할당 실패, SDK 공개 풀 직접 조작과 모든 비공개 필드의 완전 동등성은 이번 범위 밖이랍니다.
5. 전체 저장 호환성·모드·새 게임·턴 진행·멀티플레이·실제 게임 멀티코어·속도 향상은 여전히 별도 관문이와요. 실게임 실행은 별도 허용 뒤 진행하와요.
