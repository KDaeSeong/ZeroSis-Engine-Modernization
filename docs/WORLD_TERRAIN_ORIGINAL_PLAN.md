## 1. 지금 엔진이 그리는 방식

`Source/Presentation/WorldTerrainRenderer.cpp`(2026-10-05 "첫 3D 지형 후보")의 동작은 다음과 같다.

- **타일 단위 그리기:** 육각형 하나를 6개 부채꼴로 나눠 그리고, 재질은 타일마다 하나만 고른다(`MaterialId`). 재질별로 한 번씩 그리며 혼합 상태는 불투명(opaque)이다. 그래서 이웃 타일 사이에 재질 혼합이 없다.
- **UV:** 월드 좌표에 0.8을 곱한 임시 값이다. 코드 주석에도 TerrainDef의 Texture Scale로 보정하지 않았다고 적혀 있다.
- **높이:** 언덕·산만 원본 높이 조각 하나(Grass Hill 또는 Mountain)를 써서 올리고, 타일 가장자리에서 0으로 줄인다. 주석에는 "retail piece neighbourhood assembly … reconstructed" 전까지의 임시 처리라고 적혀 있다.
- **조명:** 면 법선과 고정 광원 방향으로 밝기를 0.48–1.0 사이에서 정한다.
- **안개:** 미탐색 타일은 거의 검은 단색(0.002, 0.003, 0.004)이고, 보이지 않는 탐색 타일은 밝기 30%다.
- **물:** 지형 색에 고정 파랑을 72% 섞는다.
- **타일 선택:** `SV_Target1`의 R32_UINT 타일 ID 표로 픽셀 단위 선택을 한다. 이 계약은 유지해야 한다.

## 2. 원본이 쓰는 구조 (정적 근거)

근거 파일은 모두 `evidence/world_terrain_original/` 아래에 있다.
- `retail_renderer_probe.py` / `.json`: 소매 EXE 정적 분석. 고정 SHA를 확인하고 각 주장마다 require 검사를 둔다.
- `asset_inventory.py` / `.json`: FPK 목록, TerrainDef.csv, 조각 라이브러리 머리말.
- `asset_details.py` / `.json`: DDS 머리말과 작은 텍스트 정의.
- `retail_terrain_pipeline_probe.py` / `.json`: 효과(effect)별 패스와 실제 DXBC의 대응, 조각 라이브러리 읽기 코드. 소매 EXE 정적 분석이다.
- `terrain_shader_semantics.py` / `.json`: 위 대응으로 고른 SM5 셰이더 26개를 `fxc /dumpbin`으로 디스어셈블하고, 해석이 기대는 명령을 그대로 대조한다(26/26 PASS). 디스어셈블 결과는 임시 폴더에 두고 실행 뒤 지운다.
- `pieces_library_format.py` / `.json`: `TerrainPiecesLibrary.fxsb` 전체 해독(SHA `86faac1e…`).
- `shader_disasm.py` / `shader_disasm_index.json`: 내장 DXBC 1,417개 전체의 디스어셈블 색인(셰이더 모델, 자원, 명령 수).
- `retail_terrain_blend_cpu_probe.py` / `.json`: CPU 쪽 혼합(TerrainDef 읽기, 커널, 재질 표, 청크 재질, 꼭짓점 가중치, 패스 선택, 조각 찍기). 소매 EXE 정적 분석이다.
- `pieces_id_rows.py` / `.json`: 조각 _T1 값과 TerrainDef 행의 대조.
- `retail_piece_placement_probe.py` / `.json`: 조각 대조·배치(HexPatternMatcher), 방향 4종, 텍셀 좌표 행렬, 찍기 레코드. 소매 EXE 정적 분석이다.
- `piece_cells.py` / `.json`: 조각 299개의 10×10 칸 해독(지형 비트, 대륙, 소유 칸, 단계).
- `retail_terrain_remaining_probe.py` / `.json`: 파일 조회 순서, 반사 캐시 플래그 조건, 지도 칸 함수의 두 번째 플롯 반복. 소매 EXE 정적 분석이다.
- `retail_map_cells_probe.py` / `.json`: 난수 시드와 지도 칸 채우기(플롯 → 지형 비트·대륙). 소매 EXE 정적 분석이며, 인터페이스 이름은 공개 SDK 머리말 `CvDllInterfaces.h`의 슬롯 순서로 붙였다.

### 2.1 지형 재질 정의

- `TerrainDef.csv`의 열은 다음과 같다: Continent ID, Diffuse, Heightmap, Specmap, BaseDominance, Texture Scale, Projection(0 수평/1 수직), ID.
  - 재질마다 확산(_D)·높이(_H)·반사(_S) 텍스처가 짝을 이룬다. 크기 예: 초원·평원 _D 1024² BC3, _H 2048² BC3, 유럽 산 기슭 _H 512² BC3.
  - BaseDominance는 0 또는 1이다. DLC 정의에서 1인 행은 7개다: 대륙별 산 기슭(Mountain_Base) 4개, Gibraltar, Crater, 아메리카 산 정상(Amer_Mountain_Top). FPK 정의에서는 아메리카 산 정상이 0이다.
  - Texture Scale은 재질마다 다르다(예: 초원 0.014, 해안 0.17, 얕은 바다 0.004). 원본 UV가 월드 공간에서 재질별 축척을 쓴다는 근거다.
- 소매 EXE는 `assets\terrain\TerrainTextures\TerrainDef.csv`를 `TerrainSystem.cpp`에서 읽는다.
- **읽기 코드(확정, `retail_terrain_blend_cpu_probe.json`, EXE 0x61bae0):** 쉼표를 공백으로 바꾼 뒤 `%i %s %s %s %f %f %i %x`로 읽는다.
  - 행은 파일 순서대로 저장된다. 혼합에서 재질을 가리키는 번호는 이 **행 번호**(머리줄 제외, 0부터)다.
  - BaseDominance는 `%f`로 읽힌 뒤 어디에도 저장되지 않는다. 즉 이 EXE의 지형 혼합에는 쓰이지 않는다. 행 표의 실수 칸 하나(+0x308)는 항상 0.0으로 채워진다.
  - ID 열은 16진수(`%x`)로 읽혀 `0x100000 + 대륙×0x10000 | ID` 키로 저장된다. 혼합 계산은 이 키를 쓰지 않는다.
  - Projection이 1인 행은 재질 3개(투영 0·1·2)로 펼쳐진다. 꼭짓점마다 법선으로 투영을 고른다: 법선 z > 0.9이면 0(위에서), |법선 y| > |법선 x|이면 1(xz 평면), 아니면 2(yz 평면). Projection이 0인 행은 재질 1개(투영 0)다. 재질은 최대 64개다.
  - 파일 끝에 Checkerboard.dds 행(축척 0.01)이 하나 더 붙는다.
- 같은 이름의 정의가 두 벌 있고 값이 다르다: `Assets/DLC/Shared/Terrain/TerrainDef.csv`와 `TerrainModels.fpk`의 `terraindef.csv`. 예를 들어 Mesa(40)의 축척이 0.05와 0.03, Amer 산(10)의 투영이 0과 1로 다르다. 파일 조회 순서로 보면 DLC/Shared 쪽이 적용된다(2.9절). 현재 엔진 패키지(`tools/civ5_terrain_assets.py`)도 DLC/Shared 쪽을 쓴다.
  - 두 벌의 행 순서는 같고, 0행만 다르다(DLC는 Asia_Tundra, FPK는 NULL). 조각 바깥의 ID 값 0이 0행을 가리키므로 이 차이는 화면에 영향을 줄 수 있다.
  - Projection 값이 다른 행(예: 아메리카 산 기슭)은 위 규칙에 따라 가파른 면의 투영 방식이 달라진다.

### 2.2 타일 사이 혼합

- **혼합 전담 시스템:** `cvTerrainBlend.cpp`가 따로 있고, `Resource\Common\TerrainPiecesLibrary.fxsb`(27,595,584바이트)를 읽는다.
  - 같은 문자열 묶음에 조각 분류 이름이 있다: Default, Grass, GrassHill, Plains, PlainsHill, Snow, SnowHill, Desert, DesertHill, Tundra, TundraHill, Mountain, DefaultShallows.
- **텍스처 분류명:** Terrain Heightfield, Terrain Albedo, Terrain Spec Map, Terrain Piece Heightmap, Terrain Piece Blend/ID, Terrain Decal Diffuse/Height.
- **관련 텍스처:** `hexgridid.dds`(320×320, 8비트 단일 채널, mip 없음)와 `tf_blend.dds`(128×128 RGBA).
  - `TF_BLEND.dds`는 LayoutSystem이 `DF_flat`, `_A1.dds`–`_A8.dds`와 함께 읽는다(EXE 0x663fc0). 지형 재질 혼합에는 쓰이지 않는다.
  - `hexgridid`라는 이름은 EXE 어디에도(ASCII, UTF-16) 없다. 렌더러가 이름으로 읽는 텍스처가 아니다.
- **조각 라이브러리 형식(해독 완료, `pieces_library_format.json`):**
  - 읽기 코드(EXE 0x5fca30): 버전 u32(20이어야 함) 뒤에 "u32 개수 + 원소" 배열 4개가 온다. 원소 크기는 4, 1, 2, 0x56c바이트다. 파일 끝과 정확히 맞는다. 파일이 없거나 버전이 다르면 `Generic/America/Asia/Africa/Europe` 폴더의 `*.csv`로 다시 만든다.
  - 조각 레코드 299개. 각 조각에 10×10 칸 격자와 정사각 이미지 4장(128px 148개, 512px 151개)이 있다. 이미지 이름은 `_H`(높이), `_T1`(ID), `_H_BLEND`, `_T_BLEND`이다.
  - 높이 이미지는 16비트, 나머지 셋은 8비트다. 모두 행 단위 런렝스(개수, 값)로 저장된다. 299×4장을 모두 풀었고, 모든 행의 길이 합이 이미지 너비와 같으며 두 런렝스 스트림이 남김없이 소비된다.
  - 육각형 바깥은 ID·혼합 이미지에서 0이다.
  - ID 이미지 값(0, 2–40 중 35종)은 TerrainDef의 ID 열이 아니라 **행 번호**다(`pieces_id_rows.json`). 예: `Amer_Grass` 조각의 11은 11행 Amer_Grassland, `Afri_Desert`의 27은 27행 Afri_Desert다. 종류가 분명한 조각 374건이 모두 같은 종류의 행을 가리킨다.
- **셰이더 대응(확정, `retail_terrain_pipeline_probe.json`):** 효과마다 0x520바이트 레코드가 셰이더 ID 순으로 놓인다(기준 0x5d1e5c0). 레코드 앞부분은 패스마다 셰이더 핸들 5개(VS, PS, GS, HS, DS)이고, 초기화 코드가 핸들과 DXBC를 고정한다. 그래서 RDEF 없이도 패스별 바이트코드를 정할 수 있었다. 수식은 2.5절에 정리했다.
- **내장 DXBC:** 1,417개(PS 1,034·VS 380·HS 2·DS 1), RDEF는 모두 제거돼 있다. 같은 셰이더가 SM 4.0·4.1·5.0 세 벌로 들어 있다. HS/DS는 지형 테셀레이션 전용이며 SM5에만 있다.

### 2.3 전장의 안개

원본은 안개를 세 겹으로 처리한다.

1. **FOW 마스크 계열:** FOWCell(0x32), FOWParticleShader(0x33: PartTexture, FOWMask), FOWDrawMask(0x34)·FOWBaseLayer(0x35: 둘 다 FOWBaseLayerTexture, FOWBaseMask).
   - 숲·물·건물 계열 셰이더가 FOWMask, FOWBaseLayer, TransFOWColor 또는 FOWColorKey를 읽는다. 따라서 탐색·가시 상태를 텍스처 마스크로 만들고, 각 물체 셰이더가 그 마스크로 색을 바꾸는 구조다.
   - FOWDrawMask는 타일 모양 기하를 인스턴스로 그려 마스크 채널에 값을 쓴다: 패스 0은 G, 패스 1은 R과 B, 패스 2는 R만 쓰고, 패스 3은 0으로 지운다.
   - 지형 셰이더는 마스크 R로 "지형 ↔ 대체 층"을 섞고, R×(1−B)로 색 LUT를 적용한다. 구름 입자와 FOWBaseLayer는 마스크 G가 0.01 미만인 곳을 버린다.
   - 사용처로 본 채널 해석(후보): R = 탐색됨, B = 지금 보임, G = 구름·대체 층을 깔 영역.
2. **움직이는 안개 구름(FluidFOW):** `FluidFOW.cpp`가 다음을 준비한다.
   - `FogCloudTile_dif_01/02/03.dds`(1024², BC3/BC1/BC3), `flowfield.dds`, `FX_Fog_dif.dds`(512² BC3).
   - 같은 구간(0x44ae80–0x44b260)에서 128바이트 설명자 할당 함수(0x8c69b0)를 4번 부른다. 무엇을 위한 설명자인지는 미확정이다.
   - 흐름장으로 구름 타일을 흘리는 방식으로 보이며, 정확한 수식은 미확정이다.
3. **거리 안개:** `assets/DistanceFog/FogColor.csv`(값 `146,182,243`)와 `FogRamp.dds`(128×8 RGBA). 지형·물 셰이더의 DistanceFogRamp, WaterFogRamp 바인딩이 이것을 쓴다.

### 2.5 원본 지형 그리기 파이프라인 (바이트코드 근거)

`terrain_shader_semantics.json`이 아래 각 항목의 근거 명령을 그대로 대조한다. 셰이더 이름 옆 괄호는 효과 ID와 패스 번호다.
- 확정: 연산 순서와 상수(수식).
- 해석: "조명 캐시", "그림자 캐시", "화면 공간 조명 버퍼" 같은 텍스처 이름. RDEF가 없어서 바이트코드로는 슬롯 이름을 알 수 없고, 좌표계와 쓰임으로 붙인 이름이다.
- 미확인: 각 캐시 패스가 프레임마다 어떤 순서로 도는지(패스 소속만 확정).

1. **지형 면:** 타일별 부채꼴이 아니라 전역 높이장(heightfield) 격자다.
   - 높이 = 높이장 텍스처의 알파 × `cb1[16].z` × 255.
   - SM5(TerrainShader 패스 0–2)는 4×4 제어점으로 사각 패치를 만든다. HS가 모든 변과 안쪽에 같은 분할 계수(`cb1[14].x`)를 주고(정수 분할), DS가 기저 행렬 `cb1[10..13]`로 쌍삼차(bicubic) 곡면을 계산한다. 11월 16일에 원본 업로드 값 16개와 제어점 순서를 확인했다. 기저는 Mitchell–Netravali의 B=¾, C=0이다. [분석 결과](../evidence/world_terrain_original/claude_geometry/HANDOFF_RESULT.md)
   - 나머지 패스(3–7)는 같은 높이 읽기를 꼭짓점마다 하는 일반 격자다.
2. **재질 혼합 캐시**(TerrainShaderScreen 0x4c, 패스 0–2):
   - 꼭짓점이 이미 캐시 화면 좌표에 있는 "혼합 메시"를 그린다. 꼭짓점마다 재질 슬롯 8개(BLENDINDICES0/1)와 가중치 8개(TEXCOORD2/3)를 가진다.
   - 슬롯은 `cb2[]`의 (Texture Scale, Projection)을 읽는다. UV는 투영 0이면 월드 xy×축척×0.33, 1이면 xz×축척×0.66, 2이면 yz×축척×0.66이다. TerrainDef의 Texture Scale·Projection 열이 여기에 쓰인다.
   - 픽셀 셰이더: 가중치가 0.01 이하인 층은 건너뛴다. 층마다 d = 확산², h = 높이, s = 반사²를 읽는다. 혼합 가중치는 W = (확산 알파의 8제곱) × w이다. 출력은 Σ W·d / ΣW, Σ W·h / ΣW, Σ W·s / ΣW 세 목표다(반사가 없는 변형은 두 목표).
   - 다른 가중치 경로(패스 1의 VS): 정수 지형 ID 텍스처(행은 1023−y)를 5×5 가우스(중심 0.157207)로 흐려 슬롯 8개에 나눠 담는다. ID는 `cb0[9+id]` 표로 슬롯에 대응하고, 그 표의 열은 BLENDINDICES0.x(0/1/2)가 고른다.
   - 자기 그림자(패스 3): 높이장을 빛 방향(`cb1[17].xy`)으로 40걸음 따라가며, 단위 거리마다 광선이 0.314485씩 올라간다. 결과에 `cb0[75].z`를 곱한다.
3. **법선 캐시**(NormalCalculate 0x4a): 높이 캐시에 소벨(Sobel) 8탭(세기 `cb1[1].x`)을 적용하고 n×0.5+0.5로 저장한다.
4. **조명 캐시**(CacheBake 0x4b):
   - 법선 캐시로 접공간 법선을 만든다. 조사(irradiance) 큐브맵 2장(×1.7)을 그림자 캐시로 섞고 확산 캐시를 곱한다. 감마 1/2.2와 3D 색 LUT를 적용한다.
   - 반사 변형은 (N·`cb1[21]`)^(64g+1)×(64g+1)×(1−그림자)×반사 캐시를 두 번째 목표로 쓴다. g는 반사 캐시 알파다.
5. **최종 지형**(TerrainShader 패스 0/3):
   - 조명 캐시를 읽고, `cb1[27]`이 켜져 있으면 반사 조명 캐시(t8) × 화면 공간 조명 버퍼(t9)를 선형 공간에서 더한다.
   - 월드 투영 마스크 × `cb1[25].x`만큼 3D LUT를 적용한다.
   - 지도 공간 덧그림(premultiplied)을 얹는다.
   - FOW: 대체 층과 지형을 마스크 R로 섞은 뒤, R×(1−B)만큼 3D LUT로 색을 바꾼다.
   - 거리·높이 안개: 카메라(`cb1[19]`) 기준 지수식이다. 안개색 `cb2[0]`을 FogRamp 행 `cb2[1].w`(화면 y로 읽음)로 조절해 섞는다.
6. **데칼**(TerrainDecalShader 0x4e): 확산, 부호 있는 높이(2y−1의 부호로 더하기/빼기 형식 선택), 반사를 캐시에 쓴다.

### 2.6 CPU 쪽 혼합 (확정, `retail_terrain_blend_cpu_probe.json`)

2.5절의 혼합 셰이더가 받는 꼭짓점 재질 번호와 가중치 w는 CPU가 아래 순서로 만든다.

1. **조각 찍기**(0x463b10): 배치된 조각마다 _T1·_T_BLEND·_H_BLEND(8비트)와 _H(16비트) 이미지를 풀어 텍셀에 쓴다. 이미지 이름과 역할의 대응은 쓰임과 레코드 순서로 본 해석이다.
   - 텍셀 ID: 겹친 조각 중 _T_BLEND 값이 가장 큰 조각의 _T1 값(행 번호).
   - 텍셀 높이: (_H/65535 − 기준값) × _H_BLEND/255를 더하고, _H_BLEND/255도 따로 더한다(가중 평균용).
2. **재질 표:** 행마다 재질 1개, Projection 1인 행은 3개(2.1절).
3. **청크 재질 선택**(0x568430): 청크와 테두리 2텍셀의 재질 빈도를 세어(투영 변형 포함) 많은 순으로 최대 8개를 고른다.
4. **꼭짓점 가중치**(0x527720): 5×5 커널로 주변 텍셀의 재질을 센다.
   - 1차원 가중치 0.125, 0.636056, 1, 0.636056, 0.125의 곱을 합 1로 나눈 값이다(중심 0.157207). 지도 가장자리는 감싸 돈다.
   - 투영 변형이 있는 행은 그 꼭짓점의 투영 번호만큼 재질 번호를 더한다. 끝에 합 1로 정규화한다.
5. **꼭짓점 쓰기**(0x5ce920): 텍셀마다 48바이트 꼭짓점 하나(청크 크기 + 테두리 1텍셀).
   - 위치, 텍셀 좌표, 월드 좌표(높이 = u16/255 × 배율)를 쓴다.
   - 가중치 8개(바이트, w×255)와 재질 번호 8개(바이트)를 쓴다.
   - 청크의 8재질이 가중치를 0.001 미만만 가지면 첫 칸을 1로 둔다.
6. **패스 선택**(0x694a60):
   - 반사 캐시 플래그(0xd90f28, 조건은 2.9절)가 꺼져 있으면 패스 0(목표 2개)을 쓴다.
   - 켜져 있으면 `GraphicsDetailSettings.TerrainUseAdvancedGPU`에 따라 패스 1을 쓴다. 패스 1은 같은 커널을 정점 셰이더가 ID 텍스처로 계산하고, CPU는 투영 번호만 쓴다.
   - 그 옵션이 꺼져 있으면 패스 2(CPU 가중치)를 쓴다. 옵션의 초기값은 0이고, 드라이버 우회 코드가 끌 수도 있다.

정리하면 원본의 재질 경계는 "텍셀 ID 지도 → 5×5 커널 가중치 → 청크당 상위 8재질 → 셰이더에서 확산 알파의 8제곱 곱"으로 만들어진다. BaseDominance는 이 과정 어디에도 없다.

### 2.7 조각 선택과 배치 (확정, `retail_piece_placement_probe.json`, `piece_cells.json`)

2.6절 1번의 "배치된 조각"은 아래 규칙으로 정해진다.

1. **칸(HexPatternCell, 8바이트):** u32 지형 비트 마스크, u8 대륙 번호, u8 소유(지도 쪽에서는 "이미 차지됨"), 나머지 2바이트는 쓰이지 않는다. 지도 전체도 같은 칸의 격자로 넘어온다.
2. **조각의 10×10 칸:** 칸 (x, y)는 레코드 0x9c + 8×(x + 10y)에 있다.
   - 조각은 소유 칸을 1–3개 가진다. 소유 칸은 지형 비트 하나와 대륙 번호(0 = 아무 대륙, 1 Amer, 2 Asia, 3 Afri, 4 Euro)를 가진다.
   - 나머지 칸은 0xffffffff(무엇이든 허용)이거나 이웃으로 허용하는 지형 마스크다.
   - 지형 비트: 0 초원, 1 평원, 2 사막, 3 툰드라, 4 설원, 5–9 같은 순서의 언덕, 10 산, 13 해안, 14 대양, 20 암초, 11·12·15–19·21–26 자연 경관. 조각 파일 이름에서 읽은 이 이름은 게임 쪽 코드(2.8절)와 일치한다.
   - 단계(레코드 0x3c8): 4 = 자연 경관과 특수 조각, 3 = 3칸 조각, 2 = 2칸 조각(일부 1칸), 1 = 1칸 조각.
3. **대조 순서**(0x769960 → 0x648a00): 가장 높은 단계부터 0까지 단계마다 한 번씩 돈다.
   - 위치 후보는 열 −2…너비+1, 행 −2…높이+1 전부이며 무작위로 섞는다. 위치마다 조각 순서와 방향 순서도 다시 섞는다. 섞기는 C 런타임 `rand()`를 쓴다.
   - 현재 단계의 조각만 시도한다. 조각의 의미 있는 칸(마스크가 0xffffffff가 아니거나 소유 칸)을 방향·위치 행렬로 지도 칸에 옮긴다. 지도 밖으로 나간 칸은 무시한다.
   - 탈락 조건 1: 조각 마스크와 지도 마스크가 둘 다 0이 아닌데, 공통 비트가 없거나 대륙 번호가 둘 다 0이 아니면서 서로 다르다.
   - 탈락 조건 2: 조각의 소유 칸이 이미 차지된 지도 칸에 닿는다.
   - 통과하고 소유 칸이 하나라도 지도 안에 있으면 (조각, 방향, 위치)를 기록하고 그 지도 칸들을 "차지됨"으로 표시한다. 즉 무작위 순서의 탐욕(first-fit) 배치다.
4. **방향 4종**(0x578b00): 그대로, 거울 2종, 반 바퀴. 60도 회전은 없다. 각 방향은 큐브 좌표 치환과 보정 이동으로 이뤄진다: (0,0,0), (1,−3,2), (−4,0,4), (−2,−3,5).
5. **텍셀 좌표**(0x561da0): 큐브 x = px/64 − py/128 + 0.5, 행 = py/64.
   - 육각 하나가 가로 64텍셀이고 행 간격도 64텍셀이다(행마다 32텍셀 어긋남). 2.6절의 64텍셀 청크는 육각 하나 크기다.
   - 128px 조각 이미지는 2×2 육각, 512px 이미지는 8×8 육각을 덮고, 1:1로 찍힌다. 거울 방향은 찍는 축을 거꾸로 걷는다.
6. **찍기 전 기본값**(0x512b20): 텍셀 ID 3(TerrainDef 3행, 두 사본 모두 Euro_Coast), 높이 합 0, 가중치 합 0.000001.
7. **난수:** 배치는 `rand()` 순서에 달려 있다. 시드는 2.8절에서 확인했다(지도 난수 시드). 따라서 같은 지도와 같은 시드면 배치가 같다.
8. 대조 함수는 직접 호출이 없고, 실행 중 주소를 계산하는 보호 루틴(0x574c00 → 0x675d80)을 거쳐서만 불린다. 본문은 암호화돼 있지 않아 정적으로 읽을 수 있었다.

### 2.8 난수 시드와 지도 칸 채우기 (확정, `retail_map_cells_probe.json`)

1. **시드:** `TerrainSystem::CreateTerrain`(0x709b50)은 맨 처음에 세 번째 인자로 `srand()`를 부른다. 유일한 호출자(0x60abb0)는 그 값으로 게임 컨텍스트 슬롯 0x1c가 준 객체의 슬롯 0x118 반환값을 넘긴다.
   - 공개 SDK 머리말의 슬롯 순서로는 `GetPreGame()->mapRandomSeed()`다. 객체가 어떤 인터페이스인지는 쓰임으로 본 해석이지만, 같은 함수 안의 다른 슬롯 9개도 모두 SDK 순서와 맞는다.
   - `srand` 뒤 대조 전까지 CreateTerrain이 직접 부르는 함수들을 4단계 깊이까지 따라가도 `rand()` 호출이 없다. 가상 호출 너머는 확인하지 않았다.
   - `rand()`는 MSVCR90 구현이다.
2. **플롯 → 칸**(0x60abb0의 첫 번째 플롯 반복):
   - 플롯이 없으면 대양(0x4000), 대륙 0.
   - 지형 5(해안) → 0x2000, 지형 6(대양) → 0x4000. 둘 다 대륙 0.
   - 산이면 0x400.
   - 언덕이면 지형 0 → 0x20, 2 → 0x80, 3 → 0x100, 4 → 0x200, 그 밖(평원) → 0x40.
   - 평지면 지형 0 → 0x1, 2 → 0x4, 3 → 0x8, 4 → 0x10, 그 밖(평원) → 0x2.
   - 대륙 번호는 플롯의 `GetContinentType()` 값이다(물 제외).
3. **지물:** 자연 경관(`IsNaturalWonder`)만 비트를 바꾼다. 숲·정글·습지·얼음 같은 지물은 지형 비트를 바꾸지 않는다.
   - 이름별 비트: GEYSER 0x8000, CRATER 0x10000, POTOSI 0x20000, FUJI 0x40000, MESA 0x80000, REEF 0x100000, VOLCANO 0x200000, ULURU 0x400000, MT_SINAI 0x800000, MT_KAILASH 0x1000000, SRI_PADA 0x2000000, GIBRALTAR 0x4000000, KILIMANJARO 0x800, LAKE_VICTORIA 0x1000.
   - SOLOMONS_MINES는 평지 사막(0x4)이 된다. FOUNTAIN_YOUTH와 EL_DORADO는 바탕 지형 그대로다. 목록에 없는 자연 경관은 FUJI 비트(0x40000)를 받는다.

### 2.9 파일 조회 순서, 반사 캐시 조건, 두 번째 플롯 반복 (`retail_terrain_remaining_probe.json`)

1. **파일 조회 순서(확정):**
   - 시작할 때(0x6d26a0) "Base" 색인 하나에 Resource FPK들(TerrainModels.fpk 포함), `Resource\Overrides`, `*\DLC\*`를 뺀 `Assets`를 넣는다.
   - 콘텐츠 패키지(`*.civ5pkg`)와 모드는 따로 추가 색인으로 등록된다.
   - 조회(0x8181e0)는 추가 색인을 최근 것부터 찾고, 거기서 찾으면 바로 돌려준다. Base 색인은 추가 색인에 없을 때만 쓰인다.
   - 조회 열쇠는 폴더를 뗀 파일 이름이다. 그래서 `assets\terrain\TerrainTextures\TerrainDef.csv` 요청이 어느 폴더의 TerrainDef.csv와도 맞는다.
2. **TerrainDef 사본(해석):** `Assets/DLC/Shared`는 `Upgrade1.Civ5Pkg` 패키지(GUID `{8871E748-29A4-4910-8C57-8C99E32D0167}`, Ownership FREE)이고, 시작 코드가 이 GUID를 직접 요청한다. 따라서 DLC/Shared의 TerrainDef.csv가 FPK 사본보다 먼저 잡힌다.
   - 따라서 0행은 Asia_Tundra, Mesa 축척은 0.05, 아메리카 산 기슭의 투영은 0이다.
   - 추적하지 않은 부분: 그 요청(0x4c94f0)이 패키지를 실제로 켜는지, 패키지 색인에 `Terrain\TerrainDef.csv`가 들어가는지. 폴더 구성으로 보면 그렇지만 코드로 끝까지 따라가지는 않았다.
3. **반사 캐시 플래그(0xd90f28, 확정):** 아래가 모두 참일 때만 1이다.
   - 장치 등급(0x2e49edc)이 8 이상이다. 등급은 Direct3D 기능 수준 9.3 → 6, 10.0 → 7, 10.1 → 9, 11.0 → 10이다.
   - 내부 플래그 0xd90f4c가 0이 아니다.
   - `TerrainDetailLevel`이 2 또는 3이다.
   - `TerrainTessLevel`이 0이 아니다.
4. **두 번째 플롯 반복(확정):** 지도 칸을 건드리지 않는다. 지물 0과 4의 위치를 별도 목록에 넣고, 강이 있는 플롯의 세 변(W, NW, NE)에 강 변 레코드를 만든다. 첫 번째 반복은 지물 2도 별도 목록에 넣는다.
   - 지물 번호 0·2·4는 기본 정의 순서로 얼음·습지·범람원이다(이 순서는 여기서 확인하지 않았다).
   - 따라서 조각 대조가 쓰는 칸은 2.8절 규칙만으로 정해진다.

| 원경 | 지수 거리·높이 안개(FogColor·FogRamp) | 없음 |

## 4. 구현 계획

각 단계는 먼저 통제 부품 검사로 확인한다. 실제 Host 실행은 사용자가 요청할 때만 한다.

### 0단계 — 근거 보강 (정적, 실행 없음)

1. (완료, 2026-11-09) 0x49–0x4e와 0x32–0x35의 패스별 DXBC를 찾고 `fxc /dumpbin`으로 해석했다. 결과는 2.5절과 `terrain_shader_semantics.json`에 있다.
2. (완료, 2026-11-15) `TerrainPiecesLibrary.fxsb`의 컨테이너와 이미지 인코딩, ID 값(TerrainDef 행 번호), 10×10 칸 격자와 조각 선택·배치 규칙을 해독했다(2.2, 2.7절).
3. (완료, 2026-11-15) `hexgridid.dds`·`tf_blend.dds`의 쓰임을 확인했다(2.2절). 두 TerrainDef.csv 중에서는 DLC/Shared 쪽이 적용된다(2.9절, 패키지 활성화 부분은 해석).
4. (완료, 2026-11-09) CPU 쪽 혼합을 따라가서 꼭짓점 가중치 w를 확정했고, BaseDominance가 쓰이지 않음을 확인했다(2.1, 2.6절).
5. 완료 기준: 혼합 가중치와 FOW 색 변환의 수식을 바이트코드 근거로 기록한다(완료). 남은 미확정 부분은 5절에 후보로 남긴다.

### 1단계 — 타일 사이 지형 혼합

1. 타일마다 따로 그리던 부채꼴을 원본처럼 전역 높이장 격자로 바꾼다. 재질은 텍셀 ID 지도로 정한다(2.6절).
2. UV를 TerrainDef의 Texture Scale로 바꾸고, Projection 1 재질은 꼭짓점 법선으로 투영 3종을 고른다(2.1절).
3. 2.5·2.6절의 확정 규칙으로 혼합한다: 텍셀 ID 지도 → 5×5 커널 w → 청크당 상위 8재질 → W = 확산 알파의 8제곱 × w(확산·반사는 제곱 공간에서 평균). BaseDominance는 쓰지 않는다.
   - 텍셀 ID 지도는 2.7절 규칙으로 조각을 배치하고 2.6절 1번대로 찍어서 만든다. 육각당 64×64텍셀이다.
   - 지도 칸은 2.8절 규칙으로 채운다(지형·언덕·산·자연 경관 → 비트, `GetContinentType` → 대륙).
   - 시드는 `mapRandomSeed()`를 쓰고, 섞기는 MSVCR90 `rand()`와 같은 수열을 내는 구현으로 한다. `std::random_shuffle`의 세부(0x907a00, 0x693a00)를 그대로 옮겨야 순서가 같아진다.
   - 통제 검사로 원본 배치와 같은지 확인하기 전까지는 "규칙 동등, 배치 동등은 미검증"으로 보고한다.
4. 반드시 지킬 계약:
   - 타일 선택 ID 표는 지금처럼 타일 단위로 정확해야 한다. 혼합은 색에만 쓴다.
   - 미탐색 타일의 재질이 이웃 혼합을 통해 새어 나오면 안 된다. 미탐색 이웃은 혼합 입력에서 뺀다.
   - 원본 자산은 지금처럼 SHA로 고정한 패키지에 담고, 설치본·MODS는 바꾸지 않는다.
5. 검사: 고정 지도에서 CPU 기준값과 GPU 결과를 대조한다. 타일 ID 표와 기존 입력 계약이 그대로인지, 미탐색 정보가 새지 않는지 확인한다.

### 2단계 — 전장의 안개

1. 타일의 탐색·가시 상태로 FOW 마스크 텍스처를 만들고, 타일 경계에서 부드럽게 바뀌게 한다.
2. 미탐색 영역에 원본 구름 타일 3장을 깐다. 처음에는 단순 흐름으로 시작하고, 0단계에서 흐름장 수식이 확인되면 그것으로 바꾼다.
3. 보이지 않는 탐색 영역의 색 변환을 0단계 근거(FOWColorKey/TransFOWColor)로 바꾼다.
4. 거리 안개에 FogColor.csv와 FogRamp.dds를 적용한다.
5. 검사: 마스크가 SDK의 탐색·가시 상태와 일치하는지, 미탐색 지형 정보가 화면에 나타나지 않는지 확인한다.

### 곡면 기저와 지형 높이 조회 (2026-11-21)

원본 기저를 CPU 모델과 재구성한 곡면 셰이더의 `b7` 상수 버퍼에 반영했다. x64 검사에서 제어점별 높이 표본 4,624개를 독립 커널과 비교했다. 컴파일한 헐·도메인 셰이더에서 버퍼 크기와 필드 위치, 기저 64바이트를 CPU 업로드 구조와 대조했다. 도메인 셰이더는 명시적으로 공급한 기저도 그대로 받는다. [기저와 셰이더 검사](../Tests/original_terrain_bicubic_binding.cpp)

월드 메시와 조명 정점의 높이 조회에서는 가중치가 0인 이웃을 좌표 변환과 탐색 마스크 조회 전에 건너뛴다. 정수 좌표는 해당 텍셀만 조회한다. 물가의 소수 좌표에서는 가중치가 있는 이웃을 사용하며 지도 축별 감싸기와 미탐색 높이 제외 규칙을 지킨다. 이 시점에는 패치 배치와 월드 그리기의 연결이 남아 있었다. [높이와 지도 경계 검사](../Tests/original_terrain_height_binding.cpp)

### 지형 패치 원점·간격과 월드 그리기

설치된 DX11 실행 파일에서 지형 셀 생성, 그리기 상수 기록, 높이 텍스처 주소 계산을 포함한 코드 구간 13개와 수평축 배율을 확인했다. 각 축의 표본 수를 `N`이라 하면 원점은 `-floor(N / 2) × 축 배율`이고, 셀 하나는 최대 64텍셀 간격을 차지한다. 마지막 셀은 남은 간격만큼 그린다. 세부 단계가 바뀌면 가로와 세로의 패치 수를 따로 계산하고 각 축의 실제 폭을 해당 패치 수로 나눈다. 높이를 읽을 때 쓰는 텍스처 페이지 보정값은 그리기 위치와 독립적이다. [원본 코드 구간 검사](../evidence/world_terrain_original/patch_placement/verify_retail_patch_layout.py)

V2 렌더러에서는 셀 끝점을 다음 셀과 공유한다. 지도를 감쌀 때 높이 데이터는 같은 셀에서 재사용하고, 그리는 원점은 지도 폭·높이의 정수배만큼 이동한다. 카메라의 홀수 행 반 칸 이동을 먼저 적용하고 카메라 기준 상대 좌표를 만든 뒤 화면 좌표로 투영한다. 지형 색, 타일 선택 ID와 동적 그림자의 지형 깊이가 같은 배치 함수를 쓴다. [월드 좌표 계산](../Source/Presentation/OriginalTerrainPatchPlacement.h) · [렌더러 연결](../Source/Presentation/OriginalTerrainGpu.inc)

65×65개 제어점의 높이가 모두 공개된 셀에서 안쪽 62×62 구역은 4×4 제어점의 쌍삼차 곡면으로 그린다. 테두리 한 텍셀은 원래 삼각형을 사용하며 곡면의 바깥 변은 그 테두리의 높이에 맞춘다. 미탐색 제어점이나 비순환 지도 끝이 포함된 셀은 기존 삼각형 경로로 그린다. 현재 월드에서는 최대 해상도와 변당 한 구간을 사용해 조밀한 셀당 삼각형 8,192개를 유지한다. [곡면 셰이더](../Source/Presentation/OriginalTerrainTessellationShader.h)

검증 도구는 MSVC x64 최적화·비최적화 빌드에서 D3D11 WARP 소프트웨어 장치를 사용한다. 폭 1~64와 세부 단계 0~4의 320가지 축 조합, 부분 셀의 공유 끝점, 음수 방향의 지도 반복을 검사한다. 셰이더가 생성한 정점 2,808개의 좌표와 높이 변화가 있는 곡면 정점 234개의 내부·테두리 높이를 독립 계산과 대조한다. 월드 6프레임에서는 카메라 이동과 복귀, 타일 선택, 미탐색 경계의 삼각형 경로, 해안이 있는 지도의 그림자 깊이 그리기까지 확인한다. 원본 화면 대조와 물리 GPU 성능 측정은 별도 검증 대상이다. [검사 코드](../Tests/original_terrain_patch_world.cpp) · [실행 도구](../tools/verify_terrain_patch_world.py)

## 5. 열린 질문

- `srand` 뒤 대조 전에 가상 호출 너머에서 `rand()`가 불리는지 여부. 실제 게임과 배치를 한 번 대조해야 확정된다.
- 방향 행렬의 곱셈 순서(0x75f2a0)는 10단계에서 행 벡터의 `T * R(0) * Mirror`로 정적 확정하고 구현을 교정했다. 실제 원본과 전체 배치가 같은지는 여전히 미검증이다.
