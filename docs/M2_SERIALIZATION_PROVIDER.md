# M2: 열거형·컨테이너 직렬화의 x64 구현과 저장 폭 보존

현재 상태: 후속 CRC·잠금·시간·메모리 단계에서 10개를 더 해소하여 미해결 심볼은 140개, 정합성 검사는 80개이와요. 아래 278→150개와 73개 검사는 직렬화 추가 단계의 기록이랍니다. [최신 기반 제공자 기록](M2_FOUNDATION_PROVIDER.md)

2026-09-24 기준으로 열거형 81종과 표준 문자열의 실제 x64 구현을 GameCore 연결 검사에 반영했사와요.
미해결 심볼은 **278→150개**, 추가된 미해결 심볼은 **0개**랍니다.
해소한 128개는 실제 GameCore가 요구하는 열거형 연산자 126개와 표준 문자열 연산자 2개이와요.
전체 GameCore DLL·실행부·게임 멀티코어 실행은 아직 미완료랍니다.

## 요구사항과 변경 범위

| ID | 요구사항 | 수용 근거 |
|---|---|---|
| SER01 / F07 | x86 SDK 열거형의 실제 저장 폭·부호·바이트 순서 보존 | 81종 × 1,685개 입력 × 3개 endian 모드의 쓰기·읽기 비교 |
| SER02 / F07 | 컨테이너·리플레이·투표의 항목 수는 기존 unsigned 32비트 유지 | 39개 순서 있는 출력의 바이트 일치, 양방향 교차 읽기 90건 |
| SER03 / N01 | 표현 불가능한 네이티브 항목 수를 잘라 저장하지 않음 | 일반 순차·연관 컨테이너의 2^32 항목 수 거부, 기존 스트림 상태 보존 |
| SER04 / F07 | 기존 리플레이 병합·투표 선택지 추가 동작 보존 | 이미 값이 있는 대상으로 읽기 48건 |
| SER05 / N03 | 현재 코드·실행 자료·연결 검사·Stage 추적 | 공유 제공자 검증 관문과 정합성 검사 73개 |
| SER06 / F05 | 순서 없는 컨테이너의 차이를 숨기지 않음 | 값과 양방향 읽기는 일치, 저장 순서 차이 6건은 미해결로 명시 |

변경은 이 독립 프로젝트의 제공자 코드, 시험·도구와 생성 SDK 이식본에 한정했사와요.
정식 SDK 패치 계획에는 직렬화 항목 9개를 추가하여 **452개 패치·56개 SDK 파일**이 되었답니다.
숫자 경계값 수정을 포함한 기존 이식 패치 443개는 attempt_009의 계획과 대조하여 내용이 같음을 확인했사와요.
원본 SDK·게임·MODS·Mod ID·버전·저장 키·스키마·밸런스는 보존했사와요.
산출물은 Source → Build → Stage까지이며 설치 가능한 게임 DLL이 아니와요.

## 실제 SDK 참조와 형식

VC9 x86 참조는 원본 `CvGameCoreDLLUtilWin32.lib`의 `CvEnumSerialization.obj`와
`FireWorksWin32.lib`의 `FStlContainerSerialization.obj`를 연결했사와요.
링크 지도에서 열거형 연산자 162개와 표준 문자열 연산자 2개의 실제 제공자를 확인했답니다.
새 x64 제공자 2개 C++ 파일과 시험 프로그램은 VS2022 /MD로 경고 없이 빌드되었사와요.
참조 실행에 필요한 빈 FString 공유 저장소는 기존 스트림 시험의 연결 코드를 재사용했으며,
GameCore DLL·기존 게임을 로드하지 않았사와요.

| 항목 | 보존한 실제 규칙 |
|---|---|
| 일반 열거형 80종 | 4바이트 정수 비트값; endian 설정에 맞게 저장 |
| `GameTypes` | 메모리에서는 4바이트이지만 저장은 1바이트; 읽을 때 부호 확장 |
| 표준 문자열 | 4바이트 길이와 원시 바이트; 중간 NUL도 보존 |
| 순차·연관 컨테이너 | 항목 수는 unsigned 32비트; 네이티브 `size_t`를 파일 형식으로 사용하지 않음 |
| 리플레이 `TurnData` | 4바이트 항목 수, unsigned 32비트 턴과 signed 32비트 값; 기존 대상에 병합 |
| 투표 `VoteSelectionData` | 기존 버전 1과 필드 순서·열거형·문자열 유지; 읽은 선택지를 기존 대상에 추가 |

입력 1,685개에는 작은 값, 최솟값·최댓값·비트 패턴, 실제 알림 식별자 142개의 값과 고정 시드 난수가 포함되었사와요.
`GameTypes`의 범위 밖 입력도 실제 SDK처럼 하위 1바이트를 쓰고 읽을 때 부호를 확장하는지 비교했답니다.
이는 실제 게임에서 범위 밖 열거형이 유효하다는 뜻은 아니와요.

## 경고 없이 달라지던 저장 형식

SDK 컨테이너 템플릿은 항목 수를 `size_t` 또는 `ContainerType::size_type`으로 쓰고 읽었사와요.
x86에서는 4바이트였지만 x64에서는 8바이트 연산자가 선택되어 형식이 달라졌답니다.
기존 숫자 축소 경고가 0건인 상태에서도 생기는 문제였사와요.

수정 전 실행 자료에서는 정수 5개 vector가 **24→28바이트**, 빈 vector가 **4→8바이트**,
중첩 vector가 **48→64바이트**로 늘어났사와요.
[수정 전 관측 기록](../evidence/serialization/before_width_fix/width_evidence.json)은 보관된 과거 이진 출력에 관한 기록이며,
해당 빌드 보고서가 가리키는 현재 소스까지 같은 상태라는 뜻은 아니와요.

`FStlContainerSerialization.h`의 공통 템플릿, `CvReplayInfo.cpp`의 TurnData 연산자,
`CvStructs.cpp`의 투표 선택지 읽기·쓰기를 고쳤사와요.
쓰기에서는 기존 검사 함수를 통해 unsigned 32비트 범위만 허용하고, 읽기는 같은 고정폭 형식을 사용한답니다.
컨테이너 시험에서 2^32 항목 수는 실제 거대 할당 없이 거부했으며,
최대 unsigned 32비트 값의 4바이트 기록도 확인했사와요.
이를 해당 개수의 항목이나 4GB 파일 전체를 실제 할당·저장한 시험으로 계산하지 않사와요.

직접 `size()`를 쓰는 다른 후보도 확인했사와요.
`FFastVector`, `FStaticVector`, 건설 AI의 비영토 목록, 종교 신앙 목록은 이미 unsigned 32비트 크기를 반환하므로 이 변경에 포함하지 않았답니다.
이 조사는 해당 경로에 대한 집중 점검이며 모든 게임 저장 경로의 전수 검증은 아니와요.

리플레이와 투표 시험에는 원본·이식본의 실제 함수 본문과 선언을 각각 추출하여 사용했사와요.
TurnData의 소유 클래스만 시험에 필요한 최소 형태로 구성했으며, 완전한 `CvReplayInfo` 객체나 전체 GameCore를 실행하지는 않았답니다.

## 검증 결과와 남은 차이

| 계층 | 결과 | 의미 |
|---|---|---|
| 실제 열거형 실행 | 각 아키텍처의 쓰기·읽기 쌍 409,455건, 기록 1,622,655바이트 | x86·x64·별도 Python 바이트 기준 일치 |
| 순서 있는 복합 자료 | 13개 사례 × 3모드 = 39개 출력 | x86·x64 바이트 일치 |
| 양방향 읽기 | 15개 사례 × 3모드 × 2방향 = 90건 | x86가 x64 기록, x64가 x86 기록을 읽고 값·끝 위치 확인 |
| 기존 대상에 읽기 | 리플레이·투표 4개 사례 × 12회 실행 = 48건 | 병합·추가의 기존 동작 유지 |
| 순서 없는 자료 | hash_map·unordered_set × 3모드 = 6개 출력 차이 | 논리 값은 같지만 순서와 바이트는 다름 |
| 회귀 | 할당기 18,240회 단언, 숫자 274,922회 단언, 스트림 92,160개 필드 재검증 | SDK 패치 변경 후 관련 독립 시험 통과 |
| 컴파일·연결 | BNW C++ 161개 AMD64 오브젝트, attempt_011 링크 150개 미해결 | 아직 DLL 생성 실패 |
| 추적성 | 정합성 73개 검사 통과 | 현재 원본·소스·빌드·출력·Stage 정합성; 새로운 게임 실행 증거가 아님 |

hash_map과 unordered_set의 바이트 차이는 VC9와 VS2022의 반복 순서 차이랍니다.
VC9의 컨테이너 동등 연산도 반복 순서를 비교하므로 값 검증에는 정렬한 키·값을 사용했사와요.
바이트 비교는 별도로 유지하여 이 차이를 숨기지 않았답니다.
저장 파일을 서로 읽을 수 있다는 사실만으로 게임의 반복 순서·AI 선택·동기화가 같다고 판단하지 않사와요.
순서를 임의로 정렬하는 게임 코드 변경 역시 이번에 적용하지 않았답니다.

남은 컴파일 경고는 고유 위치 기준 **343곳**으로, 문자 인코딩 325곳·구식 선언 5곳·구식 API 13곳이랍니다.
이 경고와 **150개 미해결 연결 심볼**은 서로 다른 목록이와요.
FString, FAutoArchive, 데이터베이스·현지화, 지도 편집 자료, 잠금·시간·기타 기반 서비스의 실제 구현이 더 필요하답니다.
이후 전체 저장 파일·오류 복구·새 게임·턴·도시·유닛·UI·저장과 불러오기·멀티플레이·성능 관문이 남아 있사와요.

현재 150개 이름을 선언 대상별로 분류하면 다음과 같사와요.
이는 링크 오류 이름의 분류이며 실제 호출 빈도·구현 난도·게임 실행 의존성 전체를 뜻하지 않사와요.

| 대상 | 미해결 이름 수 |
|---|---:|
| 데이터베이스 | 41 |
| 지도 편집 자료와 모드 필드 | 32 |
| 자동 상태 저장·차이 기록·문자 변환 | 24 |
| 현지화 | 16 |
| FString·문자 인코딩 변환 | 12 |
| Lua 값·표 래퍼와 오류 경계 | 8 |
| 임시 메모리·정렬 할당 | 5 |
| 임계 영역 | 4 |
| 파일·로그·진단 | 4 |
| CRC | 2 |
| 시간 측정 | 2 |

후속 구현에서는 기존 독립 CRC 검증을 SDK 클래스에 연결하고,
임계 영역·시간·메모리의 실제 SDK 계약을 확인한 뒤 각 제공자의 실행·연결 증거를 추가하는 순서로 진행하와요.
범용 성공값이나 빈 함수로 미해결 수를 줄이지 않으며, 자동 상태 저장과 순서 차이는 저장·동기화 계약에서 별도 검토할 대상이랍니다.
