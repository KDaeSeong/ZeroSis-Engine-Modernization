# 실행부 Lua 실행의 게임 상태 접근 제어

게임 라이브러리를 연결한 VM에서 실행·이벤트 전달이 소유 스레드와 GameCore 잠금을 모두 확인하도록 보완하와요. 대상은 별도 실행부의 `ScriptSystem`과 검증 도구이며, SDK 인터페이스·게임 규칙·Mod ID·기존 저장 키와 스키마를 변경하지 않사와요. 배포는 이 프로젝트의 Source → Build → Stage/NativeHost 범위랍니다.

| 요구사항 | 완료 기준 |
|---|---|
| SL01 | LoadFile·Execute·RegisterFunction·CallCFunction·CallFunction·이벤트 5종 모두 게임 라이브러리 연결 시 소유 스레드와 잠금을 검사 |
| SL02 | 거부 시 Lua 스택·함수 등록·이벤트 출력값·게임 콜백을 변경하지 않고 같은 VM의 정상 재시도 허용 |
| SL03 | 다른 스레드가 실제 잠금을 보유한 경우에도 호출을 거부하며, 자동으로 잠금을 얻거나 게임 소유 스레드로 위장하지 않음 |
| SL04 | 접근 조회의 표준·비표준 C++ 예외를 오류 반환으로 전달; VM 생성·반납·종료에도 같은 검사 적용 |
| SL05 | 실제 NativeReference의 무효화 오류, C++/Lua 오류 후 복구, 다른 스레드 거부와 잠금 중 finalizer 실행 확인 |
| SL06 | 직전 실행부에서 실제 컴파일된 원본 헤더·수정 헤더, /O2·/Od 실행, 현재 실행부 소비와 Stage 해시를 연결 |

## 결함과 구현

기존 실행부는 게임 라이브러리 등록과 VM 생성·반납·종료 때 잠금을 확인했지만, 파일 실행·함수 호출·이벤트 전달에서는 VM 소유 스레드만 확인했사와요. 게임 상태를 다른 작업자가 잠근 동안에도 소유 스레드가 Lua를 통해 게임 콜백을 실행할 수 있는 경로였답니다.

`ExecutionAccessOrReject`는 먼저 VM 소유 스레드를 확인하고, 게임 라이브러리가 연결됐다면 실행부의 게임 소유 스레드와 현재 스레드의 잠금 보유를 검사하와요. 모든 실행 경로가 Lua API·파일 준비·이벤트 인수 복사보다 먼저 이 검사를 수행하와요. 조회 실패는 고정 오류 버퍼에 남기며 예외를 `noexcept` 종료 함수 밖으로 흘리지 않사와요. 게임 라이브러리가 없는 데이터 점검 VM은 기존대로 자신의 소유 스레드에서 실행하와요.

원시 `lua_State*`를 직접 사용하는 외부 호출자까지 자동으로 보호하는 장치는 아니랍니다. 원시 Lua API를 호출하는 코드도 게임 소유 스레드와 잠금을 유지해야 하며, 전체 GameCore 객체의 동시 수정 안전성이 입증된 것은 아니와요.

## 검증 범위

원본 `HostServices.h`와 `ScriptSystem.h`는 직전 정식 실행부가 소비한 바이트 그대로 `Source/HostScriptAccess`에 고정했사와요. 실제 Lua 제공자·실행부·재귀 잠금을 사용하며, 게임 라이브러리와 참조 대상 게임 객체는 시험용 대체물이랍니다. GameCore DLL을 불러오지 않사와요.

| 시험 | 결과 |
|---|---|
| 원본 실행 경계 | 10개 API × 6개 조건 × 두 최적화 구성, 잘못된 접근 120건 허용 |
| 원본 잠금 없는 콜백 | 잠금 없음·다른 작업자 잠금 보유 조건에서 실제 시험 콜백 36회 실행 |
| 수정 실행 경계 | 같은 120건 거부, 콜백 0회·스택과 등록/출력값 보존, 같은 VM의 정상 재시도 |
| 조회 오류와 VM 수명 | 잘못된 소유 스레드 응답·조회 예외에서 생성/반납/종료 거부 후 정상 종료 |
| 실제 참조 형식과 오류 복구 | 무효화된 NativeReference·C++/Lua 오류 전달 후 정상 재호출 |
| 다른 스레드와 종료 | 구성별 외부 스레드 호출 12건 거부, finalizer는 소유 스레드가 잠금을 가진 상태에서 실행 |
| 수정본 검사 | 두 최적화 구성 합계 1,440개; 원본 2개·수정본 2개 독립 프로세스 |

정식 실행부가 수정 헤더를 소비하도록 다시 빌드하고, 기존 실행부 검사 20,948개·24개 프로세스와 DLL 예외 수명 검사 874개를 다시 통과했사와요. Source → Build → Stage/NativeHost와 검토 자료의 일치를 확인했으며 프로젝트 무결성 검사 310개를 통과했답니다. `evidence/host_script_access/conformance.json`은 현재 실행 근거이며, 초기 original/candidate 단독 보고서는 당시 탐색 이력으로만 보관하와요.

기존 수명 시험의 스크립트 등록·실행 호출부에도 잠금이 빠져 있어, VM 생성부터 콜백 호출까지 기존 GameCall 범위를 유지하도록 시험 호출부를 수정했사와요. 종료 거부 시험은 접근 검사까지 통과한 뒤 실제 활성 콜백 종료 오류가 나오는지 확인하여, 새 접근 거부를 기존 수명 검사 성공으로 오인하지 않도록 했답니다.

## 재현과 남은 관문

```text
python tools/build_host_script_access.py
python tools/verify_host_script_access.py
python tools/host_script_access_evidence.py
```

정식 `build_native_host.py`와 `verify_native_host.py`도 이 구성요소 빌드·실행을 포함하와요. 실행부 자체의 기존 20,948개 검사와 이번 별도 검사 수는 분리해 기록하와요. 실제 GameCore의 Lua 메서드·소유 객체·잠금 호출부, 첫 지도 생성·턴·저장, 게임 계산의 병렬화와 원본 동등성은 여전히 남아 있사와요.
