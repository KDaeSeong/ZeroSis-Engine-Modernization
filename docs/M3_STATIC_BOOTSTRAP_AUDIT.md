# 실제 x64 DLL의 초기화·종료 조사

정식 DLL에는 링크 지도가 없어, 같은 입력으로 만든 진단 DLL의 지도를 함께 사용했사와요. 두 DLL의 이미지 기준 주소·섹션 RVA, 전체 `.text`·`.pdata` 바이트와 CRT 포인터 표가 같음을 검사한 뒤 **정식 DLL의 바이트**를 해석했사와요. 데이터베이스와 현지화 DLL은 각각 자신의 링크 지도를 사용하와요. 전체 역어셈블 로그·입력 해시·도구 해시는 `evidence/bootstrap/static_initialization`에 남겼답니다.

## 정적 분석의 한계와 실행부 연결 조건

호출 그래프는 실제 x64 명령의 직접 호출·직접 분기를 따라간 결과랍니다. 조건의 값과 인수는 전파하지 않으므로 실패 처리 경로도 포함하와요. 운영체제·C++ 런타임 DLL 내부, 미결정 함수 포인터·가상 호출, 예외 처리 표의 별도 핸들러와 전체 DLL 진입점은 분석을 끝내지 않았사와요. 종료 함수는 컴파일러 소멸자 주소 참조를 출발점으로 삼았으므로 모든 종료 등록을 찾았다는 보증도 아니랍니다.

새 호스트는 게임 상태를 직접 소유해야 하와요. DLL 로딩과 `DllGetGameContext` 성공만으로 게임 준비 완료라고 표시하지 않으며, 호스트 서비스 연결 → 규칙 DB와 자산 준비 → 실제 GC 초기화 → 실제 지도·플레이어·도시·유닛 생성 → 턴 진행을 따로 확인해야 한답니다. 실제 게임의 규칙·난수·저장 동등성과 병렬 계산은 그 이후의 수용 관문이랍니다.

관련 기준은 [Microsoft CRT 초기화 순서](https://learn.microsoft.com/en-us/cpp/c-runtime-library/crt-initialization?view=msvc-170), [DLL 초기화 권고](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-best-practices), [PE/COFF 형식](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)이랍니다. 로더 문맥의 제약은 DllMain 본문뿐 아니라 그 과정의 전역 생성·소멸에도 적용되므로, 등록된 함수 목록을 얻은 것만으로 실행 관문을 통과했다고 판단하지 않사와요.
