- **CRC·잠금·시간·정렬 메모리를 실제 SDK 형식으로 연결했사와요.** 각 아키텍처의 CRC 결과 35,924개, 작업자 1·2·4개의 보호된 갱신 140,000회, 메모리 배치 378개와 작업자 할당 4,096회를 검증했답니다. 당시 연결 오류 10개를 해소하여 150→140개로 줄였사와요. [기반 제공자 기록](docs/M2_FOUNDATION_PROVIDER.md)

- **열거형·컨테이너·리플레이·투표의 저장 폭을 보존했사와요.** 열거형 81종의 쓰기·읽기 409,455건과 양방향 자료 읽기 90건이 통과했고, 당시 실제 연결 오류 128개를 추가 해소하여 278→150개로 줄였답니다. 해시 기반 목록의 저장 순서 차이 6건은 별도 미해결 항목이와요. [직렬화 제공자 기록](docs/M2_SERIALIZATION_PROVIDER.md)

- **메모리·직렬화 스트림 제공자를 연결했사와요.** 실제 x86 SDK와 92,160개 필드·405,504바이트가 일치했고, 당시 연결 오류 24개를 해소하여 302→278개로 줄였답니다. 잘못된 위치 이동 후 상태 손상도 보완했사와요. [스트림 제공자 기록](docs/M2_STREAM_PROVIDER.md)

- **Lua x64 제공자 연결을 반영했사와요.** 실제 x86 DLL과의 변환 차이 297건을 수정하여 74,616개 결과가 일치했고, GameCore 연결 오류 40개를 해소했답니다. 제공자 29개 오브젝트는 경고 없이 빌드되었사와요. [Lua 제공자 기록](docs/M2_LUA_PROVIDER.md)

- 별도 SDK 이식본의 **96개 파일·572개 패치 항목**으로 Lua 입력, 고정폭 개수·명령 필드, 알림 비트값, 메모리 크기·소유권·파일 실패 처리와 현지화 내부 접근 선언 등을 수정했사와요. BNW C++ **161개 모두 AMD64 오브젝트 생성**에 성공했답니다.
- 숫자 변환 **42,250개 입력·274,922회 단언**, 실제 Lua의 **74개 사례·오류 후 복구 39회**, 알림 식별자 **142개**의 비트값과 순서를 검증했사와요. 시험 프로그램은 경고 없이 빌드되었답니다. [숫자 경계값 기록](docs/M2_NUMERIC_BOUNDARIES.md)
- 실제 수정 SDK 할당기에서 **196개 배열 배치·단언 18,240회**, 4GB 경계보다 높은 가상 주소의 할당 197회와 크기 넘침 거부를 검증했사와요. 이 독립 시험은 경고 없이 빌드되었답니다.
- 전체 GameCore의 기존 `/W3` 설정에는 **343개 경고 위치**가 남아 있사와요. 별도로 강한 설정에서 드러난 8·16비트 변환 224곳도 검토 목록으로 보존했답니다. DLL 링크의 **미해결 심볼은 0개**이며 DllMain의 명시적 초기화는 후속 진입점으로 옮겼사와요. 게임 실행이나 저장 호환성 통과로 계산하지 않사와요.
- `CvCompatibleRandom`: SDK 난수 산술·카운터 동작을 명시적 32비트 상태로 이식하였사와요.
- 독립 x86 참조와 x64 구현의 **197,643개 이진 기록**이 모두 같았으며, 별도 Python 정수 기준과도 일치했사와요. 두 수치 시험 프로그램은 경고 없이 빌드되었답니다.
- `CvCompatibleCrc32`: **실제 SDK의 x86 CRC 코드**와 새 x64 구현을 5,381개 입력에서 대조하여 전체·분할 계산 10,762건이 일치했사와요.
- `OrderedBatch`: 작업자 **1·2·4개**, 24개 입력 배치의 **72회 실행·4,608개 결과**가 일치했사와요. 역순 완료, 중복 ID, 취소·예외, 다른 작업자 취소와 종료 대기도 검증했답니다.
- `VersionedState`: 오래된 결과·중복 반영·잘못된 소유자와 스레드를 거부하고, 후보 상태를 준비한 뒤 한 번에 교체하와요. **21개 시험 사례, 상태 반영 2,304회·기록 18,432개**를 검증했으며, 취소·준비 예외·복사/이동 실패에서 현재 상태를 보존했사와요.
- SDK **1,105개 파일을 원본 그대로 복사**하고 BNW C++ 161개에서 x86 GameCore DLL을 생성했사와요. 원본 소스 대신 버전 리소스 헤더 연결만 별도 보완했으며, 기존 소스·개발 도구·라이브러리의 경고는 기록에 남겼답니다.
- 73개 인터페이스 클래스의 선언 1,579개, 호출 후보 1,672개, 라이브러리 공개 심볼 4,159개를 조사했사와요.
- 실제 기준 오브젝트의 외부 요구 이름 470개 중 **341개가 SDK 라이브러리 후보와 일치**했사와요. 최종 링크 지도에서도 제공자를 확인하여 기반 서비스 대체 작업의 근거를 마련했답니다.

구현·제약은 [진행 기록](docs/M1_CONTRACTS_AND_NUMERICS.md), 수치 검증은 [실행 결과](evidence/numerics/conformance.json), 기준 DLL은 [빌드 기록](evidence/sdk_reference/build_result.json), 연결 요구사항은 [링크 조사](evidence/link_dependencies/link_inventory.json)에 있사와요. 수치 참조는 SDK 산술식을 추출한 독립 프로그램이며 원본 GameCore 실행이 아니와요. **기준 DLL과 Civ V 자체는 실행하지 않았사와요.**

새 CRC·작업 실행기의 세부 계약과 시험 범위는 [두 번째 구현 기록](docs/M2_CRC_AND_ORDERED_JOBS.md)에 있사와요. 작업자의 콜백 실행 구간이 겹치는 것은 확인했지만, 물리 코어의 명령 동시 실행·게임 턴 병렬화·속도 향상을 측정한 결과는 아니랍니다.

값 상태 반영 API와 수명·취소·실패 계약은 [상태 반영 기록](docs/M2_STATE_COMMIT.md)에 있사와요. 이 시험은 별도 값 자료를 실제 작업 실행기와 연결한 결과이며, 기존 GameCore의 도시·유닛·저장 객체를 연결한 결과는 아니랍니다.

## 확정한 요구사항과 작업 범위

- 사용자 확정 목표: **64비트·멀티코어를 목표로 엔진 개조**.
- 변경 범위: 이 독립 프로젝트의 조사 도구, 난수·CRC·작업 실행기·값 상태 소유자와 시험, 원본 SDK 복사본·x86 기준 빌드·별도 x64 이식본, 증거 자료와 이식 설계.
- 영향 분석 대상: Windows 실행부, BNW GameCore, 기반 라이브러리, Lua·UI·자산 처리, 저장·네트워크·난수, 기존 ZEROSIS 모드 연동.
- 저장 호환성: 기존 파일·Mod ID·버전·저장 키·스키마를 보존하며, 새 엔진의 호환성은 앞으로 검증할 요구사항이랍니다.
- 배포 범위: 이 프로젝트의 Source → Build → Stage. Stage에는 검증된 수치·작업 실행기·값 상태 소유자 헤더와 기록을 보관하며, 기준 DLL·시험 프로그램은 연구용 Build에 남겼사와요. 게임 설치 경로·기존 모드 Source·Build·설치 MODS에는 배포하지 않았사와요.
- `Stage/GameCore_x64`는 변경한 SDK 소스 98개, 지원 헤더 7개, 패치 계획과 16개 제공자의 소스·라이선스·시험·연결 증거 및 AMD64 DLL을 담은 검토 묶음이랍니다. 종료 객체 정리의 원본·수정본 시험 증거도 포함하와요. 게임 실행과 설치 가능한 패키지의 검증은 아직 남아 있사와요.
- 기존 모드 밸런스, 효과, 장식적인 UI의 변경은 이번 엔진 목표에 포함하지 않았사와요.

## 현재 파일에서 확인한 사실

조사일은 2026-09-22이며, 원시 자료는 [baseline.json](evidence/2026-09-22/baseline.json)에 있사와요.

| 대상 | 확인 결과 | 개조에 주는 의미 |
|---|---|---|
| 기본·DX11·태블릿 게임 실행 파일 | 모두 x86 / PE32 / LAA 켜짐 | 실행부 자체의 이식 또는 대체 필요 |
| 기본 BNW GameCore DLL | x86 / PE32 | x64 실행부와 함께 다시 구성할 대상 |
| SDK BNW 게임 로직 | C++ 161개, 헤더 173개 | 실제 분석·이식의 출발점 확보 |
| SDK BNW 빌드 설정 | Win32, MachineX86, DynamicLibrary, v90 | x64 대상과 연결 규약을 별도로 설계할 필요 |
| SDK 제공 라이브러리 | 7개 모두 x86 헤더 관측 | x64 구현·라이브러리의 확보 또는 대체 필요 |
| SDK 기반 서비스 모듈 | 헤더는 있으나 해당 디렉터리에 C/C++ 구현 파일 없음 | 현재 SDK만으로 전체 엔진 재빌드 불가 |
| GameCore의 `gDLL->...` 표현 | 977곳, 이름 160종 | 실행부와의 결합을 분리하는 작업 목록 |
| 설치 MODS의 GameCore DLL 보유 폴더 | 5개 폴더 / DLL 7개 | 향후 비교 기준과 모드 의존성 확인 필요 |
| 조사 입력 파일 | 1,139개 SHA-256 기록, 수집 전후 모두 일치 | 관측 대상의 조사 중 변경 없음 |

`gDLL` 수치는 주석이 포함될 수 있는 텍스트 검색 결과랍니다. 전체 엔진 API 수, 실행 중 호출 횟수, 병목 수를 의미하지 않으며 간접 호출과 다른 인터페이스는 별도 조사 대상이와요.

DLL 보유 폴더 5곳은 Community Patch, Gaia v537, Gaia v600, Civilization IV Diplomatic Features v11, ZeroSis' Spear of Adun v1이랍니다. 설치되어 있다는 사실만 확인했으며, 현재 활성화·로드 상태를 확인한 것은 아니와요. DLL의 LAA 표시는 파일 속성 기록일 뿐이며, 프로세스 주소 공간 판단은 게임 EXE 기준이랍니다.

설치 폴더에 있는 `steam_api64.dll`은 x64이지만, 조사한 DX11 EXE는 `steam_api.dll`을 가져오고 있사와요. 개별 x64 DLL의 존재는 게임의 64비트 전환을 의미하지 않는답니다.

## 핵심 판단

현재 확보된 것은 **전체 게임 엔진 소스가 아닌 GameCore SDK**이와요. SDK의 C++ 로직을 그대로 x64로 다시 빌드하려 해도 기반 라이브러리와 실행부가 연결되지 않사와요. 32비트 프로세스는 일반적인 방식으로 64비트 DLL을 로드할 수 없다는 Windows 제약도 있답니다. [Microsoft 프로세스 상호 운용 문서](https://learn.microsoft.com/en-us/windows/win32/winprog64/process-interoperability)

따라서 현재 확인한 자산을 바탕으로 한 설계 경로는 **새 64비트 실행부와 기반 서비스에 기존 게임 로직을 이식하는 재구현**이랍니다. 이후 전체 엔진 소스나 사용 가능한 x64 기반 라이브러리가 별도로 확인되면 재사용 범위를 다시 평가할 수 있사와요. 아직 실행부·렌더러의 구현 소스가 확보된 상태는 아니와요.

세 EXE는 이미 LAA를 사용하므로 해당 플래그를 다시 켜는 변경은 필요하지 않답니다. 64비트 Windows의 LAA 적용 32비트 프로세스는 최대 4GB 사용자 가상 주소 공간을 쓰지만, 이것은 64비트 실행 코드나 4GB를 넘는 게임 주소 공간을 제공하지 않사와요. [Microsoft 메모리 제한 문서](https://learn.microsoft.com/en-us/windows/win32/memory/memory-limits-for-windows-releases)

멀티코어는 새로운 목표 구조에서 계산과 상태 변경을 분리해 구현할 예정이와요. Civ V가 원래 멀티코어를 전혀 사용하지 않는다는 전제는 두지 않사와요. Firaxis·Intel의 2010년 발표에는 TBB와 멀티코어 대응이 이미 설명되어 있답니다. [GDC 발표](https://gdcvault.com/play/1012982/Firaxis-Civilization-V-A-Case)

## 현재 개발 관문

현재 M3/M6 실제 실행 증거는 **영어·한국어 새 게임과 정상 턴 진행, turn-zero 도시 건설, 도시 생산·연구 선택 뒤 turn-one 진행, 각 checkpoint의 fresh-session native 복원**까지랍니다. 도시 결정 명령은 격리 host의 공식 SDK Lua/Network API에서 실제 SDK receiver로 전달했으며 화면 입력이나 decision UI 통합을 입증하지는 않사와요. retail 저장 호환성·장기 진행·완전한 상태 동등성은 남아 있답니다. M5 도시 부지 평가는 최초 0·1·2·4 작업자 행렬과 현재 0·4 작업자 행렬을 별도 50턴 실행으로 통과했고, 별도 실제 ETL에서 QPC 오차 정책을 적용한 서로 다른 물리 코어의 실행 겹침도 확인했사와요. 이 함수 범위의 증거이며 게임 전반 멀티코어·속도 향상은 남아 있답니다. renderer, 사용자 gameplay 입력, 활성 모드 연결과 정식 Stage 승격도 남아 있사와요. [도시 결정과 복원](docs/M6_CITY_DECISIONS.md) · [도시 건설 이력](docs/M6_FOUND_CITY_ACTION.md) · [M5 부지 점수 기록](docs/M5_CITY_SITE_SCORES.md) · [M5 탐색 작업자 기록](docs/M5_SDK_EXPLORATION_WORKERS.md)에 범위를 나누어 두었답니다.

GameCore의 x64 컴파일·링크와 구성요소 계약은 별도 기록에서 확인했으며, 앞서 남은 정적 분석·기반 라이브러리 작업이 전부 끝났다는 뜻은 아니랍니다. 실제 한 사이클을 통과한 격리 후보도 아직 설치 게임이 아니고, 화면 표시나 게임 상태 계산의 멀티코어화는 별도 구현·검증 과제이와요.

그다음 화면 없는 x64 게임 로직 실행, 단일 스레드 결과 비교, 병렬 계산의 동일 결과 검증, UI·렌더링 통합으로 진행하도록 [초기 엔진 설계](docs/ENGINE_PLAN.md)에 관문을 나누었사와요. API·의존성 작업 목록은 [엔진 서비스 목록](evidence/2026-09-22/engine_services.csv), 세부 호출 위치는 [호출 근거](evidence/2026-09-22/engine_host_calls.csv)에 있답니다.
